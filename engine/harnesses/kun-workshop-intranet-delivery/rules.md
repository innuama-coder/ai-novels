# Harness Rules

## Authority Order

1. 本 harness 的 `workflow.md`、schemas 与已通过的门禁定义流程事实。
2. 调用方明确确认的产品范围、数据分级、环境政策和变更授权优先于任何 agent 推断。
3. leader 的记录化决策在已批准范围内有效；架构师、QA 和安全角色可提出否决性风险，但不能自行改写业务范围。
4. 原型和产品文档是需求证据；相互矛盾或缺失时必须形成开放项，不得静默选择。

## Tool Rules

- 只在授权工作区、仓库、测试服务和预发布环境内操作；生产环境和真实生产数据禁止。
- 不记录、输出或提交密钥、令牌、个人信息和内部凭证。使用已批准的密钥注入方式。
- 任何迁移、部署、基础设施变更或外部消息都要先验证目标、变更单、回滚路径和权限。
- 调度者可创建/追踪工作包，不能修改代码、批准门禁、部署或选择技术方案。

## File Rules

- 规范制品置于项目的 `delivery-runs/<run-id>/`；每阶段独立目录，禁止覆盖既有完成包。
- 完成包、评审、决策和预发布证据以 UTF-8 JSON/Markdown 存储，并记录制品哈希。
- 缺陷、假设和范围变更必须具备 ID、来源、影响、owner、状态和决策记录。
- 测试报告必须可定位到版本、环境、时间、执行命令与原始日志/截图/追踪引用。

## Human Approval Rules

人类必须明确批准：范围或验收标准的重大变更、数据处理/权限模型、不可逆架构选择、超过两轮回流、预发布变更窗口及实际部署。批准记录需包含批准人、范围、时间、目标版本和可撤销条件。沉默、聊天摘要或 agent 自述不是批准。

## Done Rule

不得把“代码已生成”或“部署命令已准备”说成上线完成。只有 G4 消费预发布部署与验收证据，且无未接受的阻断风险，才可声明 `complete`；没有 G3 授权或 S6 证据时，最终交付只能为 `partial` 或 `blocked`。
