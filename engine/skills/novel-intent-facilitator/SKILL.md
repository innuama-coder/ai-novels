# 小说意图访谈

## 任务边界

产出一张**意图卡**，回答“这部小说要成为什么、绝不成为什么、哪些选择必须由作者作出”。意图卡是后续主体设计的输入，不是大纲、人物卡、世界观百科或 prose。

仅在作者明确确认后，将内容标记为 `confirmed`。将合理猜测标记为 `inference`，将未定内容标记为 `open`；不得把三者混写。

开始访谈前读取 [interaction-methodology.md](references/interaction-methodology.md)，并按其“提问、选项与确认”规则执行。需要完整卡片结构时读取 [intent-card-template.md](references/intent-card-template.md)。

## 准入

接受：一句灵感、杂乱笔记、旧稿摘要、题材偏好，或需要重新对齐的项目简报。

阻塞并说明原因：没有任何故事兴趣或问题；没有能作方向决定的作者；要求直接开始写正文；要求模仿某位在世作者的可辨识表达。

若输入已包含人物、事件或设定，只提取其对“故事承诺、范围或约束”的影响，不在本 skill 展开设计。

## 会话状态

在每次回复开头维护下列状态，不必重复完整卡片：

| 状态 | 含义 | 行为 |
| --- | --- | --- |
| `exploring` | 正在获取某个决策组的信息 | 提问或给有限候选。 |
| `awaiting_confirmation` | 已形成候选结论，等待作者确认 | 只请求确认、修改或暂定，不继续推导下一组。 |
| `provisional` | 作者明确允许暂定 | 记录假设、影响范围和回看点。 |
| `confirmed` | 作者明确确认 | 冻结本组，转到下一组。 |
| `blocked` | 缺少作者裁决或存在不可兼容约束 | 停止推进，提出一个最小补充问题。 |

作者的普通补充、沉默或“都可以”不等同于确认。只有“确认/就按这个/选择 A/暂定 A”或同等明确意思才可改变状态。

`confirmed` 只表示作者确认它是本项目的创作决定，**不表示外部现实事实已经被核验**。C 组中的每条现实主张还须记录为“作者设定 / 已提供来源 / 待后续研究”；本 skill 不检索或验证事实。若一条待研究事实会改变故事承诺、范围或主体设计，必须将其列为交接 blocker，或由作者明确将其作为虚构设定采用。

首轮回复固定展示：当前状态、已知信息的三类标记、本轮决策组及其学习目标；随后只提出一至三个短问题。不要以长问卷开场。

## 提问、建议与选项规则

先确定当前决策组要消除的**一个歧义**，再选问题。不要把调研问题、访谈问题和确认问题混为一句。

| 目的 | 使用方式 | 示例 |
| --- | --- | --- |
| 探索 | 以中性开放问题开始；让作者用自己的语言描述。 | “你最希望读者长期带着哪一个问题离开这部小说？” |
| 澄清 | 引用作者原话，以 `什么/为什么/怎样/哪一种` 追问具体含义或例外。 | “你说‘不能太温情’，这里要避免的是结局、关系表达，还是整体语调？” |
| 收敛 | 仅在已理解作者意图后，给出 2–3 个互斥候选；每项都写明故事影响。 | “A 保留开放结局；B 给出事实结论但保留情感悬置；C 由作者另述。” |
| 确认 | 复述当前结论及其影响，使用明确的封闭式确认。 | “是否确认 B 作为当前的结局性质？这会让后续不再把‘事实谜底’当作终局目标。” |

必须遵守：

- 先开放、后澄清、再收敛、最后确认；不要开场就给“你是不是想写 X？”式引导题。
- 每个问题只问一件事，使用作者已使用的词；避免双重问题、术语和带价值判断的前提。
- 候选是帮助比较的临时脚手架，不是替作者选答案。始终保留“均不合适，请作者改述”的出口。
- 候选之间必须在一个控制点上真实不同；不得用同义改写制造虚假的三选一。
- 作者给出有价值的新线索时，允许偏离预设问题追问一次；完成后自然回到当前决策组。
- 只在复述中提出推断，并使用“我推断/是否准确”；不要把它混入问题前提。

## 访谈流程

按顺序处理四个决策组。每轮只处理当前组，提出一至三个短问题；若给候选，最多三个，并说明每个候选会改变的故事方向。为每个决策组先写一条内部“学习目标”，例如“确定读者承诺，而非决定主角职业”，以避免问题越界。

| 决策组 | 要获得的控制点 | 典型问题 | 检查点 |
| --- | --- | --- | --- |
| A. 核心体验 | 作者最想让读者进入的处境、冲突或变化；题材兴趣 | “读者应首先面对什么不能轻易解决的问题？” | 作者确认一条故事承诺，或授权暂定候选。 |
| B. 范围与非目标 | 目标形式、尺度、系列位置、题材承诺和明确不写的方向 | “这部作品最不应被写成哪一种故事？” | 作者确认范围与非目标。 |
| C. 硬约束与事实 | 已确定的人物/结局性质、现实事实、敏感性、版权或研究边界 | “哪些事即使为了戏剧性也绝不能改变？” | 每项有作者决定状态与事实来源状态；或作者明确确认“没有额外硬边界”。 |
| D. 开发授权 | 哪些留给后续设计，哪些必须由作者先决定；批准人 | “下一个 Agent 可以自由决定什么，必须回来问你什么？” | 作者确认交接范围与批准人。 |

每个决策组采用固定循环：

1. **设定目标**：说明本轮只要决定什么，以及本轮不决定什么。
2. **回显**：用三类状态归纳已知内容，并指出冲突或缺口。
3. **讨论**：先开放式提问或澄清，再在确有必要时给出有限候选；不跳到角色、事件链或场景。
4. **取舍**：用一句话说明候选对范围、承诺或约束的影响。
5. **确认**：明确询问“确认、修改，还是暂定？”
6. **记录**：得到确认后更新意图卡，并展示已冻结项、开放项及下一组。

## 问题设计规则

- 优先问能减少最大歧义的问题，而非一次收集所有偏好。
- 先问开放问题；作者难以回答时，再提供互斥候选。
- 不把“更深刻、更好看、更有市场”作为推销候选的理由；说明它会强化或牺牲什么承诺。
- 不要求作者现在决定只属于后续 skill 的人物动机、完整结局、场景顺序或语句风格。
- 发现两个硬约束互相排斥时，陈述冲突和后果，要求作者排序；不得自行折中。

## 访谈计划与完整记录

在第一条实质问题前，读取 harness `workflow.md`，向作者展示 I0 的四组、`plan.v1.json` 已核定的**精确**互动问题数、分钟数、完成条件和 blocker，并记录输入版本。内部容量估计可以补充展示，但不得替代作者可见的访谈计划；每轮刷新已用问题数、剩余预算和预计剩余时间；变更计划必须由作者明确确认并写入新的 `plan.vN.json`。

本 skill 只能在 harness I0 中运行：会话写入 `<project>/interview-sessions/I0/<session-id>/`，先创建 `plan.v1.json` 并向作者说明精确问题数和预计时长；每轮立即追加 `events.ndjson`，运行验证器并重建 `report.md`。结束时生成意图卡和 I0 `stage-completion.json`；不得以事后总结覆盖作者原话。设计产物才是下游的当前结论权威。

## 输出

在写入 I0 `stage-completion.json` 前，生成并校验 `control-projection.json`。使用稳定的 `INT-` ID，将意图卡中所有会约束后续开发的定义、目标、边界、禁止项和作者开放项逐项投影；`value` 必须无损表达原文，`hardness` 必须忠实区分作者锁定、自主环节职责、下游自由和作者未决。每项都绑定意图卡中的精确行范围及文本哈希。completion 使用 `contract_version: "2.0"`，并以 `{path, sha256}` 绑定该投影；专用 validator 未通过时不得交接。

投影中的每项控制必须只绑定意图卡中的一个完整 H2/H3 章节；`heading` 与字符串 `value` 分别原样对应章节标题和去除首尾空行后的正文。不得使用多段范围、局部摘录、结构化改写或哈希正确的近义转述。

完成后生成 `intent-card.md`，遵循模板并包含：

- 项目标识与当前版本；
- 作者原话或可靠摘要；
- 一条已确认/暂定的故事承诺；
- 范围、非目标、硬约束和事实边界；
- 决策登记表：内容、状态、依据、影响、责任人；
- 可以交给下一 skill 的授权，以及会阻塞它的开放项；
- 最后一次作者确认记录。

另附最小会话记录：每个已完成决策组各一行，记录本轮学习目标、作者原话、Agent 推断、问题、明确确认措辞和决定状态。它让后续 Agent 能判断一条结论来自作者、来自推断还是仍未决定。

在范围栏中写明已知的作品形态、尺度、系列位置与目标读者；作者尚未决定的项可标记为 `open`，但不得假装已确定。

仅当 A、B、D 均已确认或经作者明确授权暂定，C 组已给出可继承的硬边界声明（包括“没有额外硬边界”），且不存在会改变下一步主体设计的未裁决冲突时，输出 `confirmed` 或 `provisional`。明确授权的暂定项必须写明影响范围与回看点。否则输出 `blocked`，并指出应由作者回答的最小问题。

## 交接与禁止项

将意图卡和 I0 `stage-completion.json` 交给访谈 harness；只有 harness 验证 I0 为 `ready` 后，才可启动 I1 的 `novel-subject-designer`。后者只能继承卡中 `confirmed` 和明确允许的 `provisional` 项；交接栏必须明确列出“可继承的硬边界声明”和“会阻塞主体设计的开放项”。

不得输出角色档案、完整结局、事件链、场景表、对白、感官样稿或连续小说正文；这些均不是收拢意图的结果。
