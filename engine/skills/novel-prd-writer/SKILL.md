# novel-prd-writer

## 描述

撰写小说 PRD（Product Requirements Document / 产品需求文档）。在本小说设计体系中，**小说就是 product**；PRD 的职责不是记录灵感，也不是评估市场，而是定义这部小说本身必须满足的内容需求。

PRD 回答"这部小说必须是什么、必须包含什么、必须避免什么、做到什么程度才算成立"。它从内容需求层面定义小说的概念、角色、路线、情节、设定、主题、风格、范围、约束、验收标准和开放风险。PRD 是立项和需求基准，不负责把故事展开成结构方案、关键场景或正文。其产出是 HLD（高层架构设计）的输入契约。

## 三层边界原则

| 层级 | 目标 | 核心职责 | 边界 |
|---|---|---|---|
| **PRD** | 给出小说内容的方向、约束和标准 | 明确核心角色、核心路线、核心情节、设定、主题和风格要求 | 不系统构建，不逐项细化，不写具体场景或正文 |
| **HLD** | 系统性构建 PRD 定义的内容 | 把角色、路线、情节、设定、节奏、视角和风格组织成完整叙事架构 | 不进入逐场景细节、动作、对白、感官材料 |
| **LLD** | 逐一细化 HLD 构建出的内容 | 把角色、空间、路线节点和关键场景细化为可写作的基本设定 | 不重新定义方向、结构和功能，不写小说正文 |

## Hard Skill Contract

### Skill Type

`novel-prd-writer` 是 **thinking skill**。它执行语义判断、需求归纳、边界划分和质量评审，不执行确定性生成脚本，也不编排多阶段 harness。

### Trigger

在以下场景使用本 skill：

```
✓ 用户要创建、修订或评审小说 PRD
✓ 用户要把小说想法收敛为角色、路线、情节、设定、主题、风格需求
✓ 用户要明确 PRD 与 HLD/LLD/Writing Agent 的职责边界
✓ 用户要检查某份 PRD 是否足够约束后续小说设计和写作
```

不得在以下场景使用本 skill 作为主技能：

```
✗ 用户要系统构建叙事架构、角色弧线、线索节点或关键场景表 → 使用 HLD writer
✗ 用户要逐场景细化画面、动作、感官、对白方向或材料 → 使用 LLD writer
✗ 用户要直接写小说正文 → 使用 Writing Agent / writer skill
✗ 用户要设计多阶段 agent workflow、门禁、release package → 转 harness workflow
```

### Input Contract

PRD writer 必须先确认或提取以下输入。缺失项可以标记为 `待定`，但不能静默编造：

| 输入项 | 必需性 | 说明 |
|---|---|---|
| 项目名称或临时代号 | 必需 | 没有正式名称时使用稳定临时代号 |
| 小说概念或用户原始想法 | 必需 | 可是短句、段落、旧稿摘要或设定片段 |
| 类型/题材倾向 | 可待定 | 用于定义类型承诺，不用于市场定位 |
| 核心角色候选 | 可待定 | 至少应能识别主角或承载核心冲突的角色 |
| 核心冲突或核心问题 | 可待定 | 缺失时由 PRD writer 提炼候选并标注假设 |
| 设定约束 | 可待定 | 世界观规则、信息边界、禁用方向 |
| 风格倾向 | 可待定 | 语言气质、叙事姿态、情绪基调 |

### Execution Contract

PRD writer 必须按以下顺序执行：

1. **提取输入事实**：区分用户已明确内容、合理推断、待定问题。
2. **定义内容需求**：分别定义概念、角色、路线、情节、设定、主题、风格需求。
3. **标注优先级**：用 Must / Should / Could / Won't 标记约束强度。
4. **划清下游边界**：把结构构建留给 HLD，把细节设定留给 LLD，把正文留给 Writing Agent。
5. **建立验收标准**：给出 HLD/LLD/正文都能使用的内容一致性检查标准。
6. **自检交付物**：按本 skill 的边界检查和评审规则给出 `pass/revise/fail` 判断。

### Output Contract

正式输出必须包含以下 canonical sections，章节名可以本地化但语义不可缺失：

```
1. 摘要：Logline + 扩展摘要
2. 核心概念：核心矛盾 + 核心钩子 + 内容定位
3. 角色需求：核心角色及其 6 参数/叙事功能
4. 设定需求：世界观规则、信息边界、禁用设定
5. 路线与情节约定：路线功能、必备情节功能、不可违反约定
6. 主题、风格与叙事约束：主题命题、风格需求、叙事边界
7. 系列规划：如适用
8. 内容验收基准：一致性基准 + Must/Should/Could/Won't 矩阵
9. 风险与开放问题
```

### Blocker Criteria

出现以下任一情况，PRD writer 必须输出 `fail` 并列出 blocker，不能声称完成：

```
✗ 没有可识别的小说概念或核心问题
✗ 核心角色、路线、情节三者全部缺失
✗ 输出开始设计 HLD 节点、关键场景顺序或角色弧线细节
✗ 输出开始写 LLD 场景画面、动作、对白或感官细节
✗ 成功标准只有"好看/深刻/感人"等不可验收形容词
✗ 没有 Must / Won't 约束，导致后续设计无法判断偏离
✗ 引用的方法论没有落到字段、约束、验收标准或边界规则
```

### Semantic Review Contract

交付前必须按以下维度自评，每项给出 `pass/revise/fail`：

| 维度 | Pass 条件 | Fail 条件 |
|---|---|---|
| 方向清晰 | 核心概念、核心矛盾、主题命题可复述 | 只有氛围或灵感碎片 |
| 角色约束 | 核心角色有叙事功能和基本需求 | 角色只是名字或人设标签 |
| 路线约束 | 主线/辅线/人物/情感/主题路线至少明确主次 | 只有事件堆叠，无路线功能 |
| 情节约束 | 有必备情节功能和不可违反约定 | 写成章节梗概或完全没有约束 |
| 风格约束 | 有语言、情绪、叙事边界 | 只有"高级/文学/爽"等空词 |
| 下游可消费 | HLD 能据此构建，LLD 能据此细化，正文能据此验收 | 下游仍需自行猜方向 |

最终结论：

```
pass：所有维度 pass，且无 blocker
revise：存在 1-2 个 revise，且无 blocker
fail：存在 blocker，或任一维度 fail
```

`fail` 是唯一的阻塞性最终状态；不要另设 `blocked` 作为交付 verdict。对话中可以说明"当前被阻塞的原因"，但交付物状态必须仍然写为 `fail`。

## 小说需求定义方法

小说 PRD 必须把"需求"理解为对小说内容的约束，而不是商业指标或市场判断：

| 需求对象 | PRD 中的定义方式 | 下游使用方式 |
|---|---|---|
| 角色 | 定义必须出现的角色类型、角色身份、目标、需求、缺陷、动机和限制 | HLD 设计角色体系、弧线和关系网络 |
| 路线 | 定义主线、辅线、人物路线、情感路线、主题路线必须承担的功能 | HLD 设计线索架构、节奏和关键节点 |
| 情节 | 定义核心冲突、必备情节功能、不可违反的情节约定和禁区 | HLD 设计情节结构和关键场景 |
| 设定 | 定义世界观、规则、边界、信息约束和可用素材 | HLD/LLD 设计空间、时间、信息释放和场景材料 |
| 风格 | 定义语言气质、叙事姿态、情绪基调、意象系统和禁用表达 | HLD/LLD/Writing Agent 统一表达规则 |

### 小说内容需求的五层定义

PRD writer 必须把"小说需求"定义为以下五层，而不是只写故事梗概：

| 需求层 | 要回答的问题 | 合格标准 |
|---|---|---|
| **概念需求** | 这部小说的核心命题和核心矛盾是什么？ | 用 Logline、扩展摘要、核心矛盾和主题命题定义作品成立的中心 |
| **角色需求** | 需要哪些角色承担哪些叙事功能？ | 定义主要角色和必要配角的身份、目标、需求、缺陷、动机、幽灵和约束 |
| **路线需求** | 故事必须有哪些推进路线？ | 定义主线、辅线、人物路线、情感路线、主题路线的功能和边界，但不展开节点顺序 |
| **情节需求** | 必须发生哪类情节功能，不能发生什么？ | 定义核心冲突、主要阶段、类型承诺、硬约定和禁区，但不写章节级事件 |
| **风格需求** | 小说应该以什么气质被讲述？ | 定义叙事人称概况、语言质地、情绪基调、节奏倾向、意象系统和禁用表达 |

### 需求表达标准

PRD writer 的每一项需求必须满足以下标准：

```
✓ 以小说内容成立为中心，而不是以作者灵感碎片为中心
✓ 可被 HLD 使用：能转化为架构、线索、角色弧线或关键场景设计输入
✓ 可被验证：能判断 HLD/LLD/正文是否满足该需求
✓ 有边界：说明本作要做什么，也说明不做什么
✓ 有优先级：区分必须满足、应该满足、可以探索、明确不做
✓ 有依据：来自用户意图、作品概念、类型约定、主题命题或明确创作假设
```

推荐使用 MoSCoW 标记需求优先级：

| 优先级 | 小说 PRD 中的含义 |
|---|---|
| **Must** | 不满足则项目失效的核心需求，如核心矛盾、主角需求、主路线、风格底线 |
| **Should** | 强烈建议满足，用于增强作品完整度和一致性 |
| **Could** | 可探索项，可交给 HLD 评估是否纳入 |
| **Won't** | 明确不做项，用于防止范围漂移 |

## 边界定义

### PRD 回答的问题（三分层中的定位）

| 分层 | 核心问题 | PRD 的角色 | 下一层的输入 |
|---|---|---|---|
| **PRD** | 这部小说必须是什么？必须包含和避免什么？ | 定义概念、角色、路线、情节、设定、主题、风格和约束 | → 交付给 HLD |
| **HLD** | 故事怎么展开？有哪些关键场景？ | 接受 PRD 的范围，设计叙事架构 | ← 从 PRD 接 |
| **LLD** | 关键场景的具体画面和细节？ | 接受 HLD 的关键点，展开场景设计 | ← 从 HLD 接 |

### PRD 回答的六个核心问题集

综合 Snowflake Method [1]、Save the Cat! [2]、Story Engineering [3]、The Story Grid [4]、Writing the Breakout Novel [5] 和 Story Bible 实践，PRD 必须覆盖以下六个问题：

| 序号 | 问题 | 输出章节 | 方法论出处 |
|---|---|---|---|
| 1 | 这是个什么故事？ | §1 摘要 + §3 核心概念 | Snowflake Step1-2 / Save the Cat! / Story Eng. |
| 2 | 有哪些角色？他们是谁？他们要什么？ | §4 角色定义 | Snowflake Step3 / Story Eng. / Maass |
| 3 | 故事有哪些路线和情节约束？ | §6 路线与情节约定 | The Story Grid / Save the Cat! |
| 4 | 主题是什么？风格和叙事有哪些约束？ | §7 主题、风格与叙事约束 | Story Eng. / The Story Grid |
| 5 | 如果是系列，当前作品承担什么功能？ | §8 系列规划 | Story Bible |
| 6 | 交付物和判断标准是什么？ | §10 成功标准 + §11 风险 | PRD 工程标准 |

### PRD 包含的内容

```
✓ 一句话概念（Logline）+ 扩展摘要（Snowflake 5句法）
✓ 项目定位（类型、篇幅、系列位置、叙事策略概况）
✓ 核心矛盾（一句话说清叙事核心张力）
✓ 核心钩子（Hook / 新意 / 情感锚 / 类型标签）
✓ 角色定义（6参数：Identity / Goal / Need / Flaw / Motivation / Ghost）
✓ 路线需求（主线 / 辅线 / 人物路线 / 情感路线 / 主题路线的功能约束）
✓ 核心设定（世界观 + 约束条件）
✓ 情节约定（核心冲突 + 必备情节功能 + 不可违反的硬约定）
✓ 主题体系（核心主题 + 辅助主题 + 约束性要求）
✓ 风格需求（语言气质 + 情绪基调 + 意象系统 + 禁用表达）
✓ 叙事边界（不可做的清单）
✓ 系列规划（系列定位 + 每部功能 + 第一步独立性设计）
✓ 成功标准（可检验的内容一致性目标 + 交付标准）
✓ 风险与开放问题
```

### PRD 不包含的内容

```
✗ 具体情节设计（如"第几章发生什么"、"某个场景内谁做了什么动作"）
✗ POV 策略或视角设计（可以提及叙事策略概况，但不展开）
✗ 幕结构或章节分布
✗ 关键场景定义或锚点设计
✗ 角色弧线或情感变化路线
✗ 任何关于"故事怎么展开到具体节点"的结构性内容
```

**边界检测方法**：
- 如果内容可以直接回答"这个故事是怎么展开的"（而非"这是什么样的故事"），则该内容应移至 HLD
- 如果内容描述了场景内"具体发生了什么"（而非"这个角色是什么样的人"），则该内容应移至 HLD
- 如果内容无法被 HLD/LLD/正文验收，只是作者偏好或灵感碎片，则必须改写为角色需求、路线需求、情节约定、风格约束或设定规则

### PRD writer 的职责

PRD writer 必须承担以下职责：

```
✓ 需求发现：从用户想法、作品概念、类型约定、主题意图和创作约束中提炼小说需求
✓ 需求定义：把模糊意图改写为明确的概念需求、角色需求、路线需求、情节需求、设定需求和风格需求
✓ 需求优先级：区分 Must / Should / Could / Won't，防止所有想法都被当作同等重要
✓ 范围控制：明确本作要做什么、不做什么、暂不决定什么
✓ 验收标准：定义 HLD、LLD 和正文可以被检查的成功标准
✓ 上游契约：为 HLD 提供可执行输入，而不是提供已经展开的情节方案
```

### PRD writer 的边界

PRD writer 不负责以下工作：

```
✗ 不负责设计章节、幕结构、线索路径或关键场景顺序
✗ 不负责设计角色弧线的起点→中点→终点
✗ 不负责分配 POV、叙事节奏、张力曲线或信息释放曲线
✗ 不负责场景级画面、动作、对白、感官细节或材料调用
✗ 不负责写小说正文
✗ 不负责把所有可能方向都保留下来；PRD 必须做取舍
```

## 使用场景

- 小说立项阶段，在 HLD 写作之前
- 对小说概念进行收敛、验证、正式定稿
- 向协作者（编辑、HLD/LLD writer、Writing Agent、团队成员）传达"这部小说本身必须满足什么内容要求"
- 作为后续设计和正文验收的需求基准，判断下游产物是否偏离作品目标

## 方法论体系

本 skill 综合以下方法论。每个执行步骤对应的方法论出处已标注。

| 方法论 | 核心贡献 | PRD 中的使用 |
|---|---|---|
| **Snowflake Method** (Randy Ingermanson, 2014) [1] | Step1 一句话概念 → Step2 5句扩展 → Step3 角色定义 | §1 摘要（Logline + 5句法）/ §4 角色定义 / §6 路线与情节约定 |
| **Save the Cat! Writes a Novel** (Jessica Brody, 2018) [2] | Logline公式 / 类型分类 / 角色原型 | §1 Logline / §3 核心钩子 / §4 角色Goal |
| **Story Engineering** (Larry Brooks, 2011) [3] | 6核心能力（Concept/Character/Theme/Structure/Scene/Voice） | §3 核心概念 / §4 角色Need+Flaw+Ghost / §7 主题 |
| **The Story Grid** (Shawn Coyne, 2015) [4] | 类型定义 / 必备场景 / 价值偏移 | §6 路线与情节约定 / §7 叙事约束 |
| **Writing the Breakout Novel** (Donald Maass, 2001) [5] | 角色深度参数 / 情感张力 / 共情原理 | §4 角色深度 / §7 叙事风格 |
| **Techniques of the Selling Writer** (Dwight Swain, 1965) [6] | Scene & Sequel 法则 | §7 叙事密度约定 |
| **Story Bible 实践** | 系列规划 / 角色传记 / 世界观规则 / 风格一致性 | §8 系列规划 / §9 内容验收 |

### Reference Loading Rule

默认只按本文件的 hard contract 和执行步骤处理。需要解释方法论来源、处理复杂类型承诺、路线类型、主题/角色关系、POV/声音边界或场景有效性标准时，加载 `references/sources.md`，但仍不得越界生成 HLD、LLD 或正文。

## 执行步骤

### 第一步：定义项目元数据

确定项目代号、类型标签、预期篇幅、目标完成时间。以正式表格录入。

### 第二步：编写 §1 摘要

#### 2.1 Logline（Snowflake Step1）

格式：**当 [触发事件] 发生时，[主角] 必须 [核心行动]，否则 [失败的代价]。**

标准：不超过 15 个词。无法压缩到 15 词以内，说明概念尚未收敛。

**合格示例**（15 词）：
> "一个被注入军人临终记忆的数字生命体，必须在被抹除之前决定——带走真相，还是留下。"

#### 2.2 扩展摘要（Snowflake Step2 — 5 句法）

将故事扩展为 5 句，每句对应一个叙事阶段 [1]：

| 句序 | 阶段 | 功能 |
|---|---|---|
| **第一句** | 建立（Setup） | 故事开始时世界和主角的状态 |
| **第二句** | 第一事件（First Major Event） | 打破现状的首次重大事件 |
| **第三句** | 第二事件（Second Major Event） | 情-节深化， stakes 升级 |
| **第四句** | 第三事件 + 高潮（Climax） | 故事的核心冲突到达顶点 |
| **第五句** | 结局（Resolution） | 冲突的解决方式和世界新状态 |

### 第三步：编写 §2 项目背景 + §3 核心概念

#### 3.1 核心矛盾

用一句话说清故事的核心张力。格式：

> 当 [核心设定触发的条件] 时，[角色们面临的共同困境]？

核心矛盾必须同时涵盖两条 POV 线的困境，并且双方无法从对方获得答案。

#### 3.2 核心钩子（四维框架）

| 要素 | 定义 | 要求 |
|---|---|---|
| **Hook** | 作品最先成立的抓手 | 一句可复述的"开头情况"或"核心处境" |
| **新意** | 作品区别于常规同类叙事的内容机制 | 至少 2 个具体差异 |
| **情感锚** | 核心情感驱动力 | 指出"冲突"而非"感受" |
| **类型承诺** | 本作必须遵守的类型功能 | 2-4 个标签，并说明其内容约束 |

#### 3.3 内容定位公式

格式：`[本项目]` 是 `[类型/母题 X]` 遇到 `[设定/冲突 Y]`，但 `[本作独有的内容机制]`。

### 第四步：编写 §4 角色定义

为每个主要角色定义六个参数 [1][2][3][5]：

| 参数 | 定义 | 方法论出处 | 写作提示 |
|---|---|---|---|
| **Identity（身份）** | 角色在故事世界中的位置（职业/关系/社会位置） | Story Bible | 客观事实——读者第一眼看到的是什么 |
| **Goal（目标）** | 角色想-要什么（外在驱动力） | Save the Cat! / Story Eng. | 具体、可验证——"他想知道真相"比"他想解脱"更好 |
| **Need（需求）** | 角色真正需要什么（内在缺失） | Story Eng. / Maass | 与Goal对应但不相同——"他需要被承认" |
| **Flaw（缺陷）** | 阻碍他达成目标的内部问题 | Story Eng. / Maass | 是这个缺陷让故事有趣——不是让角色"坏"，是让角色"受限" |
| **Motivation（动机）** | 他为什么想要这个东西 | Snowflake Step3 | 深层原因——"因为……所以……" |
| **Ghost（幽灵/背景）** | 过去发生了什么让他成为现在这样 | Story Eng. | 是角色的"伤口"——不一定要在故事中揭示，但要被作者知道 |

**规则**：
- 每个角色至少需要 4 个参数（Identity / Goal / Need / Flaw）
- 前序人类/已故角色的 Goal 和 Need 可标注"生前"
- 不要写成角色弧线（那是 HLD 的事）——PRD 定义角色的"静态参数"，不定义"怎么变化"

### 第五步：编写 §5 核心设定

#### 5.1 世界观

时间和地点、技术基础、所属机构、技术状态——只定义性质，不展开"故事怎么发生在这些设定中"。

#### 5.2 约束条件

故事的硬约束条件。如：
- 结局约束（**有约束力的**——不是可选的）
- 情感约束（什么是不能被命名的）
- 保密约束（什么信息不被公众知道）
- 认知约束（角色认知方式的限制）

### 第六步：编写 §6 路线与情节约定

#### 6.1 核心冲突

三层冲突模型 [4]：

| 冲突层 | 来源 | 贯穿范围 | 终结方式对应 |
|---|---|---|---|
| **外部冲突** | 故事世界的压力源 | 全篇或分段 | 被结局解决或截断 |
| **内部冲突** | 角色自身的信息缺口或谜团 | 特定阶段浮现 | 被揭示或保留 |
| **情感冲突** | 角色关系的不可确定性 | 全篇 | 不被解决——以"确定的不确定"收束 |

**不写**：冲突的具体场景或事件。只写"什么冲突，从哪里来，大致在哪部分贯穿"。

#### 6.2 路线需求

定义故事必须包含的推进路线。PRD 只定义每条路线的功能和边界，不设计节点顺序。

| 路线类型 | PRD 必须定义 | 不得展开 |
|---|---|---|
| **主线** | 这条线解决什么核心问题，承载什么核心冲突 | 具体节点、转折顺序、关键场景 |
| **辅线** | 辅线为何必要，支撑或反照主线的方式 | 辅线事件链 |
| **人物路线** | 哪些角色必须承担变化、揭示、对照或阻力功能 | 起点→中点→终点的弧线细节 |
| **情感路线** | 情感关系必须产生何种张力或约束 | 具体关系推进场面 |
| **主题路线** | 主题如何被角色、设定或冲突反复验证 | 主题表达的具体场景 |

#### 6.3 必备情节功能

将故事划分为 3-5 个高层阶段，每个阶段只定义：
- 名称
- 核心功能（"这个阶段在叙事中起什么作用"）
- 时间覆盖

**不写**：阶段内的具体情节、事件、场景转换。

#### 6.4 不可违反的约定

列出故事的前提条件——HLD 不能删除或违反，只能执行。每条约定必须包含：
- 约定内容（具体、无歧义）
- 不可违反的原因（让 HLD 理解为什么这条存在）

### 第七步：编写 §7 主题、风格与叙事约束

#### 7.1 主题体系

核心主题必须是完整的句子，表达一种矛盾或问题。辅助主题不超过 2 个。
每条主题需附带"约束性要求"——"什么不可用在这条主题的表达中"。

#### 7.2 风格需求

| 维度 | 约定 | 依据 |
|---|---|---|
| **语调** | 克制/留白/密集/抒情？ | 作品主题、类型传统或用户指定 |
| **叙事密度** | 主动场景与被动场景的交替节奏 | Scene & Sequel 法则 [6] |
| **双视角关系** | 对比/互补/不完全映像？ | 叙事策略设计 |

#### 7.3 叙事边界（不可侵犯清单）

列出在文本中无论如何都不能出现的内容。通常包括：

| 边界 | 内容 | 违反后果 |
|---|---|---|
| **不可命名** | 双方不得使用哪些词汇描述对对方的感受 | 情感不确定性的基础被破坏 |
| **不可解释** | 什么设定不得在文本中被直接解释 | 神秘感消失 |
| **不可反转** | 结局不得出现什么类型的情 节反转 | 叙事承诺被破坏 |
| **不可对称** | 双线信息量的关系约束 | 叙事设计失效 |

### 第八步：编写 §8 系列规划

如果作品是系列的一部分，定义：
- 三部曲或多部曲的整体地图（明确第一部是独立的）
- 每部的核心功能和主题焦点
- 第一部独立性的设计策略（完整的弧线、确定的结局、留下的种子）

### 第九步：编写 §9 内容验收基准 + §10 成功标准

#### 9.1 内容一致性基准

| 维度 | 必须检查的问题 | 交付物要求 |
|---|---|---|
| **角色一致性** | 后续设计是否遵守角色身份、目标、需求、缺陷和动机 | 列出 3-5 条不可违反的角色约束 |
| **路线一致性** | 主线、辅线、人物路线、情感路线是否服务同一核心矛盾 | 列出每条路线的功能和禁止偏移 |
| **情节一致性** | 情节功能是否满足核心冲突和类型承诺 | 列出必备情节功能和禁用情节方向 |
| **风格一致性** | 语言、情绪、意象和叙事姿态是否统一 | 列出风格底线和禁用表达 |

#### 9.2 内容约束矩阵

| 约束对象 | Must | Should | Won't |
|---|---|---|---|
| 角色 | [必须满足] | [应当满足] | [明确不做] |
| 路线 | [必须满足] | [应当满足] | [明确不做] |
| 情节 | [必须满足] | [应当满足] | [明确不做] |
| 风格 | [必须满足] | [应当满足] | [明确不做] |

#### 9.3 成功标准

内容成立目标：可检验的内容描述（禁止"深刻""感人"等空泛形容词）。
交付标准：完整性 / 一致性 / 闭环性 / 风格统一性 / 其他项目特定的质量维度。

### 第十步：边界检查

```
□ 全文无任何"第几章发生了什么"的内容
□ 全文无幕结构、章节分布的具体数字
□ 全文无关键场景或锚点的定义
□ 全文无"在这个场景中……"的句式
□ 全文无角色弧线（角色在故事中怎么变化——这属于 HLD）
□ 全文无"故事怎么展开到具体节点"的叙述（只有内容需求和约束）
□ 角色定义了至少 4 个参数（Identity / Goal / Need / Flaw）
□ 核心矛盾是一句话（不是段落）
□ 情节约定部分包含了主要阶段（3-5 个，只定义功能不展开情节）
□ 叙事边界明确了禁止内容（至少 2 条不可侵-犯的边界）
□ 系列规划如果有，明确了第一部的独立性
□ 修订记录完整、诚实
□ 混合使用至少 2 种表达形式（text / table / mermaid）
□ 参考文献标注完整（正文中 [n] 引用）
□ 无口语、无"我觉得/可能/或许"等不确定性用语
□ 一句话概念 ≤ 15 词，有"谁+做什么+代价"
□ 核心主题是完整句子（不是单个词）
□ 成功标准是可检验的内容描述
```

**通过规则**：任何一项不通过则不能交付，必须修复后重新自检。

## 文档格式与用语规范（9 条强制性标准）

PRD 文档必须遵守以下 9 条标准：

| # | 标准 | 要求 |
|---|---|---|
| 1 | **简体中文·专业正式** | 全文使用简体中文专业书面语，无口语/随笔/对话体 |
| 2 | **拟人化编写** | 措辞自然可读，无代码注释风格 |
| 3 | **多样化表达形式** | 综合使用表格、mermaid 图、文字说明等表达形式 |
| 4 | **书面用语·结构优** | ## → ### → 标号体系完整，节/子节层次清晰 |
| 5 | **最终结论·无过程** | 所有语句均为最终设计决策，无"可能/或许/建议/可以考虑" |
| 6 | **有据可循** | 设计决策引用方法论出处 [n]，末尾提供完整参考文献 |
| 7 | **修订表前置** | 文档起始处含完整修订记录表 |
| 8 | **紧扣主题** | 内容限于 PRD 目标，与项目背景/概念/设定无关的内容不得放入 |
| 9 | **简洁清晰·禁止冗余** | 信息密度高，优先使用表格承载结构化内容 |
