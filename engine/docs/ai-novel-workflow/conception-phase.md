## 1. 先定义：构思阶段实现什么

构思阶段不实现“把小说想得尽可能多、尽可能细”，更不实现小说正文。

它实现的是一件更具体的事：**把作者对一部小说的核心意图，转化为一份能约束后续创作选择的小说设计说明。**

这份说明交给一个不了解前序讨论的开发者（人或 AI）后，对方应当不必猜测下列问题：

1. 这部小说最终要让读者经历什么样的核心冲突与变化？
2. 谁是故事的主体；他/她/它想要什么，又被什么阻挡？
3. 什么世界规则、环境压力和事实边界决定了事件只能怎样发生？
4. 主体故事线从何处开始，经由哪些必然的变化，抵达怎样的结局？
5. 哪些信息必须在何种阶段被读者知道，哪些不能被提前解释？
6. 叙述应该保持怎样的视角、距离、语言气质与禁区？
7. 哪些内容已被作者决定、哪些可由开发解决、哪些必须先回到作者？

因此，构思阶段的终点不是“完成一个大纲”，而是形成一个**足以防止开发偏航的创作控制面**。它给开发提供方向、边界和判断依据，同时保留文字创作本身应有的发现空间。

## 2. 构思阶段的目标、边界与职责

### 2.1 目标

| 目标 | 成功表现 |
| --- | --- |
| 固定方向 | 开发者能用一句话复述故事承诺、核心矛盾和结局性质，不会把小说写成另一种类型或主题。 |
| 固定主体 | 主角、关键关系和主要对抗力量都有可执行的叙事功能，不只是人物小传。 |
| 固定因果 | 主体故事线中的关键事件互为原因和结果，终局由角色的选择抵达，而非由巧合或作者解释抵达。 |
| 固定边界 | 世界规则、事实、时间范围、叙述边界、禁用项和作者的价值选择被明确记录。 |
| 支持开发 | 开发者能据此拆出场景、起草和修订，并在遇到分歧时知道该遵循什么、该向谁提问。 |

### 2.2 不属于构思阶段的工作

| 不做什么 | 原因 |
| --- | --- |
| 不写连续正文、示范章节或可直接发布的对白 | 这会把“如何表达”误当成“写什么”的决定，并过早锁死开发空间。 |
| 不为每个场景预先写动作、感官、段落和句子 | 这些是开发阶段根据设计实现的文字工作。 |
| 不以百科式设定、角色履历或术语数量衡量完成度 | 只有会改变人物选择、事件因果或叙述理解的设定才是构思控制点。 |
| 不用模板代替决策 | 缺少结局、核心选择或主题时，填再多栏目也不能进入开发。 |
| 不替作者裁决价值、情感结论、重大结局或敏感议题 | AI 可以提出有限候选和影响说明，作者拥有最终决定权。 |

### 2.3 职责边界

| 参与者 | 在构思阶段的职责 | 不应承担的职责 |
| --- | --- | --- |
| 作者 | 给出初始意图、硬约束和价值选择；裁决重大候选；批准设计说明。 | 不必自行整理成技术化模板。 |
| 构思者（AI 或人） | 提炼问题，建立故事、角色、世界与结构之间的约束；指出冲突与未知项。 | 不能把合理推断伪装成作者决定。 |
| 开发者（下一阶段） | 读取设计说明，提出无法实现或存在歧义的反馈。 | 不得静默改写核心设计。 |
| 审阅者 | 判断设计是否传达了足够的控制点与开发空间。 | 不以个人偏好替代作者的方向。 |

## 3. 构思阶段唯一交付物：小说设计说明

构思交付物应被视为一个整体，本文称为**小说设计说明（Novel Design Brief，NDB）**。它可以拆分为多个可读文档，但对开发者而言必须是一套完整、版本明确、相互不冲突的说明。

NDB 不是“小说圣经”的穷尽版本，也不是给模型喂入的资料仓库；它只记录**会影响后续创作决策的控制点**。

### 3.1 NDB 的三层内容

```text
方向层：为什么写、写成什么、绝不写成什么
结构层：谁推动什么变化、世界怎样施压、事件怎样走向结局
交接层：开发必须遵守什么、可以自由创造什么、遇到什么必须回问
```

### 3.2 NDB 必须包含的九项内容

| # | 控制点 | 必须定义的内容 | 它为开发解决什么问题 |
| ---: | --- | --- | --- |
| 1 | **故事承诺** | 一句话 premise；核心矛盾；主题命题；类型/情感承诺；范围与非目标。 | 避免开发把同一设定写成不同的故事。 |
| 2 | **结局与闭环** | 结局必须发生的状态变化；主角最终选择；核心问题被回答、保留或反转的方式；系列接口（如有）。 | 让中段选择朝同一终局累积，而非只向前续写。 |
| 3 | **关键角色与关系** | 每位关键角色的叙事身份、目标、内在需要或盲点、主要阻力、关键关系、变化/不变的方向。 | 让人物行为可判断，避免人设标签和工具人推动剧情。 |
| 4 | **世界、环境与事实边界** | 时空与社会环境；决定行动代价的规则；关键空间的叙事功能；现实事实来源与虚构边界。 | 让设定成为压力和选择条件，而不是装饰。 |
| 5 | **主体故事线** | 触发事件；阶段性目标；关键转折；危机；高潮选择；结局。每个节点说明“此前发生了什么、角色做了什么、因此什么改变”。 | 提供全书的因果骨架，避免事件清单或偶然推进。 |
| 6 | **支线与信息设计** | 支线如何支持、反照或干扰主线；秘密、谜团、伏笔和信息释放的阶段规则。 | 防止支线抢占主题、信息过早泄露或结尾没有兑现。 |
| 7 | **叙述契约** | POV、时间组织、叙述距离、语言气质、情感表达原则、可重复意象、明确禁区。 | 让多次开发、多人协作或多模型生成仍属于同一部小说。 |
| 8 | **开发地图** | 不是正文分镜，而是场景/章节级的功能序列：每个单元的目的、主要 POV、冲突/选择、状态变化、必须交代的信息和依赖。 | 让开发者能从“写什么”进入“如何写这一场”。 |
| 9 | **决策与风险清单** | 已决定项、允许开发补足项、待作者裁决项、不可违反项、已知风险及其影响范围。 | 给不确定性一个合法位置，避免 AI 擅自补设定。 |

### 3.3 交付物应当长什么样

NDB 可以是一份结构化说明，也可以是一组互相链接的文档；篇幅不是标准。每一项控制点都应满足“**定义—理由—开发含义**”三段式：

| 写法 | 不合格 | 合格 |
| --- | --- | --- |
| 角色 | “她冷静、聪明、有秘密。” | “她必须维持职业规程以保住身份；当她选择保护目标时，规程与关系必然冲突。开发不得把她写成仅凭同情行动。” |
| 世界规则 | “技术先进但危险。” | “转移只能复制可提取的信息，不能证明灵魂连续；因此角色只能争论身份，不能用技术给出终极答案。” |
| 事件节点 | “中段发现真相。” | “主角的调查使其发现盟友隐瞒了关键事实；此后继续合作将构成主动承担，而不是不知情受骗。” |
| 风格 | “高级、克制、有电影感。” | “情感主要经由选择、物件和对话缺口呈现；叙述者不得直接替人物命名核心情感。” |

## 4. 构思阶段的控制点：固定什么，保留什么

构思不是把所有东西冻结。它的质量取决于是否冻结了**错误成本最高、最容易令开发偏航**的决定。

| 必须在构思中固定 | 可由开发补足 | 必须记录为待定，不能暗中补写 |
| --- | --- | --- |
| 故事承诺、主题边界、结局性质与主体冲突 | 具体场景的动作路径、段落节奏、措辞、感官细节 | 作者尚未选定的结局、核心伦理立场、关系结论、重大身份真相 |
| 关键角色的目标、阻力、关键选择与关系方向 | 次要角色的局部习惯、局部对白表达 | 会改变主线因果的规则、关键角色动机、事件先后 |
| 世界的限制、代价和事实边界 | 不影响限制的局部物件、命名、背景纹理 | 需要研究支持却尚未核实的现实事实 |
| 主线阶段、转折功能、高潮选择与闭环 | 单场的具体进入/退出方式、章节切分 | 支线是否保留、POV 是否切换、信息何时揭示等结构决定 |
| 叙述契约与禁区 | 在契约内的意象变化、句法和局部语调 | 对特定在世作者的可辨识模仿要求 |

这张表是构思对开发最重要的授权书：开发者可以大胆地创造第二列内容，但必须遵守第一列，并把第三列退回作者。

## 5. 构思 SOP：以设计决策为中心，而非以文档生产为中心

| 步骤 | 要解决的创作问题 | 产出 | 完成判断 |
| --- | --- | --- | --- |
| 1. 收拢意图 | 作者真正想写的冲突、感受和边界是什么？ | 故事承诺、非目标、待定项。 | 能区分作者已决定、可推断与不可推断的内容。 |
| 2. 确立主体 | 谁的选择让故事发生，谁或什么持续施压？ | 关键角色/关系和世界压力的定义。 | 关键转折都能指向某个角色选择或规则后果。 |
| 3. 设计核心角色 | 这些主体为何这样理解压力、如何选择、何时改变？ | 动机、形成因果、压力行为、关系动力、变化边界。 | 给定关键压力，开发者能预测角色的默认选择、例外和代价。 |
| 4. 建立因果骨架 | 故事如何从触发走到只能如此收束的结局？ | 主体故事线、关键转折、支线功能。 | 删除任一关键节点都会造成可指出的因果或主题缺口。 |
| 5. 规定叙述边界 | 开发时如何避免写成另一部作品？ | POV、信息、时间、风格与禁区契约。 | 开发者可据此判断一个场景能否出现、能透露什么。 |
| 6. 形成开发地图 | 开发从哪里开始，每一单元应完成什么？ | 场景/章节功能序列及依赖。 | 每个单元都服务主线、角色、信息或主题中的至少一项。 |
| 7. 审阅并交接 | 这份说明是否真正降低开发者的猜测空间？ | NDB、风险清单、作者批准记录。 | 通过第 6 节的评价，且作者确认版本。 |

步骤可以反复往返。比如角色的选择缺少可信理由时，应回到“设计核心角色”；选择本身或其结局作用不成立时，再回到“确立主体”或“建立因果骨架”，而不是用更多设定填补漏洞。

### 5.1 六个访谈 skill 与审计交接责任

默认调用图、每门的可消费输入、状态门禁和结构性问题的唯一回退路由以 [conception-orchestration.md](conception-orchestration.md) 为准。本节只说明各 skill 的职责，不授权下游静默补设定。

| SOP 步骤 | 独立 skill | 工作方式 | 交付给下一 skill 的已确认结果 |
| --- | --- | --- |
| 1. 收拢意图 | `novel-intent-facilitator` | 人机访谈 | 意图卡：故事承诺候选、非目标、硬约束、待定项。 |
| 2. 确立主体 | `novel-subject-designer` | 人机访谈 | 主体定义：核心选择、关系功能及所需世界压力。 |
| 3. 建立世界运行条件 | `novel-world-interviewer` | 人机访谈 | 世界运行契约：规则、环境、资源、权力、历史、信息和压力机制。 |
| 4. 设计核心角色 | `novel-character-interviewer` | 人机访谈 | 核心角色设计：动机、形成链、压力行为、关系动力、变化与选择预测。 |
| 5. 建立因果骨架 | `novel-causality-architect` | 人机访谈 | 因果故事线：触发、阶段变化、危机、高潮选择、结局。 |
| 6. 规定叙述边界 | `novel-narrative-contract-designer` | 人机访谈 | 叙述契约：POV、信息规则、时间组织、表达原则与禁区。 |
| 6.5. 审计并可视化审阅访谈结果 | `novel-interview-integrity-auditor` → `novel-interview-brief-generator` | Agent 自主审计 + 作者审阅 | 先通过六维完整性审计，再输出 HTML 三板块简报；作者批准后才进入开发地图。 |
| 6. 自主构思 | V2 `S1→W1→E1→T1→C1→Q1→P1` 技能链 | Agent 按硬 gate 自主完成 | 故事线架构、世界、环境、事件、角色、独立审查与机器构思交付包。 |
| 7. 人审并交接 | V2 `H1-A→H1-B→H1-A→H1-C` + 主 Harness | Agent 呈现、作者外部裁决 | 十分钟人审报告、正式 H1 completion；仅 approved 生成最终构思 completion。 |

### 5.2 前五步的共同交互协议

六个访谈 skill 不是“向用户一次性索取完整大纲”。它们必须先按 [interview-protocol.md](interview-protocol.md) 展示问题数与时长计划，并使用以下循环，把讨论变成可确认的创作决策：

1. **回显已知事实**：先区分“作者已确认 / 当前推断 / 尚未决定”，不得将三者混写。
2. **聚焦一个决策组**：每轮只讨论一个相互关联的问题组，最多提出三个短问题；必要时给出不超过三个候选及其故事影响。
3. **解释取舍**：说明每个候选会改变什么控制点，不以“更好看”一类空泛理由推动选择。
4. **请求明确确认**：只有作者明确确认、修改后确认或授权暂定，才能把结果记入本步产物。
5. **给出检查点**：每完成一个决策组，列出已冻结项、仍待定项、它们对下一步的影响，并询问是否继续。

作者可以回答“暂定”“保留两个候选”或“回到上一项”；skill 必须将其记录为状态，而不能强迫伪确定。若一个未决项会改变后续核心选择，skill 必须暂停在该检查点。

每个访谈结束还必须生成完整逐轮访谈报告；当前设计产物是下游权威，报告用于审计和回退。六份访谈完成后，`novel-interview-integrity-auditor` 先检查覆盖、版本和报告完整性，只有 `ready` 才由 `novel-interview-brief-generator` 生成 HTML 简报。作者批准前不得进入自主构思；若作者发现问题，按其控制点退回对应访谈 skill。自主技能不再发起创作访谈；它们只消费已确认材料，按所有权补齐职责内的构思控制信息。发现必须由作者裁决的缺失或矛盾时，输出 blocker 和影响范围并走确定性 return route，不替作者作决定。D1/R1 只用于识别旧包，不构成 V2 成功或兼容路径。

## 6. 构思阶段的评价方法与完成标准

### 6.1 核心评价问题

审阅 NDB 时，优先问“它是否能指导开发”，而不是“它是否写得充分”。

| 维度 | 评价问题 | 通过标准 |
| --- | --- | --- |
| 方向清晰 | 一位新开发者能否准确说出这是什么故事、不是什么故事？ | 故事承诺、主题和非目标互不矛盾，且可复述。 |
| 主体成立 | 主角与关键关系是否真正驱动变化？ | 每个关键结果都能回到人物选择、关系冲突或世界规则。 |
| 角色可预测 | 核心角色是否有可信且可检验的选择逻辑？ | 动机、形成链、压力反应、关系杠杆和变化边界能解释关键选择。 |
| 因果闭环 | 主线是否从触发走向有代价的结局？ | 节点不是并列事件；高潮和结局回应开篇提出的问题。 |
| 规则有效 | 世界与环境是否限制或迫使选择？ | 规则有代价、边界和情节影响，不是资料展示。 |
| 开发可用 | 开发者是否知道该写什么、不能写什么、何时要回问？ | 开发地图、叙述契约和决策清单完整。 |
| 自由恰当 | 是否只固定控制点，没有把正文预写成僵硬脚本？ | 场景定义功能和结果，不规定每个动作与句子。 |

### 6.2 交接验收测试

把 NDB 交给一位未参与构思的开发者，要求其在不阅读原始聊天记录的情况下完成以下任务：

1. 复述故事承诺、主角选择、结局性质和不可违反项；
2. 写出主体故事线的因果链及每阶段变化；
3. 指出任意一个开发单元的目标、POV、可透露的信息与必须抵达的结果；
4. 列出本场可以自由创造的部分与必须回问作者的部分；
5. 识别两个会导致故事偏航的错误写法，并说明为何错误。

若开发者需要依靠猜测、从散文中“悟出”设计、或对同一控制点得出互相矛盾的理解，则 NDB 为 `revise`。只有上述任务均可完成、没有未裁决的结构性问题、并获得作者批准时，构思阶段才算完成。

### 6.3 典型失败信号

- 文档很长，却说不清主角最终必须作出的选择；
- 有人物设定和事件表，却无法说明事件为何由这些人物造成；
- 有完整世界观，却没有一条规则改变角色的行动代价；
- 把“之后由写作时决定”用于结局、身份真相、主题边界或信息释放；
- 开发者必须不断问“这个场景要达到什么”“这里能不能揭露”“人物为什么会这样做”。

## 7. 与开发阶段的正式交接

开发阶段收到的不是“请按大纲写小说”，而是以下授权：

```text
在故事承诺、角色选择、世界边界、主线因果、信息规则和叙述契约不变的条件下，
把开发地图中的每个功能单元实现为有生命力的小说文字。
```

开发若发现某个局部写法不好，可以自行调整；若发现控制点彼此冲突、主线无法成立或必须改变核心选择，必须带着影响分析退回构思，而不能静默改写。
