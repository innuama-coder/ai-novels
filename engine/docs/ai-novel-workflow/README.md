# AI 小说创作两阶段工作流

## 摘要

本工作流将 AI 参与的小说创作明确分为两个相互隔离、可回退的阶段：**构思（Conception）**与**开发（Development）**。构思负责作出并冻结“写什么、为何这样写、哪些事实不得改变”的设计决策；开发只负责在已批准设计的边界内，完成、审校并交付小说文字。

它不把“生成一段文本”当作完成，也不把一份长篇设定散文当作可用设计。每次工作必须有可定位的输入、可消费的产物、明确状态和审查证据。

## 目标与非目标

| 类型 | 定义 |
| --- | --- |
| 目标 | 让人类作者与 AI 能稳定地从小说意图走到可审校手稿，并在任何场景追溯其设计依据与修改原因。 |
| 非目标 | 不规定唯一的美学流派、章节数量、模型、提示词供应商或出版发行流程。 |
| 人类作者职责 | 决定主题、价值取向、重大创作选择，并批准构思包、重大变更和定稿。AI 不替代这些授权。 |
| AI 职责 | 提取约束、提出有限候选、维护追溯关系、按批准设计起草与修订、暴露不确定性。 |
| 适用边界 | 长篇、中篇、系列首部均可；短篇可裁剪场景表，但不可省略方向、因果、角色与验收。 |

## 阶段接口

```text
作者简报 / 来源事实
       ↓
构思：Novel Design Package（批准版本）
       ↓ 仅通过“开发就绪”门禁后
开发：Scene Prose + Manuscript Manifest + Review Evidence
       ↓
人工定稿 / 发布流程
```

构思与开发之间的唯一正式接口是经作者批准的**小说设计说明**。它可以有版本清单等实现载体，但在实现工作开始前，最重要的是其内容能清楚传达方向、控制点和开发授权。开发不得从聊天记录、记忆或零散旧稿中补全核心设计；输入缺失时必须提出问题或变更请求。

## 统一状态与变更规则

| 状态 | 含义 | 可进入下一阶段？ |
| --- | --- | --- |
| `draft` | 正在生成或整理，尚未完整审查 | 否 |
| `revise` | 已发现问题，必须按问题单修订 | 否 |
| `blocked` | 缺少输入、授权或存在不可裁决冲突 | 否 |
| `approved` | 人类作者批准且本阶段门禁通过 | 是 |
| `superseded` | 被新版本替代，保留只读追溯 | 否 |
| `released` | 定稿手稿已批准交付 | 终态 |

设计冻结后，开发中出现的发现按影响分流：

| 变更级别 | 例子 | 处理 |
| --- | --- | --- |
| 微小 | 标点、病句、未改变已知事实的措辞 | 在开发中修订并记录。 |
| 局部 | 某场进入方式、非关键物件、段落顺序 | 建立场景级变更记录；若不影响设计约束，可由作者批示后继续。 |
| 结构 | POV、角色目标、事件因果、场景功能、时间线、结局或主题 | 停止受影响场景，退回构思阶段，发布新版设计包后再开发。 |

## 采用的设计原则

1. 先从最小故事承诺逐步展开，再进入场景级工作；设计不是一次性写完，而是允许受控回溯。
2. 情节、角色、世界与主题必须相互约束，不能由任何单一“设定文档”孤立决定。
3. 场景必须发生可识别的价值或局势变化；章节不是场景的替代定义。
4. 草稿、结构修订、语言修订和校对分开执行，防止 AI 用润色掩盖结构问题。
5. 机器门禁检查事实、结构、状态和追溯；语义与文学质量由 rubric 和人类作者共同评审。

详细方法论与每项原则的来源见 [methodology-review.md](references/methodology-review.md)。
