# 阶段二：开发（Development）定义

## 1. 使命、边界与职责

### 1.1 使命

开发阶段的使命是将一个已批准的 NDP 转化为**可审校、可追溯、可由作者批准的完整小说手稿**。它不只是“按大纲扩写”：每一场必须保持设计事实，同时在正文层面完成场景冲突、感知、人物行动、语言、节奏和修订。

### 1.2 边界

| 开发负责 | 开发不负责 |
| --- | --- |
| 场景上下文组装、场景计划、初稿、局部重写、全书修订、语言校对与汇编 | 未授权时重写主题、终局、主体故事线、人物核心目标、世界规则或关键场景功能 |
| 维护连续性账本、版本与场景状态 | 把“更有戏剧性”的临时想法偷偷写入正文 |
| 对发现的设计矛盾提出变更请求 | 用一个模型自评代替作者的文学判断 |
| 记录每个场景使用的设计版本、评审结果和改写原因 | 模仿在世作者可辨识的独特文风；只能落实抽象风格维度 |

### 1.3 角色分工

| 角色 | 职责 | 不可替代的控制点 |
| --- | --- | --- |
| 开发 AI | 按场景包起草、检查、修订；更新账本并上报问题 | 不批准结构变更或定稿。 |
| 连续性检查器 | 检查人名、时间、地点、物件、知识状态、伏笔和约束 | 不评判文学美感。 |
| 语义/文学评审者 | 以 rubric 评估场景功能、人物、节奏、声音和可读性 | 不可绕过事实门禁。 |
| 作者/编辑 | 批准关键草稿、变更请求、宏观修订方向与最终手稿 | 是唯一 `released` 授权人。 |

## 2. 输入契约

### 2.1 进入开发的前提

开发任务必须明确 `project_id`、`design_version`、`scene_id`（或明确的全书修订范围）和责任人。必须读取 NDP 的 `approved` manifest，而不是仅引用旧正文。

| 输入 | 必需性 | 用途 | 缺失行为 |
| --- | --- | --- | --- |
| 批准的 `design-manifest.yaml` | 是 | 确认版本、场景、硬约束与开放问题 | `blocked` |
| 场景卡 / `scene_id` | 新写场景时必需 | 限定本次目标、POV、信息与价值变化 | `blocked` |
| 相关角色、空间、叙述契约 | 是 | 约束声音、感知、状态与禁用项 | `blocked` |
| 连续性账本与已批准前文 | 条件必需 | 防止时间、状态与知识倒退 | 缺失则重建账本后再写 |
| 修改任务单 | 修订时必需 | 指明问题、范围、不可改变项和验收 | `blocked` |
| 作者反馈 | 条件必需 | 决定有争议的表达或结构选择 | 没有授权时保留候选，不入正文 |

### 2.2 场景上下文包

每次生成只装配与当前场景相关的最小闭包，而非把全书资料不加筛选地塞入提示词：场景卡、前序状态摘要、后续依赖、在场角色状态、空间状态、可揭示/不可揭示信息、硬约束、目标字数、最近的作者反馈。上下文包必须有 `context_hash` 和来源路径，便于复现。

## 3. 输出契约

### 3.1 Canonical artifact

开发的机器可读入口为 `manuscript-manifest.yaml`：

```yaml
project_id: string
design_version: semver
manuscript_version: semver
status: draft | revise | blocked | approved | released
scenes:
  - scene_id: string
    prose_path: path
    source_design_version: semver
    status: planned | drafted | reviewed | approved | assembled
    context_hash: string
    continuity_entry: path
    objective_gate: pass | fail
    semantic_review: pass | revise | fail
change_requests: [path]
assembly:
  manuscript_path: path
  order: [string]
release_approval: null
```

### 3.2 交付物

| 产物 | 消费者 | 必须内容 |
| --- | --- | --- |
| 独立场景正文 | 汇编器、作者、编辑 | 场景 ID、设计版本、连续 prose；不得混入提示词、技巧标记或解释。 |
| 场景计划卡 | 开发 AI、评审者 | 本场目标、冲突、价值变化、信息边界、状态变化与退出条件。 |
| 连续性账本 | 后续场景、检查器 | 时间、地点、人物身体/关系/知识状态、物件、未解线索、已兑现伏笔。 |
| 客观检查报告 | 交付门禁 | 输入版本、规则结果、失败项与命令/实现版本。 |
| 语义评审与修订单 | 作者、开发 AI | rubric 分数、引用片段、问题、修改目标、verdict。 |
| 变更请求 | 构思阶段、作者 | 影响分析、候选、推荐与批准状态。 |
| 汇编手稿 | 作者、编辑 | 已批准场景的唯一排序、章节结构与版本。 |

## 4. 开发 SOP

| 阶段 | 输入 | 核心工作 | 输出与证据 | 阻塞/回退 |
| --- | --- | --- | --- | --- |
| D0 准入与装配 | NDP、场景 ID、账本 | 验证设计版本，构造最小场景上下文包 | context manifest、场景计划卡 | 设计未批准或上下文缺失即阻塞。 |
| D1 场景计划 | 场景卡、上下文包 | 写明目标、冲突、选择、价值变化、信息界限和末态 | 可审阅计划卡 | 场景功能不清，退回构思。 |
| D2 受约束初稿 | D1 | 连续完成正文，不边写边做宏观重构 | `scene_id` 草稿、字数/版本记录 | 发现结构冲突，停止并提变更请求。 |
| D3 硬约束检查 | 草稿、账本、NDP | 检查 POV、事实、时间、名称、知识、禁用项、场景结果 | objective report | 失败必修，不得送语义评审。 |
| D4 语义评审与定向重写 | 通过 D3 的草稿 | 分别评估场景功能、人物行动、感知、语言、节奏；按问题单重写 | review report、修订 diff | 结构性问题退回构思；局部问题回到 D2。 |
| D5 连续性提交 | 已审场景 | 更新场景末态、伏笔、知识和物件状态 | ledger entry、`reviewed` 状态 | 账本冲突则 `revise`。 |
| D6 分批汇编与宏观修订 | 已审场景集合 | 检查章节间过渡、整体节奏、重复、线索闭合 | assembly、全书评审 | 发现设计级问题，建变更请求。 |
| D7 定稿与发布 | 全书通过版 | 人工编辑、校对、作者批准、冻结版本 | `released` manifest、发布决策 | 任一未批准场景不得汇入 release。 |

初稿与修订必须分离：D2 优先实现本场功能；D4 才处理有效性、表达和节奏。这样可避免 AI 在写作时因过度润色而遗漏因果或状态变化。

## 5. 关键步骤规格

### 5.1 关键步骤 A：最小场景上下文装配

目的不是提供“越多越好”的上下文，而是让模型知道此刻允许发生什么。装配器必须从 NDP 取当前场景、前置依赖、后置不可破坏条件、在场角色与空间、账本末态和相关禁用项；对每一条信息保留来源 ID。超过范围的世界设定不进入上下文，除非场景卡引用它。

门禁：每一项场景事实必须可回溯；当前场景不能使用账本中尚未获得的知识；上下文冲突时以批准的 NDP 为准并提交账本修复任务。

### 5.2 关键步骤 B：场景完成定义

一个可批准场景必须让读者在文中感受到：人物在特定限制下试图达成目标；遭遇阻力；作出行动或选择；局势/价值发生变化；结尾留下新的可行动状态。它不要求每场都高强度冲突，也不把地点切换或章节换行算作“场景”。

### 5.3 关键步骤 C：修订分层与变更升级

修订按四轮进行，前一轮通过后才进入后一轮：

1. **结构轮**：因果、场景功能、角色选择、信息顺序、时间线。
2. **人物与叙述轮**：POV、声音、动机可见性、关系变化、环境互动。
3. **语言与节奏轮**：重复、抽象解释、句群节奏、对白和感官密度。
4. **校对轮**：错字、标点、术语、人名与格式。

第一轮发现主题、终局、核心动机、世界规则或关键场景功能有误，必须建立结构性变更请求，不能通过局部润色“修好”。

## 6. 门禁与评价

### 6.1 客观门禁

| 检查 | 阻塞规则 |
| --- | --- |
| 版本追溯 | 每场必须指向已批准 `design_version` 和 `context_hash`。 |
| 设计一致性 | 不得违反场景卡的 POV、时间、地点、硬约束、必经结果与信息边界。 |
| 连续性 | 人物、物件、知识、受伤、关系与线索状态必须和账本相容。 |
| 完整性 | 正文非空；没有提示词残留、TODO、评审文字或未解决占位符。 |
| 交付状态 | 仅 `objective_gate=pass` 且 `semantic_review=pass` 的场景可汇编。 |
| 汇编完整性 | `assembly.order` 中的每一场均已批准，且没有重复、遗漏或使用 superseded 版本。 |

### 6.2 场景语义评审 rubric（100 分）

| 维度 | 分值 | 评审问题 |
| --- | ---: | --- |
| 场景功能与价值变化 | 20 | 本场是否真正完成卡片功能，并让局势改变可感？ |
| 人物能动性与一致性 | 20 | 行动是否来自人物处境、目标和限制，而非作者操纵？ |
| POV、信息与连续性 | 15 | 读者是否只获得该 POV 应知内容，且状态可接续？ |
| 冲突、节奏与因果 | 15 | 是否有可感阻力、选择和结果，而非信息堆放？ |
| 叙述声音与可读性 | 15 | 是否落实叙述契约，避免空泛、陈词滥调与无效解释？ |
| 感官/环境与情感外化 | 10 | 环境和物件是否服务行动与状态，而非装饰或直白命名情绪？ |
| 修订完成度 | 5 | 问题单是否被逐项回应，并没有引入新违例？ |

场景通过条件：无客观 blocker；总分 ≥ 80；前四项任一项不得低于其满分的 70%；作者没有提出未处理的重大异议。全书定稿还需额外完成宏观结构评审、角色弧与线索闭合审查、语言一致性审查和人工校对。

### 6.3 人工审查点

作者必须至少在以下节点介入：批准 NDP；批准第一个代表性场景的声音/密度；裁决所有结构性变更；批准全书宏观修订方向；批准最终 `released` 手稿。AI 可以给出建议和备选，但不能用“自动通过”取代这些决定。
