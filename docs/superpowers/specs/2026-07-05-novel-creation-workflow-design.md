# 小说创作工作流规范

## 修订记录

| 版本 | 日期 | 作者 | 变更摘要 | 状态 |
|---|---|---|---|---|
| v1.0 | 2026-07-05 | Codex | 根据用户定义整理小说创作全流程，明确各阶段职责、交付物、交接契约与回路机制 | 草案 |

## 1. 目标

本文档定义小说创作项目的标准工作流：

```text
idea -> intake -> proposal -> prd -> hld -> lld -> novel writing -> novel checking -> acceptance
```

该工作流用于约束 Agent 与人类用户在小说创作中的职责分工、文档边界、交付物形态和阶段验收方式。后续所有小说技能、项目文档与正文生产都应以本文档为最高层流程规范。

## 2. 总体原则

| 原则 | 定义 |
|---|---|
| 阶段单向细化 | 每一阶段只展开上一阶段已确认的信息，不越级替代下一阶段的工作 |
| 交付物驱动 | 每一阶段必须形成可被下一阶段直接使用的明确交付物 |
| 人机分工明确 | intake 和 acceptance 允许人类深度参与；proposal 到 checking 主要由 Agent 自主完成 |
| 指定部分独立 | PRD 面向小说的指定部分，该部分必须相对独立，可单独完成设计与验收 |
| writing/checking 可循环 | 正文写作与一致性检查不是线性一次完成，而是允许多轮修订 |
| 文档先于正文 | 正文写作必须建立在已确认的 proposal、PRD、HLD、LLD 基础上 |

## 3. 阶段定义

### 3.1 idea

| 项目 | 内容 |
|---|---|
| 参与者 | 人类用户 |
| 作用 | 提供原始小说创意、题材、灵感、情绪、设定片段或目标 |
| 输入 | 用户的自然语言想法 |
| 输出 | 原始 idea |
| 交付标准 | 不要求完整、结构化或自洽 |

idea 可以是不完整的。它只需要提供创作起点，不承担设计责任。

### 3.2 intake

| 项目 | 内容 |
|---|---|
| 参与者 | 人类用户 + Agent |
| 作用 | 将人类用户给出的 idea 补充完善，形成能够编写 proposal 的输入 |
| 输入 | 原始 idea |
| 输出 | intake brief |
| 工作方式 | 可交互，可多轮问答 |

intake 应澄清以下信息：

| 类别 | 需要澄清的问题 |
|---|---|
| 创作目标 | 写什么类型、面向什么读者、希望产生什么阅读体验 |
| 题材边界 | 哪些元素必须保留，哪些元素必须避免 |
| 篇幅形态 | 短篇、中篇、长篇、系列、单卷、多部曲 |
| 叙事偏好 | 视角、节奏、文风、情绪密度、开放或封闭结局 |
| 创作约束 | 禁用设定、敏感边界、现实对应关系、参考作品使用方式 |

intake 不产出完整小说构思。它只产出 proposal 可用的输入材料。

### 3.3 proposal

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 自主完成完整小说构思 |
| 输入 | intake brief |
| 输出 | proposal document |
| 核心交付 | 完整的小说构思 |

proposal 必须明确：

| 模块 | 内容 |
|---|---|
| 核心概念 | logline、核心问题、主要卖点 |
| 小说结构 | 单篇、分部、分卷、三幕/四幕/多幕结构 |
| 故事线 | 主线、展开线、隐藏线、情感线、主题线 |
| 主要人物 | 核心角色、关系、初始冲突、终局变化 |
| 世界初设 | 基础世界观、时代、地点、制度或超自然/科幻规则 |
| 结局方向 | 终局性质、是否开放、是否反转、系列钩子 |
| 风险与开放点 | 下一阶段需要控制或细化的问题 |

proposal 的重点是“小说整体成立”。它不承担逐场景细化责任，但必须让 PRD 能够受控地选择并设计指定部分。

### 3.4 PRD

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 完成小说指定部分的设计工作 |
| 输入 | proposal document + 指定部分范围 |
| 输出 | PRD document |
| 核心交付 | 指定部分的线性主干场景 |

指定部分可以是：

| 类型 | 示例 |
|---|---|
| 长篇中的一部 | 三部曲第一部 |
| 单部中的一卷 | 上卷 / 中卷 / 下卷 |
| 小说中的一个大段落 | 第一幕、某条主要任务线、某个篇章 |
| 短篇整体 | 当小说本身篇幅较短时，PRD 可覆盖整篇 |

PRD 必须设计线性主干场景。每个主干场景至少包含：

| 字段 | 内容 |
|---|---|
| 场景编号 | 主干场景唯一标识 |
| 场景位置 | 在指定部分中的顺序 |
| 角色 | 参与角色与角色关系状态 |
| 环境 | 场景发生地点及环境功能 |
| 事件 | 场景中的核心行动或变化 |
| 冲突 | 外部冲突、内部冲突或关系冲突 |
| 价值变化 | 场景开始与结束的状态变化 |
| 后续作用 | 对下一主干场景的推动 |

PRD 的核心不是完整世界观，而是“这一指定部分如何线性推进”。完整世界展开交给 HLD。

### 3.5 HLD

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 将 PRD 中的主干场景展开为小说世界观和世界结构 |
| 输入 | PRD document |
| 输出 | HLD document |
| 核心交付 | 小说世界观 + 世界结构 + 全量人物、环境和事件 |

HLD 必须定义小说世界中的完整信息：

| 模块 | 内容 |
|---|---|
| 世界观 | 历史、制度、技术、社会结构、规则边界 |
| 世界结构 | 空间结构、组织结构、权力结构、信息流结构 |
| 角色系统 | 所有角色，不只主角和核心配角 |
| 环境系统 | 所有叙事环境、空间关系、空间功能 |
| 事件系统 | 所有关键事件、背景事件、可见事件、隐藏事件 |
| 语言风格 | 叙述风格、句式、禁用语、意象系统 |
| 视角系统 | POV 分配、视角权限、信息不对称策略 |
| 时间结构 | 故事时间、叙事时间、角色感知时间 |
| 线索结构 | 主线、展开线、隐藏线在世界中的分布 |

HLD 的重点是“小说世界完整可运行”。它不写具体 prose，也不替代 LLD 的细部设计。

### 3.6 LLD

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 具体设计小说世界，明确人物、环境和事件 |
| 输入 | HLD document |
| 输出 | LLD design documents |
| 核心交付 | 具体设计文档 |

LLD 必须将 HLD 的全量世界信息落为可写作设计：

| 设计类型 | 内容 |
|---|---|
| 人物设计 | 外貌、行为、语言、动机链、场景行为、关系变化 |
| 环境设计 | 空间布局、感官锚点、物件生态、空间演化、场景状态 |
| 事件设计 | 事件因果、触发条件、参与方、信息可见性、后果 |
| 场景设计 | 具体场景蓝图、六要素、价值变化、写作材料、约束 |

LLD 的重点是“写作前所有细节已被定义”。它不直接输出小说正文。

### 3.7 novel writing

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 完成人物描写、环境描写、事件描写和场景描写，最终输出小说 |
| 输入 | LLD design documents + HLD 风格规范 |
| 输出 | writing artifacts + novel draft |
| 核心交付 | 各项描写与小说正文 |

writing 包含两类交付：

| 类型 | 内容 |
|---|---|
| 写作素材 | 人物描写、环境描写、事件描写、场景描写工具箱 |
| 正文草稿 | 按场景或章节生成的小说正文 |

writing 必须遵守：

| 约束 | 内容 |
|---|---|
| 不重设世界 | 不修改 HLD 的世界规则 |
| 不发明关键事件 | 不引入 LLD 未定义的关键事件 |
| 不破坏角色弧线 | 角色行为必须符合设计档案 |
| 不越过视角权限 | 角色不知道的信息不能进入其 POV |
| 保持 prose 自洽 | 正文必须可读、连续、无设计残留 |

### 3.8 novel checking

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 检查小说世界的一致性和完整性 |
| 输入 | novel draft + LLD + HLD + PRD + proposal |
| 输出 | checking report |
| 核心交付 | 检查报告 |

checking 必须覆盖：

| 检查项 | 内容 |
|---|---|
| 世界一致性 | 世界规则、技术设定、组织设定是否前后一致 |
| 人物一致性 | 角色行为、语言、动机、弧线是否符合设计 |
| 环境一致性 | 空间状态、物件变化、时间天气是否连续 |
| 事件一致性 | 事件因果、信息释放、伏笔回收是否成立 |
| 视角一致性 | POV 权限、信息不对称、叙述距离是否合规 |
| 风格一致性 | 语言风格、禁用语、节奏、意象是否统一 |
| 完整性 | 是否缺场景、缺动机、缺过渡、缺必要回收 |
| 指定部分达成 | 是否完成 PRD 中指定部分的主干场景目标 |

checking 输出必须区分问题严重性：

| 等级 | 定义 |
|---|---|
| P0 | 破坏核心设定或结局，必须修复 |
| P1 | 破坏主要情节、人物弧线或世界一致性，必须修复 |
| P2 | 影响阅读体验或局部逻辑，建议修复 |
| P3 | 文风、措辞、节奏层面的优化建议 |

### 3.9 writing/checking loop

writing 和 checking 允许形成循环：

```text
novel writing -> novel checking -> revision plan -> novel writing -> novel checking
```

循环终止条件：

| 条件 | 内容 |
|---|---|
| P0/P1 清零 | 无核心设定、主线、人物弧线级问题 |
| P2 可接受 | 剩余问题不影响指定部分成立 |
| 用户认可 | 人类用户认为当前版本可进入 acceptance |
| Agent 自检通过 | Agent 明确说明仍有风险但不阻塞验收 |

### 3.10 acceptance

| 项目 | 内容 |
|---|---|
| 参与者 | 人类用户 + Agent |
| 作用 | 共同验收小说阶段成果 |
| 输入 | novel draft + checking report |
| 输出 | acceptance result |
| 核心交付 | 接受、修改意见或下一轮任务 |

acceptance 可以产生三种结果：

| 结果 | 含义 | 后续 |
|---|---|---|
| Accepted | 当前阶段通过 | 进入归档、发布或下一指定部分 |
| Accepted with notes | 当前阶段通过，但记录后续优化建议 | 可进入下一阶段，同时保留优化清单 |
| Revision required | 当前阶段不通过 | 回到 writing/checking loop |

## 4. 阶段交接契约

| 上游 | 下游 | 交接物 | 下游可依赖内容 |
|---|---|---|---|
| idea | intake | 原始想法 | 灵感方向、用户偏好 |
| intake | proposal | intake brief | 题材边界、创作目标、约束 |
| proposal | PRD | proposal document | 完整小说构思、结构、故事线 |
| PRD | HLD | 主干场景 | 指定部分的线性推进结构 |
| HLD | LLD | 世界观与世界结构 | 全量角色、环境、事件、风格、视角 |
| LLD | writing | 具体设计文档 | 可直接写作的人物、环境、事件、场景设计 |
| writing | checking | 小说正文 | 实际 prose、章节、场景完成情况 |
| checking | writing | 检查报告 | 修订问题、严重性、修复建议 |
| checking | acceptance | 检查报告 + 修订后正文 | 可验收版本及残余风险 |

## 7. 后续落地顺序

建议按以下顺序更新项目：

1. 将本文档作为项目级 workflow spec。
2. 新增或更新 intake / proposal / checking / acceptance 对应技能。
3. 重构现有 PRD/HLD/LLD 技能边界。
4. 将《断线》现有文档映射到新流程。
5. 对现有正文执行第一轮 novel checking。
6. 根据 checking report 决定回到 writing 还是进入 acceptance。
