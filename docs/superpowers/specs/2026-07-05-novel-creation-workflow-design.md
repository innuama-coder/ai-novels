## 1. 目标

本文档定义小说创作项目的标准工作流：

```text
idea -> intake -> proposal -> prd -> hld -> lld -> novel writing -> novel checking -> acceptance
```

该工作流用于约束 Agent 与人类用户在小说创作中的职责分工、文档边界、交付物形态和阶段验收方式。后续所有小说技能、项目文档与正文生产都应以本文档为最高层流程规范。

## 2. 总体原则

| 原则 | 定义 |
|---|---|
| 阶段单向细化 | 每一阶段只展开上一阶段已确认的信息，不越级替代下一阶段的工作 |
| 交付物驱动 | 每一阶段必须形成可被下一阶段直接使用的明确交付物 |
| 人机分工明确 | intake 和 acceptance 允许人类深度参与；proposal 到 checking 主要由 Agent 自主完成 |
| 指定部分独立 | PRD 面向小说的指定部分，该部分必须相对独立，可单独完成设计与验收 |
| writing/checking 可循环 | 正文写作与一致性检查不是线性一次完成，而是允许多轮修订 |
| 文档先于正文 | 正文写作必须建立在已确认的 proposal、PRD、HLD、LLD 基础上 |
| 由简入繁 | PRD 及之前的交付物必须简洁、清晰、便于人类快速阅读和评审；PRD 之后才逐层展开复杂细节 |
| 自顶而下 | 下游阶段只允许展开、细化和执行上游已确认内容，不允许自行改写上游意图 |
| PRD 后约束冻结 | PRD 及之前的交付物通过评审后，成为 HLD、LLD、writing、checking 的最高约束和边界控制 |
| 正文服从上层设计 | checking 发现正文背离 PRD 及之前文档时，默认正文需要修订；只有人类明确决定时，才回滚上游重新设计 |

## 3. 阶段定义

### 3.1 idea

| 项目 | 内容 |
|---|---|
| 参与者 | 人类用户 |
| 作用 | 提供原始小说创意、题材、灵感、情绪、设定片段或目标 |
| 输入 | 用户的自然语言想法 |
| 输出 | 原始 idea |
| 交付标准 | 不要求完整、结构化或自洽 |

idea 可以是不完整的。它只需要提供创作起点，不承担设计责任。

### 3.2 intake

| 项目 | 内容 |
|---|---|
| 参与者 | 人类用户 + Agent |
| 作用 | 将人类用户给出的 idea 补充完善，形成能够编写 proposal 的输入 |
| 输入 | 原始 idea |
| 输出 | intake brief |
| 工作方式 | 可交互，可多轮问答 |

intake 应澄清以下信息：

| 类别 | 需要澄清的问题 |
|---|---|
| 创作目标 | 写什么类型、面向什么读者、希望产生什么阅读体验 |
| 题材边界 | 哪些元素必须保留，哪些元素必须避免 |
| 篇幅形态 | 短篇、中篇、长篇、系列、单卷、多部曲 |
| 叙事偏好 | 视角、节奏、文风、情绪密度、开放或封闭结局 |
| 创作约束 | 禁用设定、敏感边界、现实对应关系、参考作品使用方式 |

intake 不产出完整小说构思。它只产出 proposal 可用的输入材料。

### 3.3 proposal

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 自主完成完整小说构思 |
| 输入 | intake brief |
| 输出 | proposal document |
| 核心交付 | 完整的小说构思 |

proposal 必须明确：

| 模块 | 内容 |
|---|---|
| 核心概念 | logline、核心问题、主要卖点 |
| 小说结构 | 单篇、分部、分卷、三幕/四幕/多幕结构 |
| 故事线 | 主线、展开线、隐藏线、情感线、主题线 |
| 主要人物 | 核心角色、关系、初始冲突、终局变化 |
| 世界初设 | 基础世界观、时代、地点、制度或超自然/科幻规则 |
| 结局方向 | 终局性质、是否开放、是否反转、系列钩子 |
| 风险与开放点 | 下一阶段需要控制或细化的问题 |

proposal 的重点是“小说整体成立”。它不承担逐场景细化责任，但必须让 PRD 能够受控地选择并设计指定部分。

### 3.4 PRD

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 完成小说指定部分的设计工作 |
| 输入 | proposal document + 指定部分范围 |
| 输出 | PRD document |
| 核心交付 | 指定部分的线性主干场景 |

指定部分可以是：

| 类型 | 示例 |
|---|---|
| 长篇中的一部 | 三部曲第一部 |
| 单部中的一卷 | 上卷 / 中卷 / 下卷 |
| 小说中的一个大段落 | 第一幕、某条主要任务线、某个篇章 |
| 短篇整体 | 当小说本身篇幅较短时，PRD 可覆盖整篇 |

PRD 必须设计线性主干场景。每个主干场景至少包含：

| 字段 | 内容 |
|---|---|
| 场景编号 | 主干场景唯一标识 |
| 场景位置 | 在指定部分中的顺序 |
| 角色 | 参与角色与角色关系状态 |
| 环境 | 场景发生地点及环境功能 |
| 事件 | 场景中的核心行动或变化 |
| 冲突 | 外部冲突、内部冲突或关系冲突 |
| 价值变化 | 场景开始与结束的状态变化 |
| 后续作用 | 对下一主干场景的推动 |

PRD 的核心不是完整世界观，而是“这一指定部分如何线性推进”。完整世界展开交给 HLD。

### 3.5 HLD

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 将 PRD 中的主干场景展开为小说世界观和世界结构 |
| 输入 | PRD document |
| 输出 | HLD document |
| 核心交付 | 小说世界观 + 世界结构 + 全量人物、环境和事件 |

HLD 必须定义小说世界中的完整信息：

| 模块 | 内容 |
|---|---|
| 世界观 | 历史、制度、技术、社会结构、规则边界 |
| 世界结构 | 空间结构、组织结构、权力结构、信息流结构 |
| 角色系统 | 所有角色，不只主角和核心配角 |
| 环境系统 | 所有叙事环境、空间关系、空间功能 |
| 事件系统 | 所有关键事件、背景事件、可见事件、隐藏事件 |
| 语言风格 | 叙述风格、句式、禁用语、意象系统 |
| 视角系统 | POV 分配、视角权限、信息不对称策略 |
| 时间结构 | 故事时间、叙事时间、角色感知时间 |
| 线索结构 | 主线、展开线、隐藏线在世界中的分布 |

HLD 的重点是“小说世界完整可运行”。它不写具体 prose，也不替代 LLD 的细部设计。

### 3.6 LLD

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 具体设计小说世界，明确人物、环境和事件 |
| 输入 | HLD document |
| 输出 | LLD design documents |
| 核心交付 | 具体设计文档 |

LLD 必须将 HLD 的全量世界信息落为可写作设计：

| 设计类型 | 内容 |
|---|---|
| 人物设计 | 外貌、行为、语言、动机链、场景行为、关系变化 |
| 环境设计 | 空间布局、感官锚点、物件生态、空间演化、场景状态 |
| 事件设计 | 事件因果、触发条件、参与方、信息可见性、后果 |
| 场景设计 | 具体场景蓝图、六要素、价值变化、写作材料、约束 |

LLD 的重点是“写作前所有细节已被定义”。它不直接输出小说正文。

### 3.7 novel writing

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 完成人物描写、环境描写、事件描写和场景描写，最终输出小说 |
| 输入 | LLD design documents + HLD 风格规范 |
| 输出 | writing artifacts + novel draft |
| 核心交付 | 各项描写与小说正文 |

writing 包含两类交付：

| 类型 | 内容 |
|---|---|
| 写作素材 | 人物描写、环境描写、事件描写、场景描写工具箱 |
| 正文草稿 | 按场景或章节生成的小说正文 |

writing 必须遵守：

| 约束 | 内容 |
|---|---|
| 不重设世界 | 不修改 HLD 的世界规则 |
| 不发明关键事件 | 不引入 LLD 未定义的关键事件 |
| 不破坏角色弧线 | 角色行为必须符合设计档案 |
| 不越过视角权限 | 角色不知道的信息不能进入其 POV |
| 保持 prose 自洽 | 正文必须可读、连续、无设计残留 |

### 3.8 novel checking

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 检查小说世界的一致性和完整性 |
| 输入 | novel draft + LLD + HLD + PRD + proposal |
| 输出 | checking report |
| 核心交付 | 检查报告 |

checking 必须覆盖：

| 检查项 | 内容 |
|---|---|
| 世界一致性 | 世界规则、技术设定、组织设定是否前后一致 |
| 人物一致性 | 角色行为、语言、动机、弧线是否符合设计 |
| 环境一致性 | 空间状态、物件变化、时间天气是否连续 |
| 事件一致性 | 事件因果、信息释放、伏笔回收是否成立 |
| 视角一致性 | POV 权限、信息不对称、叙述距离是否合规 |
| 风格一致性 | 语言风格、禁用语、节奏、意象是否统一 |
| 完整性 | 是否缺场景、缺动机、缺过渡、缺必要回收 |
| 指定部分达成 | 是否完成 PRD 中指定部分的主干场景目标 |

checking 输出必须区分问题严重性：

| 等级 | 定义 |
|---|---|
| P0 | 破坏核心设定或结局，必须修复 |
| P1 | 破坏主要情节、人物弧线或世界一致性，必须修复 |
| P2 | 影响阅读体验或局部逻辑，建议修复 |
| P3 | 文风、措辞、节奏层面的优化建议 |

### 3.9 writing/checking loop

writing 和 checking 允许形成循环：

```text
novel writing -> novel checking -> revision plan -> novel writing -> novel checking
```

循环终止条件：

| 条件 | 内容 |
|---|---|
| P0/P1 清零 | 无核心设定、主线、人物弧线级问题 |
| P2 可接受 | 剩余问题不影响指定部分成立 |
| 用户认可 | 人类用户认为当前版本可进入 acceptance |
| Agent 自检通过 | Agent 明确说明仍有风险但不阻塞验收 |

### 3.10 acceptance

| 项目 | 内容 |
|---|---|
| 参与者 | 人类用户 + Agent |
| 作用 | 共同验收小说阶段成果 |
| 输入 | novel draft + checking report |
| 输出 | acceptance result |
| 核心交付 | 接受、修改意见或下一轮任务 |

acceptance 可以产生三种结果：

| 结果 | 含义 | 后续 |
|---|---|---|
| Accepted | 当前阶段通过 | 进入归档、发布或下一指定部分 |
| Accepted with notes | 当前阶段通过，但记录后续优化建议 | 可进入下一阶段，同时保留优化清单 |
| Revision required | 当前阶段不通过 | 回到 writing/checking loop |

## 4. 交付物规格与质量标准

### 4.1 总体规格

PRD 及之前的交付物面向人类评审，必须以“快速判断方向是否正确”为第一目标。PRD 之后的交付物面向 Agent 执行，必须以“完整、可执行、可检查”为第一目标。

| 阶段范围 | 面向对象 | 文档特征 | 质量目标 |
|---|---|---|---|
| idea | 人类表达 | 非结构化、可模糊 | 提供创作起点 |
| intake | 人类评审 + proposal 输入 | 短表格、少解释 | 让用户确认需求边界 |
| proposal | 人类评审 + PRD 输入 | 简洁构思案 | 让用户确认小说整体方向 |
| PRD | 人类评审 + HLD 输入 | 主干场景表 | 让用户确认指定部分的线性推进 |
| HLD | Agent 执行 | 完整结构文档 | 让小说世界可展开 |
| LLD | Agent 执行 | 具体设计文档集 | 让写作有明确材料 |
| writing | Agent 执行 + checking 输入 | 描写素材与正文 | 生成符合设计的 prose |
| checking | Agent 执行 + 人类决策输入 | 问题报告 | 判断正文是否可进入验收 |
| acceptance | 人机共同决策 | 验收记录 | 决定通过、备注通过或退回 |

### 4.2 intake 交付物：小说需求表

| 项目 | 规格 |
|---|---|
| 交付物名称 | 小说需求表 |
| 建议长度 | 1 页内；复杂项目不超过 2-3 页 |
| 文档形态 | 表格为主，必要时附 3-5 条短说明 |
| 面向对象 | 人类用户 + proposal writer |
| 核心问题 | 这本小说要写什么、给谁看、不能写什么、下一步 proposal 必须解决什么 |

小说需求表必须包含：

| 字段 | 内容 | 质量标准 |
|---|---|---|
| 原始 idea | 用户最初给出的创意 | 保留用户原意，不擅自文学化 |
| 创作目标 | 希望达成的阅读体验或作品目标 | 能用 1-3 句话说清 |
| 类型与题材 | 类型、题材、风格方向 | 不堆叠过多标签 |
| 目标读者 | 预期读者或阅读场景 | 能指导 proposal 的取舍 |
| 篇幅形态 | 短篇、中篇、长篇、系列、分部方式 | 与用户目标匹配 |
| 必须保留 | 用户明确要求保留的元素 | 可检查、不可含糊 |
| 必须避免 | 用户明确排除的元素 | 可作为后续检查项 |
| 参考对象 | 参考作品、风格、题材方向 | 明确“参考什么”，避免照搬 |
| 叙事偏好 | 视角、节奏、情绪密度、结局偏好 | 只记录已确认偏好 |
| 开放问题 | proposal 阶段需要解决的问题 | 数量克制，优先关键问题 |

好的小说需求表应满足：

| 标准 | 说明 |
|---|---|
| 简洁 | 人类用户能在数分钟内读完 |
| 清晰 | 用户能快速判断“对 / 不对 / 缺什么” |
| 不越级 | 不展开完整世界观，不提前写主干场景 |
| 可交接 | proposal writer 不需要重新追问基础目标 |
| 可检查 | “必须保留 / 必须避免”能进入后续 checking |

### 4.3 proposal 交付物：小说构思案

| 项目 | 规格 |
|---|---|
| 交付物名称 | 小说构思案 |
| 建议长度 | 短篇 2-4 页；长篇或系列 4-8 页 |
| 文档形态 | 短章节 + 核心表格 |
| 面向对象 | 人类用户 + PRD writer |
| 核心问题 | 这部小说整体是否成立 |

小说构思案必须包含：

| 字段 | 内容 | 质量标准 |
|---|---|---|
| logline | 一句话故事 | 能体现主角、冲突、代价或变化 |
| 核心概念 | 小说最重要的设定或叙事钩子 | 不超过 3 个核心点 |
| 故事结构 | 单篇、分部、分卷、幕结构 | 能支撑后续指定部分选择 |
| 故事线 | 主线、展开线、隐藏线、情感线、主题线 | 每条线有问题、起点、终点 |
| 主要人物 | 核心角色与关系 | 不做全量人物设计 |
| 世界初设 | 世界基本规则与限制 | 只定义足够支撑构思的内容 |
| 结局方向 | 终局性质和系列钩子 | 明确不可反转项 |
| PRD 建议范围 | 下一步适合设计哪个指定部分 | 范围相对独立 |

好的小说构思案应满足：

| 标准 | 说明 |
|---|---|
| 完整 | 用户能看懂小说整体想写什么 |
| 克制 | 不提前进入 HLD 的全量世界设计 |
| 可拆分 | 能清楚看出哪些部分可进入 PRD |
| 可评审 | 用户能判断结构、故事线、结局方向是否正确 |
| 可约束 | 核心概念与结局方向可成为下游边界 |

### 4.4 PRD 交付物：主干场景表

| 项目 | 规格 |
|---|---|
| 交付物名称 | 主干场景表 |
| 建议长度 | 以表格为主；每个主干场景 1 行或 1 个短块 |
| 文档形态 | 线性场景表 + 简短说明 |
| 面向对象 | 人类用户 + HLD writer |
| 核心问题 | 指定部分从开头到结尾如何推进 |

PRD 必须包含：

| 字段 | 内容 | 质量标准 |
|---|---|---|
| 指定部分范围 | 本 PRD 覆盖哪一部、哪一卷或哪一篇章 | 边界清楚，可独立验收 |
| 主干场景列表 | 线性排列的核心场景 | 顺序清晰，不跳跃 |
| 场景角色 | 每个场景出现或被影响的角色 | 角色功能明确 |
| 场景环境 | 场景发生的地点或环境类型 | 能支撑 HLD 展开空间系统 |
| 场景事件 | 场景中发生的核心行动 | 事件可被下游展开 |
| 冲突与价值变化 | 场景的冲突和状态变化 | 能看出推进力 |
| 关键约束 | 不可改变的情节、结局、人物边界 | 可作为 checking 依据 |
| HLD 展开要求 | 下游必须补全的世界、角色、环境、事件信息 | 不把细节留成隐性假设 |

好的 PRD 应满足：

| 标准 | 说明 |
|---|---|
| 线性可读 | 人类用户能顺着主干场景读完整个指定部分 |
| 简洁清楚 | 不写完整场景 prose，不塞入 LLD 细节 |
| 三要素明确 | 每个主干场景都有角色、环境、事件 |
| 推进明确 | 每个场景都改变局面，而不是只陈列设定 |
| 可冻结 | 通过评审后，可成为 HLD 及之后的最高约束 |

### 4.5 HLD 交付物：世界观与世界结构文档

| 项目 | 规格 |
|---|---|
| 交付物名称 | 世界观与世界结构文档 |
| 文档形态 | 分章节结构文档 |
| 面向对象 | LLD writer + writing/checking agents |
| 核心问题 | 这个小说世界如何完整运行 |

HLD 必须满足：

| 标准 | 说明 |
|---|---|
| 完整 | 定义所有角色、环境、事件，不只主线可见部分 |
| 受控 | 不改变 PRD 主干场景和 proposal 核心构思 |
| 可展开 | 每个世界结构都能交给 LLD 继续细化 |
| 可追溯 | 关键设计能追溯到 PRD 或 proposal |
| 可检查 | 形成 checking 可使用的世界一致性基准 |

### 4.6 LLD 交付物：具体设计文档集

| 项目 | 规格 |
|---|---|
| 交付物名称 | 具体设计文档集 |
| 文档形态 | 人物、环境、事件、场景分册或分文件 |
| 面向对象 | writing agents |
| 核心问题 | 写作时具体怎么写才不偏离设计 |

LLD 必须满足：

| 标准 | 说明 |
|---|---|
| 具体 | 人物行为、空间状态、事件因果、场景蓝图可直接用于写作 |
| 全覆盖 | 覆盖 HLD 定义的全部必要人物、环境、事件 |
| 不重写 | 不改变 HLD 世界结构和 PRD 主干场景 |
| 可执行 | writing agent 不需要临场发明关键设定 |
| 可验证 | checking 可逐项对照 LLD 检查正文 |

### 4.7 writing 交付物：描写素材与小说正文

| 项目 | 规格 |
|---|---|
| 交付物名称 | 描写素材 + 小说正文 |
| 文档形态 | 写作素材文件、场景正文、整合稿 |
| 面向对象 | checking agent + 人类读者 |
| 核心问题 | 是否把设计转化成可读小说 |

writing 必须满足：

| 标准 | 说明 |
|---|---|
| 执行设计 | 严格遵守 LLD、HLD、PRD、proposal |
| prose 完整 | 正文是小说，不保留设计注释或说明残留 |
| 视角合规 | 不越过 POV 权限 |
| 风格一致 | 语言风格符合 HLD 规范 |
| 可检查 | 场景、人物、环境、事件能被 checking 回溯 |

### 4.8 checking 交付物：检查报告

| 项目 | 规格 |
|---|---|
| 交付物名称 | 检查报告 |
| 文档形态 | 问题列表 + 严重性 + 修复建议 |
| 面向对象 | writing agent + 人类用户 |
| 核心问题 | 当前正文是否符合上层设计，是否可进入验收 |

检查报告必须包含：

| 字段 | 内容 |
|---|---|
| 检查范围 | 检查的是哪个正文版本、哪些上层文档 |
| 总体结论 | 可验收、需修订、严重偏离 |
| 问题列表 | 按 P0/P1/P2/P3 排序 |
| 证据位置 | 指向正文和设计文档的具体位置 |
| 修复建议 | 默认修正文稿；必要时标注是否需要上游重开 |
| 残余风险 | 修订后仍可能存在的问题 |

好的检查报告应满足：

| 标准 | 说明 |
|---|---|
| 证据明确 | 每个问题都有文本依据 |
| 分级清楚 | P0/P1/P2/P3 不混用 |
| 默认守上层 | 正文偏离上层时，优先要求正文修复 |
| 可执行 | writing agent 能据此直接修订 |
| 不重写正文 | checking 只报告与建议，不直接替代 writing |

### 4.9 acceptance 交付物：验收记录

| 项目 | 规格 |
|---|---|
| 交付物名称 | 验收记录 |
| 文档形态 | 简短结论 + 备注 |
| 面向对象 | 人类用户 + 项目归档 |
| 核心问题 | 当前阶段是否通过 |

验收记录必须包含：

| 字段 | 内容 |
|---|---|
| 验收对象 | 哪个正文或阶段交付物 |
| 检查报告引用 | 对应 checking report |
| 验收结果 | Accepted / Accepted with notes / Revision required |
| 人类意见 | 用户确认、保留意见或退回原因 |
| 后续动作 | 归档、进入下一部分、回到 writing/checking |

## 5. 人类评审与约束冻结

### 5.1 人类评审边界

| 阶段 | 是否必须人类评审 | 原因 |
|---|---|---|
| intake | 必须 | 需求表需要确认是否准确理解用户意图 |
| proposal | 必须 | 小说整体构思必须由人类确认方向 |
| PRD | 必须 | 主干场景通过后会冻结为下游最高约束 |
| HLD | 可选 | Agent 自主展开；人类可抽查或要求评审 |
| LLD | 可选 | Agent 自主细化；人类通常不逐项审阅 |
| writing | 可选 | 人类可读正文，但正式判断应结合 checking |
| checking | 建议 | 检查报告帮助人类决定是否进入 acceptance |
| acceptance | 必须 | 验收是人机共同决策 |

### 5.2 约束冻结规则

PRD 通过评审后，以下内容冻结：

| 冻结项 | 含义 |
|---|---|
| 小说核心概念 | 下游不得改写小说要表达的核心问题 |
| 指定部分范围 | 下游不得扩大或缩小 PRD 覆盖范围 |
| 主干场景顺序 | 下游不得擅自重排、删除或替换主干场景 |
| 关键角色功能 | 下游不得改变核心角色在主干场景中的功能 |
| 关键环境功能 | 下游不得改变主干环境的叙事用途 |
| 关键结局与约束 | 下游不得反转已确认的结局方向和禁区 |

允许下游展开的内容：

| 可展开项 | 含义 |
|---|---|
| 角色细节 | 外貌、习惯、语言、动机链、关系微结构 |
| 环境细节 | 空间布局、感官、物件、演化状态 |
| 事件细节 | 因果链、触发机制、信息可见性、后果 |
| 场景细节 | 节奏、对话、动作、感官、prose |
| 伏笔与回调 | 在不改变主干的前提下增强结构 |

### 5.3 上游重开规则

如果 HLD、LLD、writing 或 checking 发现 PRD 及之前文档存在根本问题，Agent 不得自行修改上游约束。必须形成“上游重开请求”，交由人类决定。

上游重开请求必须说明：

| 字段 | 内容 |
|---|---|
| 问题来源 | 哪个冻结约束导致下游无法成立 |
| 影响范围 | 影响 HLD、LLD、writing 还是 checking |
| 可选方案 | 修正文稿、局部重开 PRD、回到 proposal |
| Agent 建议 | 推荐方案及理由 |
| 人类决定 | 用户选择后才能执行 |

## 6. 阶段交接契约

| 上游 | 下游 | 交接物 | 下游可依赖内容 |
|---|---|---|---|
| idea | intake | 原始想法 | 灵感方向、用户偏好 |
| intake | proposal | intake brief | 题材边界、创作目标、约束 |
| proposal | PRD | proposal document | 完整小说构思、结构、故事线 |
| PRD | HLD | 主干场景 | 指定部分的线性推进结构 |
| HLD | LLD | 世界观与世界结构 | 全量角色、环境、事件、风格、视角 |
| LLD | writing | 具体设计文档 | 可直接写作的人物、环境、事件、场景设计 |
| writing | checking | 小说正文 | 实际 prose、章节、场景完成情况 |
| checking | writing | 检查报告 | 修订问题、严重性、修复建议 |
| checking | acceptance | 检查报告 + 修订后正文 | 可验收版本及残余风险 |
