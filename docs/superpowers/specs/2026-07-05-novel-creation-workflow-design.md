## 1. 目标

本文档定义小说创作项目的标准工作流：

```text
idea -> intake -> proposal -> prd -> hld -> lld -> novel writing -> novel checking -> acceptance
```

该工作流用于约束 Agent 与人类用户在小说创作中的职责分工、文档边界、交付物形态和阶段验收方式。后续所有小说技能、项目文档与正文生产都应以本文档为最高层流程规范。

## 2. 总体原则

| 原则 | 定义 |
|---|---|
| 阶段单向细化 | 每一阶段只展开上一阶段已确认的信息，不越级替代下一阶段的工作 |
| 交付物驱动 | 每一阶段必须形成可被下一阶段直接使用的明确交付物 |
| 人机分工明确 | intake 和 acceptance 允许人类深度参与；proposal 到 checking 主要由 Agent 自主完成 |
| 指定部分独立 | PRD 面向小说的指定部分，该部分必须相对独立，可单独完成设计与验收 |
| writing/checking 可循环 | 正文写作与一致性检查不是线性一次完成，而是允许多轮修订 |
| 文档先于正文 | 正文写作必须建立在已确认的 proposal、PRD、HLD、LLD 基础上 |
| 由简入繁 | PRD 及之前的交付物必须简洁、清晰、便于人类快速阅读和评审；PRD 之后才逐层展开复杂细节 |
| 自顶而下 | 下游阶段只允许展开、细化和执行上游已确认内容，不允许自行改写上游意图 |
| PRD 后约束冻结 | PRD 及之前的交付物通过评审后，成为 HLD、LLD、writing、checking 的最高约束和边界控制 |
| 正文服从上层设计 | checking 发现正文背离 PRD 及之前文档时，默认正文需要修订；只有人类明确决定时，才回滚上游重新设计 |
| 强 harness 驱动 | 除 intake 外，每个节点必须由一个 harness workflow 负责调度、串接、分配、登记、打包和验收 |
| 业务技能内聚 | harness 不做实际业务设计或写作；所有业务工作必须由职责单一、边界明确、可独立验收的独立技能完成 |

## 2.1 节点执行架构

除 intake 外，每个工作流节点必须采用以下执行架构：

```text
node = harness workflow + independent skills
```

harness workflow 的职责：

| 职责 | 内容 |
|---|---|
| 输入校验 | 确认上游交付物齐备、版本明确、冻结项可识别 |
| 任务分解 | 将节点目标拆给多个独立技能，不直接完成业务内容 |
| 调度编排 | 决定技能调用顺序、并行关系、依赖关系和重试策略 |
| 边界仲裁 | 阻止独立技能越级修改上游约束或侵入其他技能职责 |
| 交付打包 | 将独立技能交付物登记、编号、装配为节点交付包 |
| 质量验收 | 按 artifact、schema、rules、references、traceability 验收节点输出 |
| 重开管理 | 发现上游根本问题时生成上游重开请求，而不是自行改写上游 |

harness workflow 明确禁止：

| 禁止项 | 原因 |
|---|---|
| 不直接设计故事、角色、世界、场景或正文 | 业务内容必须由独立技能完成 |
| 不用打包名义改写技能输出的核心业务结论 | 打包只解决文件组织、版本登记和交接，不替代业务判断 |
| 不绕过 rules / references / traceability 验收 | harness 是质量闸门，不是自由生成器 |
| 不在下游节点修改上游冻结项 | 只能生成上游重开请求 |

需要改写、归并、分级、排序、取舍、过渡或口径统一的集成工作，本身属于业务能力，必须由独立 integrator / checker / router skill 承接，不能由 harness workflow 直接完成。

独立技能必须满足：

| 要求 | 内容 |
|---|---|
| 内聚 | 一个技能只负责一个可命名的业务能力 |
| 边界清晰 | 明确输入、输出、允许做什么、禁止做什么 |
| 可独立验收 | 技能输出必须有自己的 rules、references 和 traceability |
| 可被编排 | 技能不得假设自己拥有整个节点控制权 |
| 可替换 | 更换某个技能不应破坏 harness 的总体契约 |

intake 是例外。intake 可以采用轻量交互式 harness，但不强制拆成多个 Agent 自主技能，因为 intake 的核心任务是与人类用户对齐需求。

## 3. 阶段定义

### 3.1 idea

| 项目 | 内容 |
|---|---|
| 参与者 | 人类用户 |
| 作用 | 提供原始小说创意、题材、灵感、情绪、设定片段或目标 |
| 输入 | 用户的自然语言想法 |
| 输出 | 原始 idea |
| 交付标准 | 不要求完整、结构化或自洽 |

idea 可以是不完整的。它只需要提供创作起点，不承担设计责任。

### 3.2 intake

| 项目 | 内容 |
|---|---|
| 参与者 | 人类用户 + Agent |
| 作用 | 将人类用户给出的 idea 补充完善，形成能够编写 proposal 的输入 |
| 输入 | 原始 idea |
| 输出 | intake brief |
| 工作方式 | 可交互，可多轮问答 |

intake 只按需要澄清最少信息。以下类别是提问范围，不是需求表必填清单：

| 类别 | 需要澄清的问题 |
|---|---|
| 核心意图 | 用户真正想探索的问题、题材或阅读体验 |
| 题材边界 | 哪些元素必须保留，哪些元素必须避免 |
| 篇幅形态 | 短篇、中篇、长篇、系列、单卷、多部曲 |
| 叙事偏好 | 视角、节奏、文风、情绪密度、开放或封闭结局 |
| 创作约束 | 禁用设定、敏感边界、现实对应关系、参考作品使用方式 |

intake 不产出完整小说构思，也不替用户补全所有偏好。它只冻结 proposal 必须服从的最小核心输入；其他内容进入开放问题。

### 3.3 proposal

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 自主完成整部小说的构思契约 |
| 输入 | intake brief |
| 输出 | proposal document |
| 核心交付 | 完整小说构思，回答“这部小说整体是否值得写、写什么、承诺什么阅读体验” |

proposal 必须明确：

| 模块 | 内容 |
|---|---|
| 读者承诺 | 类型、情绪体验、阅读快感、题材边界 |
| 核心概念 | logline、核心问题、主要卖点、不可替换的叙事钩子 |
| 整体结构 | 单篇、分部、分卷、三幕/四幕/多幕结构或其他宏观结构 |
| 故事线 | 主线、展开线、隐藏线、情感线、主题线的起点、终点和相互关系 |
| 主要人物 | 核心角色、关系、初始冲突、终局变化 |
| 世界初设 | 只定义足够支撑构思的时代、地点、制度、技术或超自然/科幻规则 |
| 结局方向 | 终局性质、不可反转项、是否开放、是否保留系列钩子 |
| PRD 建议范围 | 下一阶段适合拆出的指定部分，以及该部分为什么相对独立 |
| 风险与开放点 | 下一阶段必须控制或细化的问题 |

proposal 的硬标准：

| 标准 | 内容 |
|---|---|
| intake 是最高约束 | proposal 必须先建立 intake boundary ledger，逐条登记 `KEEP-*`、`AVOID-*`、`OPEN-*` |
| 不反写 intake | proposal 可以回答开放问题，但不能把自己的设计决策写成用户已确认需求 |
| 不吸收后期草稿 | 旧 PRD / HLD / LLD / writing 只能作为非冻结参考，不能覆盖 intake brief |
| 决策要标源 | 每个新增核心设定必须标明来自 intake 约束、`OPEN-*` 回答，还是 proposal 自主设计 |

proposal 的重点是“小说整体成立”。它是整部小说的顶层构思契约，不承担逐场景细化责任，也不展开完整世界 bible；但必须让 PRD 能够受控地选择并设计指定部分。

proposal 明确禁止：

| 禁止项 | 原因 |
|---|---|
| 不写主干场景表 | 逐场景推进属于 PRD |
| 不定义全量角色、环境、事件 | 全量世界系统属于 HLD |
| 不写章节正文或 prose 样章 | 正文生产属于 writing |
| 不把开放问题伪装成设定 | 未决问题必须显式交给 PRD 或 HLD |

### 3.4 PRD

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 完成小说指定部分的主干场景契约 |
| 输入 | proposal document + 指定部分范围 |
| 输出 | PRD document |
| 核心交付 | 指定部分的线性主干场景，回答“这一部分从开头到结尾如何推进” |

指定部分可以是：

| 类型 | 示例 |
|---|---|
| 长篇中的一部 | 三部曲第一部 |
| 单部中的一卷 | 上卷 / 中卷 / 下卷 |
| 小说中的一个大段落 | 第一幕、某条主要任务线、某个篇章 |
| 短篇整体 | 当小说本身篇幅较短时，PRD 可覆盖整篇 |

PRD 必须设计线性主干场景。主干场景不是全部章节，也不是 prose 草稿，而是指定部分不可缺少的因果节点。每个主干场景至少包含：

| 字段 | 内容 |
|---|---|
| 场景编号 | 主干场景唯一标识 |
| 场景位置 | 在指定部分中的顺序 |
| 角色 | 参与角色与角色关系状态 |
| 环境 | 场景发生地点及环境功能 |
| 事件 | 场景中的核心行动或变化 |
| 冲突 | 外部冲突、内部冲突或关系冲突 |
| 价值变化 | 场景开始与结束的状态变化 |
| 后续作用 | 对下一主干场景的推动 |

PRD 的核心不是完整世界观，而是“这一指定部分如何线性推进”。它必须把角色、环境、事件写到足以让人判断主干是否成立，但不能越级展开为全量世界设定。完整世界展开交给 HLD。

PRD 明确禁止：

| 禁止项 | 原因 |
|---|---|
| 不重新定义小说核心概念 | 核心构思已由 proposal 冻结 |
| 不把指定部分扩展成整部小说 bible | PRD 只服务指定部分 |
| 不补写所有背景角色和隐藏事件 | 全量人物/环境/事件属于 HLD |
| 不写具体对白、段落和修辞 | 具体表达属于 LLD 和 writing |

### 3.5 HLD

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 将 PRD 中的主干场景展开为可运行的世界系统契约 |
| 输入 | PRD document |
| 输出 | HLD document |
| 核心交付 | 小说世界观 + 世界结构 + 全量人物、环境和事件，回答“什么样的世界系统能让 PRD 主干必然成立” |

HLD 必须定义小说世界中的完整信息：

| 模块 | 内容 |
|---|---|
| 世界观 | 历史、制度、技术、社会结构、规则边界，以及这些规则如何影响 PRD 场景 |
| 世界结构 | 空间结构、组织结构、权力结构、信息流结构 |
| 角色系统 | 所有角色，不只主角和核心配角；包括其功能、关系、动机和信息权限 |
| 环境系统 | 所有叙事环境、空间关系、空间功能、状态变化 |
| 事件系统 | 所有关键事件、背景事件、可见事件、隐藏事件及其因果关系 |
| 语言风格 | 叙述风格、句式、禁用语、意象系统 |
| 视角系统 | POV 分配、视角权限、信息不对称策略 |
| 时间结构 | 故事时间、叙事时间、角色感知时间 |
| 线索结构 | 主线、展开线、隐藏线在世界中的分布 |

HLD 的重点是“小说世界完整可运行”。它不写具体 prose，也不替代 LLD 的细部设计。HLD 可以补全 PRD 未展开的世界原因、人物网络、背景事件和信息流，但不得擅自改变 PRD 已冻结的主干场景、顺序、结局方向或关键角色功能。

HLD 明确禁止：

| 禁止项 | 原因 |
|---|---|
| 不重排、删除或替换 PRD 主干场景 | PRD 通过评审后冻结 |
| 不改变 proposal 的核心概念和读者承诺 | 顶层构思已冻结 |
| 不把世界设定写成章节执行稿 | 章节执行属于 LLD 和 writing |
| 不用“世界观更合理”为理由自动改写上游 | 发现根本问题时必须发起上游重开请求 |

### 3.6 LLD

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 具体设计小说世界，明确人物、环境和事件 |
| 输入 | HLD document |
| 输出 | LLD design documents |
| 核心交付 | 具体设计文档 |

LLD 必须将 HLD 的全量世界信息落为可写作设计：

| 设计类型 | 内容 |
|---|---|
| 人物设计 | 外貌、行为、语言、动机链、场景行为、关系变化 |
| 环境设计 | 空间布局、感官锚点、物件生态、空间演化、场景状态 |
| 事件设计 | 事件因果、触发条件、参与方、信息可见性、后果 |
| 场景设计 | 具体场景蓝图、六要素、价值变化、写作材料、约束 |

LLD 的重点是“写作前所有细节已被定义”。它不直接输出小说正文。

### 3.7 novel writing

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 完成人物描写、环境描写、事件描写和场景描写，最终输出小说 |
| 输入 | LLD design documents + HLD 风格规范 |
| 输出 | writing artifacts + novel draft |
| 核心交付 | 各项描写与小说正文 |

writing 包含两类交付：

| 类型 | 内容 |
|---|---|
| 写作素材 | 人物描写、环境描写、事件描写、场景描写工具箱 |
| 正文草稿 | 按场景或章节生成的小说正文 |

writing 必须遵守：

| 约束 | 内容 |
|---|---|
| 不重设世界 | 不修改 HLD 的世界规则 |
| 不发明关键事件 | 不引入 LLD 未定义的关键事件 |
| 不破坏角色弧线 | 角色行为必须符合设计档案 |
| 不越过视角权限 | 角色不知道的信息不能进入其 POV |
| 保持 prose 自洽 | 正文必须可读、连续、无设计残留 |

### 3.8 novel checking

| 项目 | 内容 |
|---|---|
| 参与者 | Agent |
| 作用 | 检查小说世界的一致性和完整性 |
| 输入 | novel draft + LLD + HLD + PRD + proposal |
| 输出 | checking report |
| 核心交付 | 检查报告 |

checking 必须覆盖：

| 检查项 | 内容 |
|---|---|
| 世界一致性 | 世界规则、技术设定、组织设定是否前后一致 |
| 人物一致性 | 角色行为、语言、动机、弧线是否符合设计 |
| 环境一致性 | 空间状态、物件变化、时间天气是否连续 |
| 事件一致性 | 事件因果、信息释放、伏笔回收是否成立 |
| 视角一致性 | POV 权限、信息不对称、叙述距离是否合规 |
| 风格一致性 | 语言风格、禁用语、节奏、意象是否统一 |
| 完整性 | 是否缺场景、缺动机、缺过渡、缺必要回收 |
| 指定部分达成 | 是否完成 PRD 中指定部分的主干场景目标 |

checking 输出必须区分问题严重性：

| 等级 | 定义 |
|---|---|
| P0 | 破坏核心设定或结局，必须修复 |
| P1 | 破坏主要情节、人物弧线或世界一致性，必须修复 |
| P2 | 影响阅读体验或局部逻辑，建议修复 |
| P3 | 文风、措辞、节奏层面的优化建议 |

### 3.9 writing/checking loop

writing 和 checking 允许形成循环：

```text
novel writing -> novel checking -> revision plan -> novel writing -> novel checking
```

循环终止条件：

| 条件 | 内容 |
|---|---|
| P0/P1 清零 | 无核心设定、主线、人物弧线级问题 |
| P2 可接受 | 剩余问题不影响指定部分成立 |
| 用户认可 | 人类用户认为当前版本可进入 acceptance |
| Agent 自检通过 | Agent 明确说明仍有风险但不阻塞验收 |

### 3.10 acceptance

| 项目 | 内容 |
|---|---|
| 参与者 | 人类用户 + Agent |
| 作用 | 共同验收小说阶段成果 |
| 输入 | novel draft + checking report |
| 输出 | acceptance result |
| 核心交付 | 接受、修改意见或下一轮任务 |

acceptance 可以产生三种结果：

| 结果 | 含义 | 后续 |
|---|---|---|
| Accepted | 当前阶段通过 | 进入归档、发布或下一指定部分 |
| Accepted with notes | 当前阶段通过，但记录后续优化建议 | 可进入下一阶段，同时保留优化清单 |
| Revision required | 当前阶段不通过 | 回到 writing/checking loop |

## 4. 交付物规格与质量标准

### 4.1 总体规格

PRD 及之前的交付物面向人类评审，必须以“快速判断方向是否正确”为第一目标。PRD 之后的交付物面向 Agent 执行，必须以“完整、可执行、可检查”为第一目标。

| 阶段范围 | 面向对象 | 文档特征 | 质量目标 |
|---|---|---|---|
| idea | 人类表达 | 非结构化、可模糊 | 提供创作起点 |
| intake | 人类评审 + proposal 输入 | 短表格、少解释 | 让用户确认需求边界 |
| proposal | 人类评审 + PRD 输入 | 简洁构思案 | 让用户确认小说整体方向 |
| PRD | 人类评审 + HLD 输入 | 主干场景表 | 让用户确认指定部分的线性推进 |
| HLD | Agent 执行 | 完整结构文档 | 让小说世界可展开 |
| LLD | Agent 执行 | 具体设计文档集 | 让写作有明确材料 |
| writing | Agent 执行 + checking 输入 | 描写素材与正文 | 生成符合设计的 prose |
| checking | Agent 执行 + 人类决策输入 | 问题报告 | 判断正文是否可进入验收 |
| acceptance | 人机共同决策 | 验收记录 | 决定通过、备注通过或退回 |

所有交付物规格必须按以下模型表达：

| 组件 | 含义 | 验收作用 |
|---|---|---|
| artifact | 交付物名称、面向对象、长度、文档形态、核心问题 | 判断交付物是否属于正确类型 |
| schema | 必须包含的字段、字段含义、字段质量要求 | 判断交付物是否完整 |
| rules | 必须遵守的规则、禁止事项、通过/拒绝条件 | 判断交付物是否合格 |
| references | 好交付物的参照标准、正例特征、反例特征、质量标杆 | 判断交付物是否优秀、清晰、可用 |
| traceability | 必须引用和追溯的上游文档、冻结项、方法论、版本或证据 | 判断交付物是否受控、可追溯、可检查 |

rules、references 和 traceability 的关系：

| 项目 | 要求 |
|---|---|
| rules | 必须能被 Agent 或人类用“通过 / 不通过 / 需要重开”来判定 |
| references | 必须描述“好交付物长什么样”，用于提升交付质量，而不是说明引用来源 |
| traceability | 必须指明规则依据来自哪里，避免 Agent 凭空生成或自行改写上游意图 |
| 缺少 rules | 交付物只能阅读，不能验收 |
| 缺少 references | 交付物只能合规，不能判断是否足够好 |
| 缺少 traceability | 交付物只能自洽，不能证明其服从上游约束 |

### 4.2 intake 交付物：小说需求表

| 项目 | 规格 |
|---|---|
| 交付物名称 | 小说需求表 |
| 建议长度 | 半页到 1 页；复杂项目仍优先控制在 1 页内 |
| 文档形态 | 极简表格为主，只附必要短说明 |
| 面向对象 | 人类用户 + proposal writer |
| 核心问题 | 这本小说要写什么、给谁看、不能写什么、下一步 proposal 必须解决什么 |

小说需求表只冻结最小核心信息：

| 字段 | 内容 | 质量标准 |
|---|---|---|
| 原始 idea | 用户最初给出的创意 | 保留用户原意，不擅自文学化 |
| 核心意图 | 用户希望探索的题材、问题或阅读体验 | 1-2 句话；不能替用户扩写成完整构思 |
| 硬约束 | 用户明确要求保留 / 避免的少量事项 | 通常不超过 3-5 条；必须可检查 |
| 参考对象 | 仅记录用户明确给出的参考对象 | 说明“参考什么”，避免照搬 |
| 开放问题 | proposal 阶段必须解决的关键问题 | 通常不超过 3 条；只保留方向级问题 |
| 交接状态 | ready / ready_with_open_questions / not_ready | 如实反映是否足够进入 proposal |

以下字段只在用户明确给出或强相关时记录，不能为了完整表格而推断：

| 可选字段 | 使用条件 |
|---|---|
| 类型与题材 | 用户已明确，或从原始 idea 中直接可见 |
| 目标读者 | 用户已明确目标读者或阅读场景 |
| 篇幅形态 | 用户已明确短篇、中篇、长篇、系列等形态 |
| 叙事偏好 | 用户已明确视角、节奏、情绪密度、结局偏好 |

好的小说需求表应满足：

| 标准 | 说明 |
|---|---|
| 简洁 | 人类用户能在 1-2 分钟内读完 |
| 清晰 | 用户能快速判断“对 / 不对 / 缺什么” |
| 不越级 | 不展开完整世界观，不提前写主干场景 |
| 可交接 | proposal writer 知道哪些是冻结项、哪些必须自行设计 |
| 可检查 | “必须保留 / 必须避免”能进入后续 checking |

intake rules：

| 规则 | 通过标准 | 拒绝条件 |
|---|---|---|
| 保留原意 | 原始 idea 被准确记录，未被 Agent 文学化改写 | 为了“更像小说”而改变用户原始意图 |
| 显式边界 | 必须保留、必须避免、参考对象、敏感边界均可检查 | 把限制写成模糊形容词，无法进入后续 checking |
| 最小核心 | 只冻结 proposal 必须服从的关键边界 | 从前置材料中提取大量可后续设计的细节 |
| 问题外显 | 不确定信息进入开放问题 | Agent 擅自补全用户未确认的关键偏好 |
| 快速评审 | 普通需求表半页到 1 页 | 用户需要读大量解释才能判断是否理解正确 |

intake references：

| 参照维度 | 好的小说需求表 | 不好的小说需求表 |
|---|---|---|
| 信息密度 | 一页内能看清目标、禁区、偏好和开放问题 | 大段解释，读完仍不知道用户真正要什么 |
| 用户原意 | 保留用户原话中的关键意象、题材和情绪 | 把用户想法改写成 Agent 自己喜欢的故事 |
| 边界表达 | 必须保留和必须避免都可检查 | 用“高级”“有质感”“不要俗”这类不可检查表达 |
| 开放问题 | 只留下会影响 proposal 方向的问题 | 把所有细节都推迟，导致 proposal 无法启动 |
| 参考对象 | 写清参考的是结构、风格、题材还是情绪 | 只列作品名，容易导致照搬或误读 |

intake traceability：

| 引用项 | 用途 |
|---|---|
| 原始 idea | 证明需求表没有改写创作起点 |
| 用户确认记录 | 证明创作目标、禁区、参考对象来自用户确认 |
| 参考作品说明 | 证明“参考什么”，并避免照搬 |
| 本 workflow spec | 证明 intake 未越级进入 proposal、PRD 或 HLD |

### 4.3 proposal 交付物：小说构思案

| 项目 | 规格 |
|---|---|
| 交付物名称 | 小说构思案 |
| 建议长度 | 短篇 2-4 页；长篇或系列 4-8 页 |
| 文档形态 | 短章节 + 核心表格 |
| 面向对象 | 人类用户 + PRD writer |
| 核心问题 | 这部小说整体是否成立，是否值得进入指定部分设计 |

小说构思案必须包含：

| 字段 | 内容 | 质量标准 |
|---|---|---|
| logline | 一句话故事 | 能体现主角、冲突、代价或变化 |
| 读者承诺 | 类型、情绪体验、阅读快感、题材边界 | 能指导下游取舍 |
| 核心概念 | 小说最重要的设定或叙事钩子 | 不超过 3 个核心点，且不可替换 |
| 故事结构 | 单篇、分部、分卷、幕结构 | 能解释整部小说的宏观推进 |
| 故事线 | 主线、展开线、隐藏线、情感线、主题线 | 每条线有问题、起点、终点，不写逐场景细节 |
| 主要人物 | 核心角色与关系 | 不做全量人物设计 |
| 世界初设 | 世界基本规则与限制 | 只定义足够支撑构思的内容 |
| 结局方向 | 终局性质和系列钩子 | 明确不可反转项 |
| PRD 建议范围 | 下一步适合设计哪个指定部分 | 范围相对独立 |
| 未决问题 | PRD 或 HLD 必须解决的问题 | 显式列出，不隐含在叙述中 |

好的小说构思案应满足：

| 标准 | 说明 |
|---|---|
| 完整 | 用户能看懂小说整体想写什么 |
| 克制 | 不提前进入 HLD 的全量世界设计 |
| 可拆分 | 能清楚看出哪些部分可进入 PRD |
| 可评审 | 用户能判断结构、故事线、结局方向是否正确 |
| 可约束 | 核心概念与结局方向可成为下游边界 |
| 可追问 | 开放点被显式列出，便于 PRD/HLD 接收 |

proposal rules：

| 规则 | 通过标准 | 拒绝条件 |
|---|---|---|
| 服从 intake | 核心概念、题材、禁区、读者承诺均可追溯到 intake | 改写用户确认过的题材边界或创作目标 |
| intake 边界账本 | `KEEP-*`、`AVOID-*`、`OPEN-*` 均被登记、处理和追踪 | 跳过需求表，直接从旧 PRD/HLD/LLD 生成构思 |
| 整体成立 | logline、结构、故事线、主要人物、结局方向互相支撑 | 只有设定堆叠，没有故事问题、冲突或终局方向 |
| 故事线闭合 | 主线、展开线、隐藏线、情感线、主题线至少有起点和终点 | 故事线只有标签，没有变化路径 |
| 保持克制 | 只定义支撑构思所需的世界初设和核心人物 | 写成全量世界 bible、主干场景表或章节大纲 |
| 明确可冻结项 | 核心概念、读者承诺、结局方向、不可反转项被明确标出 | 下游无法判断哪些内容不可改变 |
| 可拆入 PRD | 至少给出一个相对独立的 PRD 建议范围 | proposal 不能支持指定部分设计 |

proposal references：

| 参照维度 | 好的小说构思案 | 不好的小说构思案 |
|---|---|---|
| 一句话故事 | 主角、目标、冲突、代价或变化一眼可见 | 只有世界设定或气氛，没有故事 |
| 整体结构 | 能看出开端、中段压力、关键转折和终局方向 | 只有章节名或概念列表，没有推进关系 |
| 故事线 | 每条线都有问题、起点、变化和终点 | 主线、情感线、主题线只是标签 |
| 克制度 | 足够支撑评审，不提前写世界 bible | 把 proposal 写成 HLD、PRD、LLD 的混合物 |
| 可拆分性 | 能自然拆出一个相对独立的 PRD 范围 | 整部小说糊成一团，无法进入指定部分设计 |
| 读者承诺 | 类型、情绪和阅读快感清晰 | 只有作者想表达什么，没有读者会读到什么 |

proposal traceability：

| 引用项 | 用途 |
|---|---|
| intake brief | 证明 proposal 服从用户需求和边界 |
| intake boundary ledger | 证明 `KEEP-*`、`AVOID-*`、`OPEN-*` 被逐条处理 |
| 用户确认的必须保留 / 必须避免项 | 形成 proposal 的硬约束 |
| story structure / beat / synopsis 方法论参考 | 支撑整体结构、故事线、结局方向的设计 |
| Snowflake Method 参考 | 支撑由一句话逐层展开的构思方式 |
| proposal 文档版本 | 作为 PRD 的上游冻结来源 |

### 4.4 PRD 交付物：主干场景表

| 项目 | 规格 |
|---|---|
| 交付物名称 | 主干场景表 |
| 建议长度 | 以表格为主；每个主干场景 1 行或 1 个短块 |
| 文档形态 | 线性场景表 + 简短说明 |
| 面向对象 | 人类用户 + HLD writer |
| 核心问题 | 指定部分从开头到结尾如何因果推进 |

PRD 必须包含：

| 字段 | 内容 | 质量标准 |
|---|---|---|
| 指定部分范围 | 本 PRD 覆盖哪一部、哪一卷或哪一篇章 | 边界清楚，可独立验收 |
| 指定部分目标 | 该部分必须完成的故事功能 | 能追溯到 proposal |
| 主干场景列表 | 线性排列的因果节点 | 顺序清晰，不跳跃；每个节点不可缺少 |
| 场景角色 | 每个场景出现或被影响的角色 | 角色功能明确，但不做完整人物档案 |
| 场景环境 | 场景发生的地点或环境类型 | 能支撑 HLD 展开空间系统，但不写完整空间设定 |
| 场景事件 | 场景中发生的核心行动或变化 | 事件可被下游展开，且有因果输出 |
| 冲突与价值变化 | 场景的冲突和状态变化 | 能看出局面如何被改变 |
| 信息变化 | 读者或角色在场景后新增、误判或失去的信息 | 能支撑 HLD 的信息流设计 |
| 关键约束 | 不可改变的情节、结局、人物边界 | 可作为 checking 依据 |
| HLD 展开要求 | 下游必须补全的世界、角色、环境、事件信息 | 不把细节留成隐性假设 |

好的 PRD 应满足：

| 标准 | 说明 |
|---|---|
| 线性可读 | 人类用户能顺着主干场景读完整个指定部分 |
| 简洁清楚 | 不写完整场景 prose，不塞入 LLD 细节 |
| 三要素明确 | 每个主干场景都有角色、环境、事件 |
| 推进明确 | 每个场景都改变局面，而不是只陈列设定 |
| 可冻结 | 通过评审后，可成为 HLD 及之后的最高约束 |
| 可展开 | HLD 能据此补全世界系统，不需要重新发明主干 |

PRD rules：

| 规则 | 通过标准 | 拒绝条件 |
|---|---|---|
| 服从 proposal | 指定部分目标、结局方向、关键角色功能可追溯到 proposal | 修改 proposal 的核心概念、读者承诺或不可反转项 |
| 指定部分独立 | 本 PRD 覆盖范围有明确起点、终点和验收边界 | 范围无限扩张，无法单独设计或验收 |
| 主干因果清晰 | 每个主干场景都有角色、环境、事件、冲突、价值变化、后续作用 | 场景只是设定展示，不能推动下一节点 |
| 线性可读 | 人类能按顺序读出指定部分从开头到结尾的推进 | 场景顺序依赖未写出的隐藏假设 |
| 不越级 | 不写全量世界系统、完整人物档案、具体对白或 prose | PRD 变成 HLD、LLD 或 writing 混合文档 |
| 可冻结 | 关键约束和 HLD 展开要求显式列出 | HLD 不知道哪些内容必须保持不变 |

PRD references：

| 参照维度 | 好的主干场景表 | 不好的主干场景表 |
|---|---|---|
| 线性推进 | 顺着场景读，能看出指定部分如何从起点走到终点 | 场景像素材清单，顺序可随便调换 |
| 因果关系 | 每个场景都有导致下一步的输出 | 场景之间靠“然后又发生”连接 |
| 场景功能 | 每个主干场景都改变人物、局势、信息或关系 | 场景只展示设定、气氛或背景 |
| 颗粒度 | 足够 HLD 展开，但不写具体 prose | 过粗导致不可执行，或过细变成章节草稿 |
| 可冻结性 | 哪些角色功能、结局、事件顺序不可改很清楚 | 下游不知道哪些是建议，哪些是约束 |
| 指定部分独立 | 起点、终点、验收范围清楚 | 必须读完整部小说设计才能判断这部分是否成立 |

PRD traceability：

| 引用项 | 用途 |
|---|---|
| proposal document | 证明 PRD 的指定部分、目标、角色功能和结局方向有上游依据 |
| proposal 冻结项 | 定义 PRD 不得改变的顶层边界 |
| scene / beat / value shift 方法论参考 | 支撑主干场景的因果、冲突和价值变化标准 |
| 用户对 PRD 的评审结论 | 形成 HLD 及之后的冻结依据 |
| 上游重开请求 | 当 PRD 无法服从 proposal 时，作为唯一合法变更通道 |

### 4.5 HLD 交付物：世界观与世界结构文档

| 项目 | 规格 |
|---|---|
| 交付物名称 | 世界观与世界结构文档 |
| 文档形态 | 分章节结构文档 |
| 面向对象 | LLD writer + writing/checking agents |
| 核心问题 | 这个小说世界如何完整运行，并支撑 PRD 主干场景必然成立 |

HLD 必须满足：

| 标准 | 说明 |
|---|---|
| 完整 | 定义所有角色、环境、事件，不只主线可见部分 |
| 受控 | 不改变 PRD 主干场景和 proposal 核心构思 |
| 可展开 | 每个世界结构都能交给 LLD 继续细化 |
| 可追溯 | 关键设计能追溯到 PRD 或 proposal |
| 可检查 | 形成 checking 可使用的世界一致性基准 |
| 可运行 | 角色动机、环境规则、事件因果、信息流彼此咬合 |

HLD 必须包含：

| 字段 | 内容 | 质量标准 |
|---|---|---|
| PRD 支撑矩阵 | 每个主干场景需要哪些世界规则、角色关系、环境状态、背景事件支撑 | 能逐场景追溯 |
| 世界规则 | 社会、技术、制度、超自然或现实规则 | 明确边界和例外 |
| 全量角色系统 | 所有已知角色及其功能、关系、动机、信息权限 | 不只列名字 |
| 全量环境系统 | 所有叙事空间及空间关系、功能、状态变化 | 能支持场景调度 |
| 全量事件系统 | 背景事件、可见事件、隐藏事件、因果链 | 能解释 PRD 中事件为何发生 |
| 风格与视角规范 | 语言风格、POV 权限、叙述距离、信息不对称 | 可供 writing 和 checking 使用 |
| 下游 LLD 任务 | 需要进一步细化的人物、环境、事件、场景清单 | 不把细节遗漏给 writing 临场发明 |

HLD rules：

| 规则 | 通过标准 | 拒绝条件 |
|---|---|---|
| 服从 PRD | 每个世界系统设计都能追溯到 PRD 主干场景或 proposal 核心构思 | 以“世界观更合理”为由改写 PRD 主干 |
| 支撑矩阵完整 | 每个 PRD 主干场景都有对应的规则、角色、环境、事件、信息流支撑 | 某个主干场景需要靠临场解释才能成立 |
| 全量定义 | 所有角色、环境、事件、规则、时间和信息结构均被定义 | 只定义主角和可见场景，隐藏因果留空 |
| 内部一致 | 角色动机、组织规则、环境状态、事件因果互不冲突 | 世界系统自相矛盾或无法支持后续 writing |
| 不越级写作 | 不输出具体章节 prose，不替代 LLD 的细部设计 | HLD 写成正文草稿或场景执行稿 |
| 重开受控 | 发现 PRD 根本问题时只发起上游重开请求 | Agent 直接修改 PRD 或 proposal 冻结项 |

HLD references：

| 参照维度 | 好的世界观与世界结构文档 | 不好的世界观与世界结构文档 |
|---|---|---|
| 支撑性 | 每个世界规则都能解释或强化 PRD 主干场景 | 世界设定漂亮但与主干场景关系松散 |
| 完整性 | 角色、环境、事件、信息流和时间结构互相咬合 | 只写主角设定，背景因果靠临场补 |
| 可运行性 | 人物动机、制度规则、资源限制会自然产生事件 | 世界像百科条目，不会推动故事 |
| 边界感 | 补全 PRD 未展开内容，但不改 PRD | 借世界观展开重写主干场景 |
| 可交给 LLD | 下游能清楚知道哪些对象需要细化 | 只有宏大描述，无法落到人物、环境、事件设计 |
| 可检查性 | checking 能据此判断正文是否违反世界规则 | 规则含糊，任何正文都能解释为合理 |

HLD traceability：

| 引用项 | 用途 |
|---|---|
| PRD document | 证明 HLD 支撑的主干场景来源 |
| proposal document | 证明世界系统没有偏离整部小说的核心构思 |
| PRD 冻结项和评审结论 | 定义 HLD 不得修改的边界 |
| worldbuilding / character profile 方法论参考 | 支撑世界系统、角色系统、环境系统的完整性标准 |
| 上游重开请求记录 | 记录 HLD 发现但不能自行修复的上游问题 |

### 4.6 LLD 交付物：具体设计文档集

| 项目 | 规格 |
|---|---|
| 交付物名称 | 具体设计文档集 |
| 文档形态 | 人物、环境、事件、场景分册或分文件 |
| 面向对象 | writing agents |
| 核心问题 | 写作时具体怎么写才不偏离设计 |

LLD 必须满足：

| 标准 | 说明 |
|---|---|
| 具体 | 人物行为、空间状态、事件因果、场景蓝图可直接用于写作 |
| 全覆盖 | 覆盖 HLD 定义的全部必要人物、环境、事件 |
| 不重写 | 不改变 HLD 世界结构和 PRD 主干场景 |
| 可执行 | writing agent 不需要临场发明关键设定 |
| 可验证 | checking 可逐项对照 LLD 检查正文 |

LLD rules：

| 规则 | 通过标准 | 拒绝条件 |
|---|---|---|
| 服从 HLD | 人物、环境、事件、场景设计均可追溯到 HLD | 修改 HLD 世界规则或 PRD 主干场景 |
| 足够具体 | writing 可以据此写出动作、对话、环境、事件推进 | 仍需 writing 临场发明关键设定 |
| 覆盖完整 | HLD 要求细化的对象都有对应设计 | 遗漏关键角色、环境、事件或场景 |
| 可检查 | 每个具体设计可被 checking 对照正文验证 | 设计只有抽象评价，无法检查执行情况 |

LLD references：

| 参照维度 | 好的具体设计文档集 | 不好的具体设计文档集 |
|---|---|---|
| 可写性 | writing 可以直接据此写动作、对话、感官和事件推进 | 仍停留在“他很复杂”“空间压抑”等抽象评价 |
| 具体度 | 细到行为、状态、触发条件、可见信息 | 只有概念，没有可执行材料 |
| 覆盖度 | HLD 要求细化的对象都有对应设计 | 关键人物或关键场景缺设计 |
| 不重写 | 只细化 HLD，不改变世界规则和主干 | 设计过程中重新发明设定 |
| 可检查 | checking 能逐项对照正文是否执行 | 正文写得怎样都无法判定是否符合 LLD |

LLD traceability：

| 引用项 | 用途 |
|---|---|
| HLD document | 证明具体设计来自世界系统 |
| PRD 冻结项 | 防止 LLD 改写主干场景 |
| HLD 下游 LLD 任务清单 | 证明 LLD 覆盖所有需要细化的对象 |

### 4.7 writing 交付物：描写素材与小说正文

| 项目 | 规格 |
|---|---|
| 交付物名称 | 描写素材 + 小说正文 |
| 文档形态 | 写作素材文件、场景正文、整合稿 |
| 面向对象 | checking agent + 人类读者 |
| 核心问题 | 是否把设计转化成可读小说 |

writing 必须满足：

| 标准 | 说明 |
|---|---|
| 执行设计 | 严格遵守 LLD、HLD、PRD、proposal |
| prose 完整 | 正文是小说，不保留设计注释或说明残留 |
| 视角合规 | 不越过 POV 权限 |
| 风格一致 | 语言风格符合 HLD 规范 |
| 可检查 | 场景、人物、环境、事件能被 checking 回溯 |

writing rules：

| 规则 | 通过标准 | 拒绝条件 |
|---|---|---|
| 执行 LLD | 正文场景、人物行为、环境状态、事件推进可回溯到 LLD | 引入 LLD 未定义的关键设定或关键事件 |
| 遵守上层 | 不违反 HLD 世界规则、PRD 主干场景、proposal 核心构思 | 为了 prose 效果改写冻结项 |
| prose 完整 | 输出为可读小说正文，无设计说明残留 | 正文混入提纲、解释性注释或 Agent 自述 |
| POV 合规 | 叙述信息不超出视角权限 | 角色知道其不应知道的信息 |
| 可被检查 | 正文版本、章节、场景编号清楚 | checking 无法定位文本证据 |

writing references：

| 参照维度 | 好的描写素材与正文 | 不好的描写素材与正文 |
|---|---|---|
| 小说性 | 正文可直接作为小说阅读 | 像设计说明、剧情梗概或 Agent 解说 |
| 执行度 | 人物、环境、事件、视角都能回扣 LLD/HLD | 为了好看擅自发明关键设定 |
| 连续性 | 场景之间情绪、信息、时间和行动连续 | 每场都像独立片段 |
| 风格一致 | 语言风格稳定，符合 HLD 的叙述规范 | 同一段落内风格摇摆 |
| 可检查性 | 场景编号、版本、对应设计清楚 | checking 找不到对应设计或文本位置 |

writing traceability：

| 引用项 | 用途 |
|---|---|
| LLD design documents | 证明正文执行的具体设计来源 |
| HLD 风格与视角规范 | 证明正文语言和 POV 合规 |
| PRD 主干场景表 | 证明正文覆盖指定部分主干 |
| proposal 核心概念和读者承诺 | 证明正文没有偏离作品方向 |

### 4.8 checking 交付物：检查报告

| 项目 | 规格 |
|---|---|
| 交付物名称 | 检查报告 |
| 文档形态 | 问题列表 + 严重性 + 修复建议 |
| 面向对象 | writing agent + 人类用户 |
| 核心问题 | 当前正文是否符合上层设计，是否可进入验收 |

检查报告必须包含：

| 字段 | 内容 |
|---|---|
| 检查范围 | 检查的是哪个正文版本、哪些上层文档 |
| 总体结论 | 可验收、需修订、严重偏离 |
| 问题列表 | 按 P0/P1/P2/P3 排序 |
| 证据位置 | 指向正文和设计文档的具体位置 |
| 修复建议 | 默认修正文稿；必要时标注是否需要上游重开 |
| 残余风险 | 修订后仍可能存在的问题 |

好的检查报告应满足：

| 标准 | 说明 |
|---|---|
| 证据明确 | 每个问题都有文本依据 |
| 分级清楚 | P0/P1/P2/P3 不混用 |
| 默认守上层 | 正文偏离上层时，优先要求正文修复 |
| 可执行 | writing agent 能据此直接修订 |
| 不重写正文 | checking 只报告与建议，不直接替代 writing |

checking rules：

| 规则 | 通过标准 | 拒绝条件 |
|---|---|---|
| 证据优先 | 每个问题都有正文位置和设计文档依据 | 只有主观评价，没有证据 |
| 分级稳定 | P0/P1/P2/P3 按影响范围区分 | 把风格偏好标成核心设定问题 |
| 默认修正文稿 | 正文偏离上层时，优先要求 writing 修订 | checking 擅自改写 proposal、PRD、HLD |
| 重开显式 | 只有上层约束导致下游无法成立时，才提出上游重开请求 | 用重开逃避正文修订 |
| 可执行修复 | 每个问题给出具体修复方向 | writing 无法据报告行动 |

checking references：

| 参照维度 | 好的检查报告 | 不好的检查报告 |
|---|---|---|
| 证据性 | 每个问题都有正文位置和设计依据 | 只有“感觉不顺”“人物不够好” |
| 分级感 | P0/P1/P2/P3 与影响范围匹配 | 把偏好问题当阻塞问题 |
| 可修复 | writing 能据此修改具体文本 | 建议停留在“加强”“优化”“更有张力” |
| 守边界 | 默认修正文稿，必要时才提出上游重开 | checking 直接重写设定或正文 |
| 残余风险 | 明确哪些问题修后仍需观察 | 报告结论过满，不保留风险 |

checking traceability：

| 引用项 | 用途 |
|---|---|
| novel draft 版本 | 明确被检查对象 |
| LLD / HLD / PRD / proposal | 作为一致性和完整性检查依据 |
| checking 严重性定义 | 保证 P0/P1/P2/P3 判定一致 |
| 上游重开规则 | 约束 checking 不得自行改写上游 |

### 4.9 acceptance 交付物：验收记录

| 项目 | 规格 |
|---|---|
| 交付物名称 | 验收记录 |
| 文档形态 | 简短结论 + 备注 |
| 面向对象 | 人类用户 + 项目归档 |
| 核心问题 | 当前阶段是否通过 |

验收记录必须包含：

| 字段 | 内容 |
|---|---|
| 验收对象 | 哪个正文或阶段交付物 |
| 检查报告引用 | 对应 checking report |
| 验收结果 | Accepted / Accepted with notes / Revision required |
| 人类意见 | 用户确认、保留意见或退回原因 |
| 后续动作 | 归档、进入下一部分、回到 writing/checking |

acceptance rules：

| 规则 | 通过标准 | 拒绝条件 |
|---|---|---|
| 结论明确 | 只能使用 Accepted、Accepted with notes、Revision required | 验收结论含糊，无法决定后续动作 |
| 依据完整 | 验收对象、checking report、人类意见齐备 | 没有检查依据或用户意见 |
| 后续可执行 | 明确归档、进入下一部分或回到 writing/checking | 验收后不知道下一步做什么 |
| 保留意见受控 | Accepted with notes 不阻塞当前阶段，但形成后续清单 | 把阻塞问题伪装成备注通过 |

acceptance references：

| 参照维度 | 好的验收记录 | 不好的验收记录 |
|---|---|---|
| 结论清楚 | 一眼知道接受、备注接受还是退回 | 只有“还可以”“再看看” |
| 依据清楚 | 验收对象、检查报告、人类意见齐备 | 不知道验收的是哪个版本 |
| 后续明确 | 下一步动作可直接执行 | 通过后不知道进入归档、下一部分还是修订 |
| 备注受控 | 备注不阻塞当前阶段，阻塞项必须退回 | 把必须修的问题写成备注 |

acceptance traceability：

| 引用项 | 用途 |
|---|---|
| novel draft 或阶段交付物版本 | 明确验收对象 |
| checking report | 证明验收基于检查结果 |
| 用户验收意见 | 证明 acceptance 是人机共同决策 |
| 后续任务记录 | 证明验收结果被正确落地 |

## 5. 人类评审与约束冻结

### 5.1 人类评审边界

| 阶段 | 是否必须人类评审 | 原因 |
|---|---|---|
| intake | 必须 | 需求表需要确认是否准确理解用户意图 |
| proposal | 必须 | 小说整体构思必须由人类确认方向 |
| PRD | 必须 | 主干场景通过后会冻结为下游最高约束 |
| HLD | 可选 | Agent 自主展开；人类可抽查或要求评审 |
| LLD | 可选 | Agent 自主细化；人类通常不逐项审阅 |
| writing | 可选 | 人类可读正文，但正式判断应结合 checking |
| checking | 建议 | 检查报告帮助人类决定是否进入 acceptance |
| acceptance | 必须 | 验收是人机共同决策 |

### 5.2 约束冻结规则

PRD 通过评审后，以下内容冻结：

| 冻结项 | 含义 |
|---|---|
| 小说核心概念 | 下游不得改写小说要表达的核心问题 |
| 指定部分范围 | 下游不得扩大或缩小 PRD 覆盖范围 |
| 主干场景顺序 | 下游不得擅自重排、删除或替换主干场景 |
| 关键角色功能 | 下游不得改变核心角色在主干场景中的功能 |
| 关键环境功能 | 下游不得改变主干环境的叙事用途 |
| 关键结局与约束 | 下游不得反转已确认的结局方向和禁区 |

允许下游展开的内容：

| 可展开项 | 含义 |
|---|---|
| 角色细节 | 外貌、习惯、语言、动机链、关系微结构 |
| 环境细节 | 空间布局、感官、物件、演化状态 |
| 事件细节 | 因果链、触发机制、信息可见性、后果 |
| 场景细节 | 节奏、对话、动作、感官、prose |
| 伏笔与回调 | 在不改变主干的前提下增强结构 |

### 5.3 上游重开规则

如果 HLD、LLD、writing 或 checking 发现 PRD 及之前文档存在根本问题，Agent 不得自行修改上游约束。必须形成“上游重开请求”，交由人类决定。

上游重开请求必须说明：

| 字段 | 内容 |
|---|---|
| 问题来源 | 哪个冻结约束导致下游无法成立 |
| 影响范围 | 影响 HLD、LLD、writing 还是 checking |
| 可选方案 | 修正文稿、局部重开 PRD、回到 proposal |
| Agent 建议 | 推荐方案及理由 |
| 人类决定 | 用户选择后才能执行 |

### 5.4 proposal / PRD / HLD 边界对照

proposal、PRD、HLD 的边界按“整体构思 -> 指定部分主干 -> 世界系统支撑”划分：

| 维度 | proposal | PRD | HLD |
|---|---|---|---|
| 核心问题 | 整部小说是什么，为什么成立 | 指定部分如何线性推进 | 什么世界系统支撑这些推进 |
| 主要读者 | 人类用户 + PRD writer | 人类用户 + HLD writer | LLD / writing / checking agents |
| 文档属性 | 构思契约 | 主干场景契约 | 世界系统契约 |
| 范围 | 整部小说 | 指定部分 | 支撑指定部分及整部构思的完整世界 |
| 粒度 | 宏观结构和故事线 | 主干场景级 | 世界规则、全量人物、环境、事件级 |
| 允许决定 | 类型承诺、核心概念、整体结构、结局方向 | 指定部分范围、主干场景顺序、场景角色/环境/事件/冲突 | 世界规则、关系网络、信息流、背景事件、风格和视角规则 |
| 不允许越界 | 不写主干场景表，不写全量世界 bible | 不改 proposal 核心概念，不写全量世界 bible | 不改 proposal/PRD 冻结项，不写正文 |
| 人类评审重点 | 方向对不对，小说值不值得继续设计 | 主干顺不顺，指定部分能不能冻结 | 通常抽查完整性和追溯性 |
| 下游依赖 | PRD 依赖其整体构思和边界 | HLD 依赖其主干场景和冻结约束 | LLD/writing/checking 依赖其完整世界系统 |

快速判定规则：

| 问题 | 归属 |
|---|---|
| “这本小说到底讲什么、给读者什么体验？” | proposal |
| “第一部从开头到结尾有哪些不可缺少的因果节点？” | PRD |
| “为什么这些节点在这个世界里必然会发生？” | HLD |
| “某个角色在某场戏里具体怎么说、怎么动？” | LLD / writing |
| “正文是否违反上层设计？” | checking |

## 6. 阶段交接契约

| 上游 | 下游 | 交接物 | 下游可依赖内容 |
|---|---|---|---|
| idea | intake | 原始想法 | 灵感方向、用户偏好 |
| intake | proposal | intake brief | 题材边界、创作目标、约束 |

| checking | acceptance | 检查报告 + 修订后正文 | 可验收版本及残余风险 |

本节用于说明 proposal、PRD、HLD 边界定义参考了哪些小说创作方法论。参考资料只用于抽象工作流边界，不作为具体小说内容模板。

| 参考 | 对本工作流的启发 |
|---|---|
| [Reedsy: Story Structure](https://reedsy.com/blog/guide/story-structure/) | 故事结构是组织读者体验的宏观框架，归入 proposal |
| [Reedsy: Three-Act Structure](https://reedsy.com/blog/guide/story-structure/three-act-structure/) | 幕结构适合描述整部小说的宏观推进，不等于主干场景表 |
| [Save the Cat: Beat Sheets](https://savethecat.com/beat-sheets) | 节拍用于控制结构、节奏和角色转变，可影响 proposal 与 PRD 的拆分 |
| [Helping Writers Become Authors: Story Structure Series](https://www.helpingwritersbecomeauthors.com/secrets-story-structure-complete-series/) | 结构节点需要服务冲突、转折和结局，支撑 PRD 的因果场景观 |
| [Advanced Fiction Writing: Snowflake Method](https://www.advancedfictionwriting.com/articles/snowflake-method/) | 从一句话逐层展开，支持“由简入繁、自顶而下”的阶段设计 |
| [Jane Friedman: Novel Synopsis](https://janefriedman.com/how-to-write-a-novel-synopsis/) | synopsis 强调完整呈现核心故事和结局方向，支撑 proposal 的构思契约定位 |
| [MasterClass: Novel Synopsis](https://www.masterclass.com/articles/how-to-write-a-novel-synopsis-step-by-step-guide) | 概要应交代核心人物、冲突和情节走向，但不承担世界 bible 的职责 |
| [Advanced Fiction Writing: Writing the Perfect Scene](https://www.advancedfictionwriting.com/articles/writing-the-perfect-scene/) | 场景需要目标、冲突、结果及后续反应，支撑 PRD 的主干场景字段 |
| [Fictionary: Scene Structure](https://fictionary.co/journal/scene-structure/) | 场景应有明确目的、冲突、转折和价值变化，强化 PRD 的线性推进标准 |
| [Reedsy: Character Profile](https://reedsy.com/blog/character-profile/) | 角色档案属于较细粒度设计，proposal 只保留核心角色，HLD/LLD 再全量展开 |
| [Reedsy: Worldbuilding Guide](https://reedsy.com/blog/worldbuilding-guide/) | 世界构建覆盖地理、历史、社会、技术、权力与资源系统，归入 HLD |

归纳后的边界原则：

| 方法论主题 | 工作流归属 | 原因 |
|---|---|---|
| logline、synopsis、读者承诺、整体结构 | proposal | 用于判断整部小说方向和宏观承诺 |
| beat、scene、turning point、value shift | PRD | 用于判断指定部分是否线性推进 |
| worldbuilding、character system、setting system、continuity bible | HLD | 用于让主干场景在完整世界中成立并可检查 |
