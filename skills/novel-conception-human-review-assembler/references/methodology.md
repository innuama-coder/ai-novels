# 十分钟小说构思人审方法

> 兼容性边界：本文保留 1.x 方法论背景。V2 运行不得读取本文中的 R1/D1
> 文件名或旧 `report_blueprint` 字段；正式机器契约唯一见
> [review-plan-contract.md](review-plan-contract.md)。

## 1. 评审对象不是“摘要”，而是四个作者判断

报告必须帮助作者判断世界、故事、人物和阅读体验，而不是证明 Agent 做了很多工作。机器构思中的 ID、审计结论和派生链只在其能支撑判断时进入主视图，其余留在结构化追溯字段。

## 2. 先定义决定，再设计信息

作者最终只有两个动作：

- `approve`：构思可以进入后续开发；
- `revise`：指出世界、故事、人物或片段中需要调整的部分。

因此每个板块都必须以一个可回答的问题收束，而不是以资料罗列结束。

## 3. 四个板块的最小充分信息

### 世界设定

必须让作者看到：

- 世界是什么、范围在哪里；
- 关键系统如何运行：规则、权限、资源、代价、失败方式；
- 主要环境的辨识特征、基本要素、进入条件/危险、故事功能和状态变化；
- 哪些规则不可突破，哪些接口有意保持开放。

视觉语义采用“系统—环境运行图”：节点表现系统和环境，边表现约束、资源、权限或影响。

### 故事线定义

必须让作者看到：

- 故事承诺、戏剧问题、起点、终点和赌注；
- 主线、支线、背景线各自解决什么问题、由谁推动、在哪里交汇、怎样结束；
- 3–8 个评审阶段组成的时间线，每个阶段表现“压力 → 选择 → 后果/代价 → 新状态”；
- 叙述信息约束、结局性质和仍然开放的后续接口。

视觉语义采用“多线时间线”：横向是阶段，纵向是故事线，交汇点必须可定位到 D1 开发单元。

### 角色定义

必须让作者看到：

- 核心人物的故事职责、表层目标、深层需要、恐惧、价值边界；
- 人物知道什么、不知道什么，受压时如何行动；
- 至少一个能改变局面的自主选择、弧线终点和不可改写项；
- 围绕核心人物的至少三层关系，以及关系在压力下怎样改变。

视觉语义采用“分层关系图”：节点是人物，边带有层级、关系职责、初态、压力和终态。

### 小说片段

片段不是装饰，也不是完整章节。每个片段必须回答一个不同的评审问题，并说明它验证哪些构思对象。默认三类：

1. 开篇或首次有效接触：验证世界与叙述承诺；
2. 关系受压：验证人物能动性和关系变化；
3. 决定性选择或余波：验证代价、结局性质和体验。

片段只能在 D1 明示的创作自由内做局部实现，不得增加新的权威事实。

## 4. 十分钟预算

默认内部估算参数为：

- CJK：400 个字符/分钟；
- 拉丁文本：200 个词/分钟；
- 导航预留：0.5 分钟。

这些数值是版本化的保守产品设计基准。单次报告不得修改；只有完成真实可用性测试、
升级 profile 与技能版本并重跑全部验收后才能校准。内容预算默认分配：

| 区域 | 分钟 |
| --- | ---: |
| 快速定向 | 0.5 |
| 世界 | 1.5 |
| 故事 | 2.5 |
| 人物 | 2.0 |
| 片段 | 2.5 |
| 决定 | 0.5 |
| 导航预留 | 0.5 |

计划阶段按片段最大长度验收；组装阶段按实际字数验收。任何区域都不能通过挤占另一区域来隐藏信息架构问题。

## 5. 八项理解任务

只读最终报告，评审人应能回答：

1. 这部小说是什么、明确不是什么？
2. 哪条世界规则或环境限制真正改变了事件？
3. 主线为何一步步走到结局？
4. 支线与背景线为什么存在、何时与主线交汇？
5. 核心人物主动做了什么，而不是只被情节推动？
6. 关键关系受到什么压力，前后如何改变？
7. 片段体现的视角、信息控制和情绪体验是否符合预期？
8. 结局付出了什么代价，哪些问题仍然开放？

`review_tasks` 必须把这八项任务映射到可见报告元素和来源对象。

## 6. 渐进披露，但不隐瞒关键事实

最终 HTML 可以先显示一句话、图和短句，再允许展开补充说明。但审批所需的规则、因果、人物边界和结局性质必须在默认十分钟路径内可见。不能把关键问题放进附录、悬浮提示或默认折叠的深层区域。

## 7. 完整性账本

`source-inventory.json` 从 R1 绑定的 D1 包中确定性提取所有评审对象。`coverage_ledger` 对每个对象记录：

- 对象属于世界、故事、人物、开发单元还是开放项；
- 它出现在哪些报告元素中；
- 它在文字、图、时间线、关系图或片段任务中承担什么作用。

验证器检查覆盖，不判断文学质量。文学体验由片段技能和作者共同判断。
