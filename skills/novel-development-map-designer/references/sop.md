## 1. G0 硬准入

### G0.1 验证当前状态

1. 读取当前 `run-state`，确认 run 一致、`active_return` 为 `null`。
2. 对 I0–I5、V1、V2 completion packet 运行 harness `validate_stage_completion.py`。
3. 验证 V1 semantic verdict 为 `pass`。
4. 验证 V2 `author-approval.json`：
   - `approval_scope: V2`；
   - `decision: approved`；
   - `record_assurance: self_recorded`；
   - 批准记录绑定当前 V2 HTML 哈希。
5. 验证 I0–I5 completion 与 run-state 中的当前引用一致。

### G0.2 失败处理

任一失败时：

- 不读取聊天或旧稿补齐；
- 不生成候选开发地图；
- 写入只含准入证据和声明失败的 `gate-data.json`；
- 运行验证器自动输出 `blocked-map-report.md`；
- 写明最小缺口、客观证据、唯一拥有者和受影响范围；
- 不创建 `ready` completion。

## 2. M1 控制点与权限建模

### M1.1 只读六份权威设计产物

按 I0→I5 顺序提取：

- 意图：故事承诺、非目标、伦理／主题边界、结局性质、作者授权；
- 主体：不可转移选择、目标、职责、代价、双／多主体协作；
- 世界：能力、资源、权力、信息、限制、验证条件和违规代价；
- 人物：目标、信念、压力行为、关系杠杆、变化与不可越界写法；
- 因果：触发、转折、危机、高潮、结局、余波及节点依赖；
- 叙述：POV、角色知识、读者知识、时间、披露、表达和公平边界。

### M1.2 原子化

为每项会改变开发决策的陈述建立控制点：

```text
一条控制点 = 一个来源 + 一个拥有者 + 一个可判断的要求
```

拆分以下混合句：

- 同时包含两个不同主体责任；
- 同时包含世界规则和人物选择；
- 同时包含事实结局和叙述披露；
- 同时包含已确认内容和开放问题。

不为背景履历、重复解释和不改变选择的装饰信息创建硬控制点。

每条控制点必须引用 `source_artifacts` 中的权威产物，并记录：

- 精确且唯一的 Markdown 标题；
- 逐字存在于该节正文的短证据；
- 短证据的 SHA-256。

`source_artifacts` 本身必须与 I0–I5 completion 的设计产物同路径、同哈希。禁止用手填 `{artifact, section}`、复制件或摘要制造可追溯性。

控制点只保存权威陈述，不另写自由文本“开发作用”。D1 对控制点的组织性解释必须落到单元字段，并在 `derivation_claims` 中绑定字段当前值、来源控制点和理由。

### M1.3 状态分类

- `hard`：下游不得改变；
- `delegated`：已授权自主具体化，但仍须有开发落点；
- `open`：必须维持开放或退回拥有者，不能暗中补写。

### M1.4 建立权限分区

把全部控制点精确投影到 `authority_partition`，并明确：

- 作者锁定：事实与边界不可改变，但允许推演它们的必要后果；
- 明确授权：D1 必须具体化，不应重新询问作者；
- 作者开放：保持问题开放，不得以“完善逻辑”为名裁决；
- D1 自主职责：补齐运行机制、因果桥、对抗、策略、代价、关系、信息和主题检验；
- 下游保留：章节、场景、对白、动作、意象、文风和非结构性实现。

“控制点是 hard”不等于“D1 只能复述”；它表示新增决定必须与该控制点兼容。

## 3. M2 开发缺口审计

### M2.1 从开发者无法回答的问题出发

依次检查故事运行、世界承载、人物职责和跨域关系：

1. 既有关键节点之间缺少什么原因、行动或状态桥梁？
2. 阻力是谁或什么，它为什么持续存在，又会怎样回应人物？
3. 世界规则在机构、资源、权限、验证和失败时怎样实际运行？
4. 人物除根本动机外，会采用什么策略、误判和调整？
5. 关键选择还有哪些真实选项，各自吸引力和代价是什么？
6. 关系如何因行动而变化，而非只在说明中变化？
7. 信息从哪里获得、怎样验证、谁先知道、怎样改变行动？
8. 主题通过什么互有代价的选择得到检验？
9. 配角或团队必须承担什么不可替代功能？
10. 结局需要哪些尚未建立的条件？
11. 世界的历史、空间、制度、资源、伦理和日常如何实际影响人物，而不是只剩一组规则？
12. 除主线外，哪些关系变化、制度冲突或历史因果必须形成支线／背景线，并在何处与主线交汇？
13. 谁实际拥有决定权、传递关键信息、形成关键能力、执行对抗、施加关系压力、完成行动和承担后果？是否仍有职责只落在抽象组织或无名标签上？

只有“不回答就会迫使章节开发临时发明核心逻辑”的问题进入 `development_gaps`。

### M2.2 分配解决权限

- 能在不改变控制点的情况下回答：`autonomous_decision`；
- 不影响核心逻辑、属于具体实现：`downstream_freedom`；
- 明确由作者保持开放：`author_open`；
- 必须改变互相冲突的控制点：不要登记成 gap，直接声明 blocker。

## 4. M3 自主方案与设计决定

### M3.1 生成候选

对每个自主缺口至少提出两个真实方案。候选必须：

- 都能完成所需故事功能；
- 与来源控制点兼容；
- 在人物、世界、因果、叙述或主题上具有不同收益与代价；
- 不是“完整方案”和“明显错误方案”的伪比较。

### M3.2 作出选择

按以下顺序判断：

1. 是否保留作者核心承诺和开放项；
2. 是否增强人物能动性而非作者便利；
3. 是否让世界规则同时提供机会、限制和后果；
4. 是否产生可继续发展的压力与状态变化；
5. 是否减少巧合、便捷技术、无依据授权和事后解释；
6. 是否能在不过早写场景的前提下被下游执行；
7. 是否用最少的新设定解决最多的结构问题。

把选择写入 `design_decisions`，并记录权限依据、必要性、兼容性、影响、可撤销性、投影对象和下游自由。

### M3.3 投影

每项设计决定至少进入：

- 一个功能单元；以及
- 世界、故事、阶段、人物或信息义务中的至少一个。

只存在于方案表、备注或审阅意见中的“决定”不算完成。

## 5. M4 完整构思与最少必要单元

M4 的执行顺序是硬约束，不以本节材料的篇幅或最终报告展示顺序改变：

```text
故事线需求审计
→ 故事线清单与汇流／分叉／交接拓扑
→ 全局主要事件
→ 可选旋律线
→ 逐事件环境需求
→ 世界系统与主要环境
→ 人物职责、人物档案与关系网络
→ 功能单元及跨域闭合
```

不得先建立一组世界地点再把故事塞进去，也不得在故事与环境尚未稳定时补人物名单。

### M4.1 先完成故事线架构与主要事件

先扫描全部权威输入和开发缺口，建立 `story.storyline_demands`。逐项记录：

- 哪项目标、关系、对抗、调查／信息、制度行动、历史因果或余波责任需要持续推进；
- 若不单独处理，会让哪项选择、代价、信息或结局失去因果承担；
- 它应独立成线、并入既有线，还是确有证据地不适用；
- 对应哪些权威控制点、主要事件和设计决定。

故事线数量由需求审计决定，不预设三条，也不以数量越多越完整。只要同一组事件已经能够在一条线内承担同一戏剧问题，就应合并；若目标、承载者、压力升级、信息节奏或闭合条件不同，且会独立改变主干选择、代价、信息或结局，就应分线。

建立 `storylines` 后，用 `storyline_architecture` 明确：

- 哪些线在本书开始时已经独立运行；
- 哪条线是支付本书核心承诺的唯一 `main`；
- 哪些 `precursor` 在主干形成前推进并于何处汇流；
- 哪些 `subplot / background` 在何处分出、碰撞、揭示、同步、交接或重新并入；
- 每个连接点转移了什么目标、信息、责任或压力，连接后形成什么新状态；
- 哪些线在本部闭合，哪些线只完成本部责任后留下系列接口。

多线故事必须有明确连接点；每条非主线都要参与连接并沿连接路径进入主干。连接点必须锚定全局主要事件，不能只写“二线在中段汇合”。

在人物阶段完成后，必须回投影一次“故事线承载闭环”：

- `storylines[].protagonists` 必须全部改为规范人物 ID，不得保留“团队”“两国”“某类人”或人物说明句；
- 每条故事线至少有一名承载人物、一个主要环境和两个主要事件；每个事件—故事线组合至少有一名承担该线的人物在场，唯有明确连接点允许旧线在责任移交事件中由新线人物接手；
- 一条线有多名承载者时，他们必须通过标记为该线的人物关系边形成连通子图；
- 首个事件、连接事件和末个事件必须分别回答“谁使本线进入、谁接走责任、谁完成或保留末态”，不能只写抽象团队、制度或国家；
- 若末态包含同意、授权、拒绝、承诺、核验接受或联合复盘等多方结果，每一方都必须由具体人物行动或已登记且可回看的受控通道实现；只有单方观察到的结果必须写成观察或推断，不得升级为多方决定。

随后完成事件发现与主要事件设计。事件扫描、事件跨度、前提反查、汇总词反查、行动／对抗／状态变化／下一压力以及全局事件唯一事实源，均按下文“主要事件检查表”执行。故事线、事件和连接点必须迭代到彼此一致后，才允许进入世界设计。

### M4.2 在结构完成后设计可选旋律线

只有结构故事线、连接点和主要事件稳定后，才考虑 `story.melody_lines`。旋律线不是支线缩写，也不承担必须完成的故事任务；它只在既有事件上提供可展开、可压缩或可省略的情绪、意象、称谓、日常或认知变奏。

每条旋律线必须：

- 引用三个至七个按因果顺序排列的既有主要事件作为复现锚点；
- 说明每次出现如何发生递进或反转，不能只重复同一象征词；
- 给出可扩展方式和删除整条线后的影响；
- 明确不得承担主因果、结局闭合、新 POV 或决定性信息；
- 明确不能制造新的世界公理、核心人物动机或章节开发必答任务；
- 说明后续系列可以怎样回收，但不得提前裁决作者开放问题。

若删除旋律线会使袭击无法解决、人物终局选择失去原因、读者缺少公平判断所需证据或结局无法成立，它就不是旋律线，必须回到 `storyline_demands` 作为结构故事线处理。若它只有一次出现或只是同一意象反复命名，应交给章节与文风开发，不进入构思地图。

### M4.3 按逐事件需求完善世界信息、运行系统与主要环境

先为每个全局主要事件建立且只建立一条 `world.event_environment_requirements`。逐事件回答：

- 事件发生必须具备什么空间、数字、记忆、制度或社会能力；
- 哪些功能区必须同时或先后可达；
- 哪些资源、权限和信息通道是行动前提；
- 环境以什么风险、阻断和失败方式制造压力；
- 事件是否跨环境，转移人物、信息、资源或权限时需要什么通道；
- 被选择的主要／次要环境为何足以承载事件而没有提供未登记的便捷解法。

环境需求与事件 `environment_ids` 必须完全一致，全部需求共同覆盖全部主要环境。只有完成这张需求台账，才能开始设计世界八域、系统和环境。

再完成世界八域审计：本体与自然、时间与历史、空间与地理、社会与文化、制度与权力、经济与资源、法律伦理规范、日常生活。每域必须说明：

- 这部分世界是什么；
- 它怎样改变人物可知、可做、可失去的内容；
- 哪些内容必须在本书中出现；
- 哪些名称、细节和表现形式留给下游。

再把会实际控制事件的规则组织成 `systems`。每个系统明确行动者、资源、规则、权限、成本、限制、失败方式、故事作用和故事内状态变化。只有说明“存在某项技术／制度”而没有操作条件与后果，不算完成。

随后登记 `environments`。主要环境不是地点名单，而是承载核心行动、持续塑造人物感知，或决定关键许可、资源和风险的环境。每个环境逐一回答：

- 它是什么类型、覆盖什么范围，最鲜明的特征是什么；
- 构成它的基本要素、感知条件、进入者和访问限制是什么；
- 有哪些资源与设施，人物可以做什么、不能做什么；
- 危险、压力和失效条件怎样作用于人物与事件；
- 它服务哪些故事线和开发单元，随故事发生什么状态变化；
- 它有哪些有边界的物理、数字、记忆或权限功能区；人物、资源和初始状态分别位于哪里；
- 功能区通过什么通道连接，进入条件是什么，连接被阻断会造成什么后果；
- 对每个登记单元，哪些人物在哪些功能区行动，进入状态、可做／不可做、环境压力和离开状态分别是什么；
- 哪些名称、布局、装饰、天气、具体移动和场景调度留给下游。

`event_hosting` 必须与该环境的 `unit_ids` 一一对应；事件人物必须是规范人物档案且承担该单元，人物必须实际位于事件使用的至少一个功能区。无人设备区、隔离危险区或当前不可进入区允许没有人物，但仍须说明资源、状态和连接后果。多功能区环境必须给出连通路径且不能留下孤区。单房间可以只有一个功能区；数字、记忆和制度环境可使用逻辑区或权限区，但仍必须是人物与事件可以进入、受限并改变状态的场域，不能把工作流程、规则清单或信息生命周期改名为环境。

主要环境必须合计覆盖全部开发单元；偶发地点和不改变选择的布景不强制登记。不要锁定房间尺寸、装饰、镜头、逐拍动作或正文表现。

#### 主要事件检查表（供 M4.1 执行）

只按戏剧功能分线，不按 POV、地点或人物名单机械分线：

- `main`：支付本书核心承诺，恰好一条；
- `precursor`：主干形成前独立推进、随后汇流的前置线，按实际需要建立；
- `subplot`：承担关系、人物弧、制度冲突或主题压力，按实际需要建立；
- `background`：把过去事件、世界演变或不可见力量转成当前压力和逐步揭示，按实际需要建立。

先做事件发现，后做事件设计：

1. 逐份扫描 I0–I5 权威成果，至少提取因果节点及其前提、叙述契约要求在开篇／结尾呈现的事实、人物状态转变、世界状态变化、信息取得与验证、批准／拒绝／承诺、救援／控制／关停等行动步骤；
2. 在 `story.event_source_coverage` 中逐项保留原文摘录、来源位置、候选类型与处置。除真正不发生变化的静态背景外，候选必须进入一个或多个主要事件；
3. 用 `story.event_span` 明确本书最早因果变化、开篇事件、主行动入口、最终余波。主角登场、数字生命启动或核心危机出现都不自动等于故事起点；
4. 进行“前提反查”：逐个检查所有事件的 `preconditions`，凡其中包含本书会呈现、会核验、会造成角色／资源／权限／目标变化的先前行为或结果，必须向前追溯为独立事件，不能只留在前提句；
5. 进行“汇总词反查”：出现“前序铺垫”“危机升级”“证据会合”“团队行动”“方案获批”“任务建立”等汇总表述时，逐项判断内部步骤是否各自改变人物、信息、资源、权限、目标或不可逆状态；若改变，拆成主要事件。

完成扫描后建立全局 `story.major_events`，再让各线按因果顺序引用事件 ID。主要事件不是章节标题，也不是“关系变化”“危机升级”之类抽象功能，而是故事世界中确实发生、能被人物经历或被证据确认的变化。一个事件只承担同一时空压力下的一项主导状态变化；多个动作可以同属一个事件，但死亡、失败尝试、任务批准与接受、救援、证词、硬件控制、授权核验等若分别改变可用条件，就不得合并。每个事件必须回答：在什么前提下，谁在什么主要环境发起何种行动；什么力量回应或使其复杂化；发生了什么不可撤回的决定性变化；直接结果、前后状态、信息变化和下一压力是什么；它由哪些更早事件造成。事件必须显式登记发起行动者与对抗行动者，并让其规范姓名出现在相应行动文本中；承担 `opposition_execution` 需求的人物必须至少真正反制一次。事件必须绑定实际开发单元、规范人物和该单元的 `event_hosting` 环境，不得凭空添加人、地点或能力。

每次新增、删除或改写主要事件后，不得只修事件表。必须从事件事实源重新投影并核对阶段进入／退出条件、开发单元、故事线、人物需求与行动、关系变化、环境承载、信息状态、系统覆盖、权限链和来源覆盖，直到所有投影对同一因果事实给出一致答案。

在允许进入世界设计前，再执行五项交叉门。它们检查的是实际故事需要，不要求每部小说机械拥有反派、亲属线、双高潮或精确日历；不适用时必须写出与权威输入和当前结构相容的理由，不能为过门而增造内容：

1. **核心承诺结构证明**：对每条作者锁定的核心承诺，指出至少一个不可省略主要事件，能看见“既有材料／默认策略 → 当前压力 → 人物重新判断或选择 → 可观察后果”。旋律线、人物简介和主题说明不能成为唯一证据。若主题声称人物形成新的价值、身份或世界观，仅有新感情、新称谓或旁白结论不够；
2. **线路实质性**：每条 `subplot` 必须至少改变一次主干所需的选择、代价、信息、资源、权限、关系状态或结局条件。只在问句中声称“可能有风险”、从未进入事件状态变化的线路，应补成可观察后果，或并入其他线路／世界信息；这不要求公开上游明确保持开放的责任真相；
3. **对抗适应**：当主角策略、行动入口或关闭方案已被对抗方感知时，检查对抗是否至少产生一次升级、转向、反制或有因果的退出／失能。不能让前段有能力的对抗方在后半程无解释停止行动；没有人格化对手的故事可用制度、环境或信息限制的状态变化完成此项；
4. **闭合条件一致性**：把高潮／结局所需的每项条件逐项对齐 `world.systems` 输入与失败方式、主要事件前提与结果、人物能力／权限和证据来源。某条信息若只提供查找入口，就不能在另一处被写成充分关闭条件；某系统若声称若干输入已足够，就不能在高潮临时增加无前置的唯一钥匙；
5. **时间与高潮层级**：为长期关系形成、倒计时、调查／救援／核验和余波给出足以检查真实性的近似跨度、先后和并发关系，但不预写章节日历。若外部行动胜负与核心人物不可逆选择不是同一件事，明确两者的先后与各自状态变化，避免动作高潮吞掉主题高潮；二者确为同一事件时说明理由即可。

五项交叉门的结论必须进入 `thematic_testing`、`opposition_adaptation`、`easy_solution`、`forward_causality` 或 `downstream_sufficiency` 的实际反证过程，并在对应事件、阶段、故事线和世界系统中完成修正；不能只在检查文字中宣称通过。

世界运行系统必须写成“输入条件 → 转换规则 → 可观察输出”，并显式列出所覆盖的环境与主要事件。系统集合必须覆盖全部主要环境和主要事件；任何关键技术、制度或超自然能力若只写名称、不说明生效前提、处理过程、可核验结果与失败方式，均视为尚未完成。

同一交汇事件只在全局事件表定义一次，由连接点涉及的多条线共同引用。每条线必须有承载者、核心问题、起点、驱动力、升级、主要事件序列、结局状态和闭合方式；主线至少三个事件，其他线至少两个。每条线除首个事件外，后续事件必须引用该线更早的事件作为因果前驱；首末承载单元必须进入事件序列。只提供背景说明、从不通过连接点改变主干选择、代价、信息或结局的“线”应删除或并入世界信息。

### M4.4 最后发现人物需求并补齐核心人物三层关系图

只有故事线、主要事件、逐事件环境需求、世界系统和主要环境稳定后，才执行人物需求扫描。每项人物职责必须回指实际故事线、事件、环境或功能单元；不得为了人物关系层数反向虚构无故事职责的人物。

在画关系图之前建立 `characters.demand_register`。必须逐项扫描：

1. `decision_authority`：谁能作出不可替代的批准、拒绝、承诺或终局选择；
2. `information_transfer`：谁取得、筛选、传递、核验或截断关键情报；
3. `expertise_formation`：谁使核心人物获得关键知识、能力、方法或学术立场；
4. `opposition_execution`：谁实际执行阻拦、追捕、审查、反制或合法拒绝；
5. `relationship_pressure`：谁以共同历史、爱、亏欠、身份或价值冲突改变选择成本；
6. `operational_execution`：谁把命令或信息转成不可由一句话自动完成的现实行动；
7. `aftermath_responsibility`：谁在高潮后承担记录、审判、照料、治理、复原或持续代价。

每项写清触发、故事职责、遗漏后果、重要度、来源对象和处置。结构性或支持性需求必须解析到具体人物档案；只有确实不参与本故事运行的语境项，才可用 `contextual + not_applicable`，并保留可审计理由。一个人物可以承担多项需求，但每项需求必须在其 `demand_ids` 中反向登记。抽象组织、项目、制度或“团队”不能作为处置结果。

人物档案完成后再做一次关系反查：

- 凡两名人物在同一主要事件中直接完成交接、承诺、拒绝、救援、胁迫、告别或关系状态变化，必须判断是否需要直接人物关系边；不能因为两人可经第三人连通就省略现实中的直接关系；
- 每条关系的 `storyline_ids` 必须覆盖它实际改变选择、代价、信息或末态的全部故事线，人物档案也必须反向承担这些线；
- 环境文字中出现的具体人物必须被明确区分为实际进入者、远程受控参与者或外部权利／风险边界。外部权利人不得写成已经进入功能区、获得记录或知道项目；远程参与者必须有环境通道和权限记录。

围绕每个核心人物建立人物—人物关系图，并按最短路径距离展开：

1. 第 1 层：与核心人物直接相连的人物；
2. 第 2 层：至少通过一个第 1 层人物才能抵达的人物；
3. 第 3 层：至少通过一个第 2 层人物才能抵达的人物。

先建立一个全局人物图：`characters.profiles` 只保存人物定义，`characters.relationships` 只保存人物之间的关系边。每个人物只定义一次；人物目标、需要、边界和行动选择不得复制到关系边。每个无向人物对只允许一条边，边的两端必须引用规范人物档案。完成全局图后，由验证器从每个核心人物执行最短路径计算并派生第 1、2、3 层；不得保存 `relationship_layers`、`via_character_id` 或人工层号。这样同一配角服务多个核心人物时仍只有一份事实，三层关系不会因重复投影而互相矛盾。

机构、项目、群体、制度和历史只能作为世界系统、环境压力或人物所代表的力量，不能计算为人物层级。需要制度压力时，应定义实际作出选择、执行规则或承担后果的具体人物。核心与支持人物必须完成命名：上游已给姓名时用 `confirmed`，在授权范围内补出的姓名用 `autonomous`；“某领导、某老师、接头人、专家、队长”等只说明功能，不能作为完成姓名。只有无结构职责的语境性外围人物可以用 `functional`。三层表示真实人物网络的图距离，不表示关系主题、亲疏类别或影响机制。

### M4.4 从因果变化出发

以 I4 因果节点为骨架，不按章节号拆分。每个候选单元回答：

1. 开始前什么已成立？
2. 谁在什么压力下追求什么？
3. 什么具体阻碍这个目标，它会怎样适应前序行动？
4. 人物有哪些真实选项，各自吸引力和代价是什么？
5. 谁作出什么不可替代的选择，放弃了什么？
6. 人物、关系、局势、价值或知识发生什么变化？
7. 该后果制造了什么下一压力？
8. 这个末态为哪个后续选择提供前提？

无法回答选择、代价、变化或下一压力的候选通常不是独立功能单元。

### M4.5 合并

合并满足任一条件的候选：

- 只重复已有信息；
- 没有独立状态变化；
- 只能与相邻单元共同完成同一个选择；
- 删除后没有任何控制点失去承载；
- 只是实现细节、过场或说明。

### M4.6 拆分

仅当一个候选同时包含无法由同一 POV、同一知识状态或同一因果阶段承载的变化时拆分。不要因为地点变化、章节习惯或字数偏好自动拆分。

### M4.7 行动与反应

检查重要后果是否得到人物反应、困境或新决定。反应可以：

- 与行动合并；
- 成为独立单元；
- 由下一单元前置状态吸收。

选择能保留因果真实性的最少方案，不强制 Scene/Sequel 格式。

## 6. M5 依赖与信息设计

### M3.1 依赖图

为每个单元列出不可替代的前置单元：

- 事实依赖；
- 人物认识依赖；
- 关系变化依赖；
- 权限／资源依赖；
- 读者理解依赖。

排序必须满足：

- 依赖只指向更早单元；
- 无循环；
- 终局可以反向追溯到触发与关键选择；
- 删除任一关键单元都会产生可指出的缺口。

### M3.2 人物能动性

对每个关键结果追问：

- 谁选择了它？
- 该选择是否由已确认动机和压力行为解释？
- 辅助角色、巧合、技术或机构是否替代了核心主体？
- 角色越界时，是否存在已确认阈值与代价？

无法归因时，先检查 D1 是否漏单元；若上游缺少选择逻辑，阻塞并回到 I1、I3 或 I4。

### M3.3 世界与权限

每次关键行动必须绑定：

- 可用资源；
- 信息来源；
- 行动权限；
- 验证条件；
- 规则代价。

不得在地图中新增便捷能力、未建立的资源或临时授权。

### M3.4 信息责任

先为每个需要跨单元管理的重要信息建立 `information_obligations` 稳定 ID、来源控制点、受众、知识持有者与处理期限，再在单元中按以下状态引用其 ID：

- `establish`：本单元必须让角色或读者获得；
- `hint`：只允许形成怀疑；
- `withhold`：因 POV／公平悬念暂不可知；
- `payoff`：兑现先前建立或暗示的内容。

检查：

1. 每个 payoff 都有更早 hint／establish；
2. `within_book` 义务必须在本部更晚单元 payoff；
3. `series` 义务必须有明确系列接口和登记为 `series` 的终点；
4. POV 人物只能知道其感知、输入、推断与授权允许的信息；
5. 不能用可靠叙述撒谎制造反转；
6. 开放项不能被信息安排偷偷裁决。

`audience` 明确区分读者、当前 POV 人物、故事内其他人物或混合受众。面向具体故事人物时，用 `knowledge_holder_controls` 引用能够证明其知情资格的既有控制点；不得只在自由文本里含混写“他们知道”。

四组信息数组可以为空；世界约束和禁止项确实不适用时也可以为空。不要为了满足字段而制造不存在的建立、规则或禁令，语义验收负责判断关键行动是否因此失去依据。

### M3.6 终点线

找出依赖图中所有没有下游单元的 graph terminal，为每个终点登记一条 `terminal_threads`：

- `main`：主故事承诺完成的位置，至少一条；
- `subplot`：独立副线责任完成的位置；
- `series`：本部完成但保留系列接口的位置。

登记集合必须与全部 graph terminal 完全一致。不得假定所有小说恰好一个最终单元。

## 5. D1 生成交付

### D1.1 先生成模型

先用 `manage_generation.py begin` 建立绑定当前 `CODEX_THREAD_ID` 和 input gate 的新工作区。再严格提交 `control-model`、`gap-and-options`、`story-architecture`、`event-world-model`、`character-model`、`final-map`；不能跳步、换任务或在会话外先准备完整 final map 后倒填阶段。顺序必须是权限分区 → 缺口与方案 → 故事线需求、故事线拓扑和主要事件 → 逐事件环境需求、世界八域、系统与主要环境 → 七类人物职责、规范人物档案和三层人物关系 → 功能单元、依赖、信息及最终闭合。

为所有业务派生字段建立统一 `derivation_claims`：以 `subject_type + subject_id + field` 标识主体字段，写明来源控制点、来源设计决定和理由，并以规范 JSON 值的 SHA-256 绑定当前值。覆盖控制点分类、功能单元、信息义务、开放项和终点线程；审核性说明（coverage/semantic evidence）不冒充故事事实。新增的对抗、选项、选择代价、后果和下一压力必须引用已投影的设计决定。POV、因果节点、世界限制和禁止项直接引用控制点 ID，不另造标签。

### D1.2 生成业务文档

运行：

```powershell
python scripts/render_development_map.py <package-directory>
```

确定性生成：

1. `development-map.md`：按拓扑顺序展示单元、终点线及开发授权；
2. `coverage-matrix.md`：逐控制点展示精确来源、承载和客观证据；
3. `map-check.md`：由验证器记录结构化检查、交接自测证据和实际 verdict。

三份文档不得手写。模型变化后必须重新渲染前两份、再由验证器重建检查报告。

### D1.3 禁止内容

- 连续正文；
- 示例对白；
- 动作／镜头清单；
- 感官样本；
- 未确认的章节数、字数和固定节拍；
- 改写作者主题、人物根本动机、世界公理、事件真相或结局；
- 没有缺口、备选、权限依据和影响投影的任意新增内容。

## 6. A1 确定性验收

运行：

```powershell
python scripts/validate_development_map.py <package-directory> --write-validation
```

脚本检查：

- 哈希和批准；
- 六份来源是否与 completion 权威产物同路径、同哈希；
- 控制点的精确节、逐字证据和证据哈希；
- 权限分区是否与控制点 hardness 完全一致；
- 缺口是否全部分类且具有合法去向；
- 自主决定是否具有真实备选、唯一选择、权限与兼容性说明；
- 决定与缺口、单元和完整构思的双向投影；
- 顶层字段、枚举和唯一 ID；
- 六区控制点；
- 单元的目标、适应性阻力、选项、选择成本、后果和下一压力；
- POV、因果、世界和禁止项是否引用正确 area 的权威控制点；
- 每个业务派生字段是否有唯一且匹配当前值的来源声明；
- 状态变化；
- 依赖有效、顺序正确且无环；
- 所有图终点及主／副／系列终点登记；
- hard/delegated 100% 覆盖；
- open 项合法处理；
- 孤立单元；
- 地图和覆盖矩阵是否为当前模型的确定性渲染，检查报告是否来自当前权威验证；
- 信息义务是否明确受众与知识持有者、先铺设后回收，系列义务是否存在有效系列接口；
- 十三项结构化压力测试和八任务开发交接自测记录；
- 声明 blocker。
- 生成会话任务 ID、六阶段顺序、阶段文件哈希、链头和最终模型绑定；故事阶段必须投影最终故事，事件—世界阶段必须投影最终故事与世界，人物阶段必须投影最终三域构思；
- 占位语及同组对象的高相似模板复述。

脚本验证结构化证据确实指向有效控制点和单元，并阻止明显占位与批量模板；它仍不能证明执行者绝对诚实或单独裁决文学价值，R1 必须在不同 Codex 任务中独立复核。

## 9. A2 语义压力测试

在 `map-data.json.semantic_checks` 中逐项记录执行者、角色、方法、检查对象与结构化反证断言。每条断言必须写明测试、失败条件、尝试的反例、结论和 `failure_found`，并用 `field_evidence` 绑定当前单元的必要字段及值哈希。不能只写 `pass`，也不能用数量统计或与绑定字段无关的文字冒充语义检查；一旦发现失败，就不能保留 pass。`map-check.md` 由验证器根据实际检查结果生成：

### A2.1 缺口闭合

逐条说明为什么它是真缺口、为什么归 D1／下游／作者，以及自主决定是否真正回答了问题。

### A2.2 因果正向回放

从触发开始，逐单元检查：

```text
前置成立 → 目标受到阻力 → 人物选择 → 状态变化 → 下一前置
```

出现“然后又发生”但没有因果转换时为失败。

### A2.3 结局反向追溯

从最终单元反向追问每个结果需要什么前提，直到开端。任何无法回到已建立选择、规则或关系的结果为失败。

### A2.4 人物弧与能动性

为每个核心人物检查：

- 起始默认策略；
- 压力下重复或升级的策略；
- 越界／变化阈值；
- 关键选择；
- 选择后的代价与末态。

地图不能只覆盖角色“出现”，必须覆盖其选择逻辑。

### A2.5 对抗、选择与便捷解法

对每个重要单元检查：

- 对抗力量是否有自己的目标、筹码和适应方式；
- 人物是否面对至少两个真实选项；
- 被选择方案是否支付实际代价或放弃价值；
- 是否存在更简单、更安全、更快的解决方案；
- 若存在，世界规则、人物价值、信息限制或机会成本是否可信地阻断它。
- 主角方案暴露或首次接近成功后，对抗方是否适应、被可信地解除能力，或由制度／环境阻力完成等价升级；
- 高潮闭合所需条件是否在世界系统、事件链、人物权限和证据来源中给出同一答案。

### A2.6 世界、信息与叙述

检查 POV、读者知识、角色知识、披露时点、铺设与回收，没有越权或不公平隐瞒。

### A2.7 主题行动检验

检查主题是否由不同价值立场、人物选择和后果进行检验。每条核心承诺至少需要一项不可省略的主要事件证明；可选旋律、人物简介、称谓或旁白结论不能成为唯一证据。若主题涉及新身份、新价值或新世界观，必须能看见它与继承材料／默认策略的区别以及可观察后果。只有抽象主题说明而没有行动代价为失败；不要求故事给出单一正确答案。

### A2.8 最少必要性与下游充分性

对每个单元执行删除测试：

- 删除后若没有控制点、因果、人物弧或信息义务受损，应合并或删除；
- 若两个相邻单元状态变化相同且没有独立选择，应合并；
- 若一个单元承担互相冲突的 POV／知识状态，应拆分。
- 若删除一条设计决定没有任何构思对象或单元受损，该决定是装饰；
- 若章节开发仍需临时发明核心动机、规则、阻力或主线因果，构思尚不充分；
- 若已经规定章节、场景、对白或正文表达，D1 越过了下游边界。
- 若一条独立支线只有假设性风险、从未改变主干状态，应落实后果或合并，不得用线路数量冒充完整性；
- 若长期关系、行动倒计时或核验流程没有足以判断真实性的近似时间尺度，仍属下游必须补造的结构缺口；
- 若外部行动高潮与人物不可逆选择相互独立却没有明确先后与各自结果，应补足高潮层级。

## 10. A3 开发交接自测

地图设计者仅以当前 D1 交付作为回答证据，按下游开发者视角完成：

1. `promise`：复述故事承诺、主角选择、结局性质和不可违反项；
2. `autonomous_value`：指出 D1 相对访谈骨架新增了哪些关键设计以及它们解决什么；
3. `causal_chain`：复述主因果链、关键反制及每阶段变化；
4. `unit_contract`：指出任一单元的目标、选项、成本、POV、可透露信息与末态；
5. `freedom_boundary`：区分该单元可自由创造与必须回问的内容；
6. `drift_detection`：给出两个偏航写法并说明违反哪条控制点或设计决定；
7. `easy_solution`：提出最危险的便捷解法并说明构思如何可信阻断；
8. `scene_plan`：为任一单元生成场景计划，不猜测结构性决定。

若回答依赖聊天、旧稿、常识补全或互相矛盾，则 verdict 不能为 `ready`。

将结果写入顶层 `handoff_self_test`，要求：

- 执行者角色为 `map_designer`，`assurance` 固定为 `self_test`；
- `evidence_scope` 为 `d1_package_only`；这只约束证据来源，不声称设计者没有接触过上游；
- 八项任务 ID 恰好是 `promise`、`autonomous_value`、`causal_chain`、`unit_contract`、`freedom_boundary`、`drift_detection`、`easy_solution`、`scene_plan`；
- 每项保存足以显示真实理解的回答和具体证据 ID。

不能只写“已检查”，也不能把该记录描述为独立证据。R1 由不同执行角色仅凭当前 D1 包重新执行这八项任务，才构成独立交接验收。

## 9. Verdict 与回退

### `ready`

- A1 全部通过；
- A2 每项有客观证据；
- A3 八项任务均可完成；
- `declared_blockers` 为空；
- `map-data.json`、三份 Markdown 和 `validation.json` 一致；
- 正式受控会话生成并验证 `generation-session.json` 与阶段证据；入口不接收会话外候选模型；
- 正式入口生成并验证 `execution-record.json`，绑定当前技能、阶段链、最终模型、输入门、执行者和任务 ID；
- 验证器生成 `package-manifest.json`，完整绑定执行包；
- 由 `execute_autonomous.py` 调用 completion 生成器；
- 只有生成器构造的候选 completion 通过主 harness 后才写入正式文件，其 `design_artifact` 指向该 manifest。

### `revise`

上游成立，但 D1 存在漏覆盖、字段缺失、依赖错误、单元冗余、信息错位或文档不一致。只修订 D1，重跑 A1–A3。

### `blocked`

准入失败，或必须改变上游控制点才能使地图成立。输出唯一回退包：

| 问题 | 拥有者 |
| --- | --- |
| 故事承诺、范围、伦理、结局性质 | I0 |
| 核心主体、不可转移选择、职责 | I1 |
| 规则、资源、权限、信息通道 | I2 |
| 动机、压力行为、关系与变化阈值 | I3 |
| 事件顺序、因果、危机、高潮、结局 | I4 |
| POV、读者知识、时间与公平披露 | I5 |

不得在 D1 发起创作访谈或自行补写答案。

## 14. 稳定质量回归

每次修改技能或模型后，至少用一个不含当前小说专名的合格样例和下列反例回归：

1. 多条故事线只替换标题、核心问题与升级逻辑相同；
2. 多个主要环境的状态变化相同；
3. 不同人物复制同一组行动选择，导致能力与权限不可区分；
4. 四个以上开发单元复用同一前提、对抗和结果模板；
5. 三层关系复用同一历史、冲突、筹码和变化；
6. 八项交接自测复用同一回答。

合格样例必须保留共同故事前提，同时让各对象在功能、压力、选择、状态变化和下游责任上可区分。测试不得硬编码某一部小说的角色、事件或结局。
