# 小说访谈简报生成

生成一个**三部分审阅界面**，不是新的小说设计文档。目标不是覆盖所有访谈记录，而是让作者在一页中判断：世界规则是否成立、故事如何必然发展、人物选择是否可信。

开始前读取 [brief-design.md](references/brief-design.md) 和 [review-brief-template.html](assets/review-brief-template.html)。模板提供信息密度、可访问性和三部分结构基线；替换所有 `{{...}}` 占位符，不能把它们留在交付物中。

## 准入与定位

只由 harness V2 调用：六个 I-stage completion packet 与 V1 completion packet 必须均为 `ready`，且 `interview-integrity-report.md` verdict 为 `ready`。内容仅来自 `intent-card.md`、`subject-definition.md`、`world-operating-contract.md`、`core-character-design.md`、`causal-storyline.md`、`narrative-contract.md`；六份设计产物是生成简报的**唯一内容输入**；完整性审计只决定准入，不补内容。

不得把已有 `*-interview-review-brief.html`、`novel-design-brief.md`、`development-map.md`、`coverage-matrix.md`、`map-check.md`、构思审阅、旧 HTML 或聊天摘要作为内容基线，更不得复制它们的版式。它们只可用于发现版本已过期；若六份唯一输入与其冲突，以六份输入为准。

将它放在 `novel-narrative-contract-designer` 之后、`novel-development-map-designer` 之前。它不发起访谈、不裁决开放项、不改变上游状态，也不替代作者确认。

若有输入缺失、不是 `ready`、版本冲突或关键事实无法追溯，输出 `interview-brief-blocked.md`：列出最小缺口、责任 skill、受影响板块。不要从聊天记录、旧稿或下游材料补全。

## 信息选择规则

每项信息都要保留来源和状态：`confirmed`、`delegated`、`provisional`、`open` 或 `blocked`。只提取会控制后续开发的内容：定义、目标、职责、边界、约束、关键选择、状态变化、信息责任与开放项。

一条内容只有同时满足下列至少一项才可上板：改变角色选择、限制因果、规定读者信息、定义能力/权限、规定结局或构成作者必须确认的开放项。背景履历、重复解释、技术名词和未锁定细节一律省略或收进简短脚注。

## 通用信息契约

把这份简报视为小说构思的通用审查面板，而不是任何单一项目的复述。只从输入材料抽取信息；不得把既有项目、示例人物、题材、技术设定或既往 HTML 的内容当作默认字段或判断前提。

三个板块各自回答一个通用问题：

| 板块 | 必须回答的问题 | 最小信息单元 |
| --- | --- | --- |
| 世界设定 | 什么规则、资源、权力或环境条件改变人物的可选行动？ | 前提；限制与代价；权力/责任；外部压力；范围边界 |
| 故事线设定 | 谁在什么压力下作何选择，选择如何改变下一局面？ | 作品承诺；触发；关键选择；代价；转折；结局/余波；信息呈现约束 |
| 人物设定 | 人物为何这样选择，并会在压力下如何变化或坚持？ | 结构角色；目标；价值/信念；能力与边界；受压策略；变化；关键关系 |

信息只需深入到能改变后续创作决定的程度。若材料不足，明确标为“待确认”并提出一条精确的评审问题；不得用通用套路、世界百科、人物履历或虚构细节填满空位。主题、意图、视角和信息披露不增加第四板块：把它们分别放进最能约束创作决定的世界、故事线或人物单元。

## 输出

输出到项目构思文档目录，默认命名为 `<project>-interview-review-brief.html`。生成**单文件、可离线打开**的 HTML：内联 CSS 和最少必要 JavaScript；不依赖 CDN、远程字体、图像、图表库或网络请求。

除页首状态/来源页脚外，正文**只允许下列三个部分**；不得再附加总览、信息台账、风险清单或独立审阅清单作为第四部分。评审提示须嵌入三个板块各自的底部。

三个可见一级板块标题必须分别以 `1. 小说世界设定`、`2. 小说故事线设定`、`3. 小说人物设定` 开头；可在破折号后追加一个简短评审问题，但不能改用仅含修辞性的标题。

### 1. 小说世界设定：运行边界图

回答“在什么规则下故事才成立”。使用一个中心对象/主体与三到五个环绕约束的关系图，而不是百科卡片：

- **中心**：故事中最能改变人物选择的关键存在、行动场域或制度；不得预设题材、技术、人物或冲突类型。
- **环绕块**：时间与外部压力、能力/信息通道、权限与不可越界行为、行动验证条件、主题伦理禁区；
- **每块**固定为：`定义 → 作用/职责 → 不能越过的边界`，每项最多一短句；
- **视觉语义**：实线表示已确认限制；虚线只表示开放接口，必须标明“开放”；颜色之外必须有文字标签和线型；
- **评审提示**：在本板底部列出三至五项“开发不得改变”的约束与最多两项开放项。

### 2. 小说故事线设定：因果主轨

回答“为何会走到这个结局”。以因果故事线为唯一骨架，压缩成四至六个阶段节点，而不是复制全部节点表：

- **每节点**只呈现：`压力/前提 → 谁的选择 → 代价或反转 → 新状态`；
- **主轨**：用连续实线箭头连接已确认因果；每个节点具有可见编号、阶段名和一行结论；
- **真实多线**：仅在上游明确存在并行主线时使用泳道。标出共同时间窗、汇合点和停止点；汇合后明确只剩哪条主线；
- **记忆/历史材料**：默认是当前节点的虚线注释，绝不单独画成故事线，除非上游明确为并行线；
- **结局**：用终点卡同时写明“已实现结果”和“仍未解决的后果/开放接口”；
- **评审提示**：嵌入一行问题：“若删去任一节点，后续哪个选择失去前提？”

### 3. 小说人物设定：选择关系图

回答“谁在什么压力下承担什么选择”。只展示核心人物；默认使用两张主卡与一条关系杠杆，不扩写人物小传：

- **每张人物卡**固定四格：`定义`、`目标`、`职责`、`边界`；可另加一条“压力触发 → 关键选择”；
- **关系桥**：只写双方之间改变主线的欲求、误读、资源或责任，不以爱情/关系标签替代因果；
- **角色状态**：用明确的 `confirmed` / `delegated` / `open` 标签显示来源，不能把授权 Agent 的细化当成作者确认；
- **评审提示**：嵌入一行“该角色在压力下不能被写成什么”。

## 绘制与无障碍规则

1. 先写每张图的**可读文字摘要**，再画关系线。图形只强化结构，不能是唯一信息来源。
2. 一个视觉元素只表达一种关系；不用交叉箭头、装饰性分支或超过五种颜色。节点文字越长，越应压缩或用 `<details>` 放入来源说明。
3. 使用 `<header>`、`<main>`、三个 `<section>`、层级标题、列表、`<details>` 和有名称的链接；用 `<button>` 而非伪按钮。
4. 所有状态都用文字、图标/形状和颜色三重表达；关键内容不依赖 hover、拖拽、动画或位置。
5. 宽屏可横向展示因果轨与关系图；窄屏、键盘与打印版必须退化为线性卡片/列表。提供明显焦点样式和 `prefers-reduced-motion`。

## 生成步骤

1. 审核六份输入、其会话 `validation.json` 与 V1 verdict 的版本、状态与权威关系；记录 `open`/`delegated`/`provisional` 项。
2. 为世界、故事线、人物各建立一个“控制点清单”，每部分保留不超过五个主要视觉对象；超过时优先合并同类约束而非增加卡片。
3. 先完成三部分的文字摘要与评审问题，再填入模板的图形/关系区。
4. 从上游复制短而精确的措辞；压缩造成的归纳标为“简报归纳”，不伪称作者原话。
5. 生成 HTML，保留单文件、离线、可打印与移动端可读特性；页首门禁为 `awaiting_author_review`，页脚列输入版本和范围。

## 自检与交接

只有全部通过时才交付 `review-ready` 的 HTML：

- 六份输入均可追溯且 `ready`，每份均有关联会话的 `validation.json`，V1 verdict 为 `ready`；
- 正文恰好有“小说世界设定、小说故事线设定、小说人物设定”三部分；
- 世界图含中心、约束、职责与边界；故事线含选择、状态变化、汇合/停止规则与结局后果；人物卡含定义、目标、职责、边界和关系杠杆；
- 没有把记忆、开放项或未确认细节画成已发生的主线事实；
- 每个部分都给出嵌入式审阅提示；
- HTML 含 `<!doctype html>`、`lang`、标题、语义化主区、可见焦点、打印规则和输入来源；不含远程资源、占位符、正文、场景动作、未经确认的新设定或“已批准”表述。

交付给作者时，只说明简报位置、覆盖的输入版本、blocker（如有），以及作者可以批准、退回或要求修订。作者批准后，harness 写入 `author-approval.json`；只有该批准与 I0–I5、V1、V2 当前版本的哈希链全部有效时，才可作为自主构思 B0 的输入。不得调用旧 D1/R1 或 `novel-development-map-designer`；若作者退回某项，按 harness `workflow.md` 的唯一回退门处理。
