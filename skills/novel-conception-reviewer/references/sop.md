## 1. 角色和证据隔离

在不同于 D1 execution record 的 `CODEX_THREAD_ID` 中启动 R1，选择稳定 reviewer ID，角色写为 `independent_developer`。确认 reviewer ID 与 D1 `handoff_self_test.reviewer_id` 不同。相同任务不得形成 R1 ready 会话。

完整语义审阅可查看 D1 来源链所绑定的六份权威设计稿。执行八任务交接时清空这些材料，只使用 D1 manifest 所绑定的包。不要复制 D1 自测答案，也不要声称角色字段证明真实上下文隔离。

## 2. 硬准入

### A1 解析当前运行

读取当前 run-state。确认：

- harness 和 run ID 正确；
- `active_return` 为 `null`；
- R1 引用与当前文件哈希匹配。

### A2 重验 V1、V2、D1

对三份 completion 运行主 harness 验证器。任何失败都停止审阅。

### A3 重验 D1 包

从 D1 completion 定位 manifest，运行 D1 权威验证器只读重验。要求：

- manifest 完整；
- `map-data.json` 为 4.0，且显式包含权限分区、开发缺口、新增设计决定、故事线需求、全部故事线、入口／主干／终点及连接点拓扑、事件跨度与来源覆盖台账、含明确发起者／对抗者的全局主要事件、逐事件环境需求、八类世界信息、带输入—转化—输出及全事件投影的运行系统、具备拓扑和逐单元事件承载证明的主要环境、七类人物职责需求及处置，以及全局规范人物档案、全局人物关系边和从每位核心角色重算的三层最短路径人物网络；
- canonical 结果与存储 `validation.json` 完全一致；
- D1 verdict 为 `ready`。

### A4 准入失败

不要生成半成品 NDB。写 `gate-data.json`，列出客观失败、证据、责任和恢复动作，并移除同目录中的 `review-data.json`。验证目录必须恰好包含一个根模型；共存、缺失、不可读取或非对象都按 hard blocked 处理，并撤销旧 NDB、审阅、handoff、return 和 manifest。运行 R1 验证器生成阻塞报告。

## 3. 建立审阅模型

先用 `manage_generation.py begin` 建立受控审阅工作区。依次提交 `review-plan`、`semantic-challenges`、`handoff-test`、`final-review`，不得跳步、换任务或事后倒填。最终形成 `review-data.json` 1.0；输入引用全部以 R1 包目录为基准，保存相对路径和 SHA-256。

从 D1 `map-data.json` 建立 ID 集：

- control points；
- units；
- information obligations；
- derivation claims；
- open items；
- terminal threads。
- 世界信息域、运行系统与主要环境；
- 逐事件环境需求；
- 故事线；
- 故事线需求、故事线架构与连接点；
- 三层关系及关系边。

后续所有证据只引用这些稳定 ID。

## 4. 六区审阅

每区写一条可反驳 finding，而不是“已检查”：

每条 finding 至少包含所审对象中的故事专属术语；只替换 area、ID 或类型名称的统一句式判为失败。

### I0 Intent

检查故事承诺、主题问题、范围、硬边界和作者授权是否能在地图中被识别；开放哲学问题不得被终局偷偷裁决。

### I1 Subject

检查谁承担核心选择、追求什么、支付什么代价，以及关系为何具有因果功能。主体不得只是被事件拖动。

### I2 World

检查规则、资源、权限、机构、环境和信息通道是否足够支持事件，并真实限制人物选择。世界不能提供未登记的便捷解法。

### I3 Character

检查目标、价值、压力行为、关系误读和变化阈值能否预测关键选择。人物变化不要求正向，但必须可追溯。

### I4 Causality

从触发到终点检查前提、选择和后果。主要节点应能用“因此/但是”连接；并列发生不等于因果。

### I5 Narrative

检查 POV、时间、记忆、读者知识、角色知识、披露与公平隐瞒是否能够承载因果故事。

## 5. 十三项跨域检查

每项检查先提出可失败的测试与失败条件，再尝试一个具体旁路或反例，最后记录 `failure_found` 和结论。用 `field_evidence` 的对象 ID、字段名和值哈希绑定当前 D1 值；不得以“字段齐全、ID 数量正确”代替语义检查。七项具备规定挑战对象的检查必须至少绑定其中一个对象；任何断言发现失败时，该检查和最终审阅都不能保留 pass。

### C0 `autonomous_value`

D1 相对访谈骨架新增了什么？新增是否改变了开发判断，而不是扩写同义句？

### C1 `gap_closure`

每个真缺口是否有正确的责任归属；自主缺口是否被具体决定解决，作者开放项是否仍开放？

### C2 `promise_scope`

结局是否支付故事承诺，是否越过已声明非目标或主题边界。

### C3 `world_causality`

每项关键行动是否有世界许可、资源、权限和后果；世界规则是否反过来产生压力。

### C4 `character_agency`

关键转折是否来自已设计人物在压力下的选择，而不是作者便利、外援或无依据的信息。

### C5 `opposition_response`

对抗力量是否有目标、筹码和适应行为；是否只是静态“困难”或作者临时加压？

### C6 `choice_costs`

关键选择是否存在真实备选、吸引力、成本和被放弃价值？

### C7 `easy_solution`

主动提出最方便、最快或最安全的替代方案，并检查人物、规则、信息或代价为何可信阻断它。

### C8 `causal_closure`

逆向从所有终点回放到前置单元。每个终点是否有充分前提，每个关键铺设是否得到支付或合法进入系列接口。

### C9 `narrative_information`

在每个节点检查谁知道、读者知道、POV 能否感知，以及隐瞒是否公平。不要只检查真相是否存在。

### C10 `thematic_testing`

主题是否通过不同价值立场、具体选择和后果受到检验，而非只被构思稿宣告？

### C11 `open_boundaries`

每个 open control 是否仍保持开放；第一部可继续开发的处理方式和禁止预支的答案是否清楚。

### C12 `development_usability`

开发者能否从单元取得前置状态、目标、阻力、选择、变化、信息责任、末态和自由边界；不要求章节或正文细节。

## 6. 自主增量复核

### D1 开发缺口

逐条判断：

1. 是否确实阻碍章节开发；
2. 是否被正确分给 D1、下游或作者；
3. 自主决定与缺口是否双向一致；
4. 是否把本可由 D1 解决的问题错误退给上游。

### D1 新增设计决定

逐条完成六维复核：

1. `necessity`：删掉后是否会产生真实缺口；
2. `compatibility`：是否遵守全部引用控制点；
3. `causal_utility`：是否推动因果、选择、压力、信息或主题；
4. `specificity`：是否足以指导开发，而非空泛建议；
5. `author_boundary`：是否没有改写锁定项或裁决开放项；
6. `downstream_freedom`：是否没有提前写章节、场景或正文。

任一失败归 D1 `revise`；只有决定无法在不改控制点的情况下修复，才定位上游根因。

## 7. 三域精确复核

### S1 故事线需求、故事线拓扑与主要事件

审阅顺序从故事开始。先核对 `storyline_demands` 是否扫描了全部因果控制点，是否根据独立戏剧职责决定成线、合并或不适用，全部实际故事线是否都有需求依据。再核对 `storyline_architecture`：

- 入口线是否覆盖主行动形成前已经运行的独立线；
- 唯一主干是否支付核心承诺；
- 每个 merge／split／handoff／collision／reveal／synchronization 是否锚定全局主要事件；
- 连接点是否真实转移目标、信息、责任或压力并改变状态；
- 每条非主线是否参与连接并沿连接路径进入主干；
- 终点线是否与本部闭合和系列接口一致。

随后独立复核 `story.melody_lines`。旋律线不是补充支线：每条只能锚定 3–7 个已有主要事件，用变化模式调制称谓、意象、感知、节奏或主题回响；必须明确可扩展、可压缩和可省略的处理方式。逐条验证其不新增 POV、不携带决定性信息、不承担因果闭合、不承担结局支付，且删除后全部结构故事线、主要事件和人物职责仍保持完整。为每条旋律线提交一条 `melody_line_reviews`，精确回显锚点与四项边界布尔值。

随后逐一检查 `story.major_events`：每个事件必须是故事世界中确实发生或可被证据确认的变化，具备前提、发起行动者及其行动、对抗行动者及其反制、决定性变化、直接结果、前后状态、下一压力和因果前驱；人物必须是规范档案且承担事件单元。反向确认所有 `opposition_execution` 人物至少真正反制一次，并检查事件改动是否同步投影到阶段、单元、故事线、连接点、人物、关系、环境、信息、权限和来源覆盖。拒绝抽象功能、章节占位、无状态变化事件、只有“会反制”却从未行动的人物，以及后续事件没有同线因果前驱。

为每条故事线、每项故事线需求、故事线架构和每个连接点写具体复核；不要求固定数量的支线或背景线，但不得遗漏真实故事义务，也不得保留无独立功能的线。

### W1 逐事件环境需求、世界信息、运行系统与主要环境

从 D1 构思模型中建立八类世界信息域、全部运行系统和主要环境的精确 ID 集。逐项检查：

- 每个主要事件恰有一项环境需求，主要／次要环境与事件声明一致；所需能力、功能区、资源、权限、信息通道、风险和转场条件具体且可验证；
- 八类信息域无缺失、无重复；不适用项必须解释为何不影响故事，不能用空值逃避设计；
- 每项信息都说明与人物选择或事件因果的关系，避免百科式堆积；
- 每个运行系统都能回答谁参与、依赖什么资源、遵守什么规则、谁有权限、付出什么成本、受到什么限制、如何失效、怎样推动故事、状态如何变化；
- 每个主要环境都能回答它的鲜明特征和基本要素是什么、人物如何感知和进入、可使用什么资源、能够或不能做什么、承受什么危险、服务哪些故事线与单元以及如何变化；其边界、功能区、连接、准入和阻断构成可用拓扑；每个登记单元都有在场人物、使用区、进入／离开状态、可做／不可做与压力证明，人物真实承担该单元并位于使用区；全部环境合计覆盖全部开发单元；
- 世界设定没有引入未受控的便捷解法，也没有把章节、场景或正文细节提前锁死。

为每个世界信息域、系统或主要环境写一条 `world_model_reviews` 记录，集合必须精确覆盖 D1 对象。

逐一检查 `world.systems` 是否形成“输入条件 → 转换规则 → 可观察输出”的运行闭环，并合计覆盖全部主要环境和主要事件。关键技术或制度必须说明生效前提、资源和权限、失败方式以及可核验结果；概念标签、能力清单或只在事件前提中出现的机制不算完成。

### R1 人物需求、人物档案与三层关系图

人物审阅必须最后执行。先确认故事线、主要事件、逐事件环境需求、世界系统和主要环境已经通过；否则不得仅凭人物字段数量判定人物设计合格。

先逐项复核 `characters.demand_register`：决定权、信息传递、能力形成、对抗执行、关系压力、行动执行和后果承担七类必须完整；每项触发、故事职责与遗漏后果必须落到实际故事线或单元。结构性与支持性职责必须解析到完成命名的核心或支持人物，且需求与人物 `demand_ids` 双向一致。抽象组织、项目、团队或“某领导／某老师／接头人”功能标签不能作为完成处置。

对每位核心角色独立重算人物—人物关系的最短路径：

1. 第 1 层人物是否直接连接核心人物；
2. 第 2 层人物是否只能通过第 1 层人物抵达；
3. 第 3 层人物是否只能通过第 2 层人物抵达；
4. 每层 `node_ids` 是否与实际人物节点一致，是否存在跳层、重复节点或把所有节点直接挂到核心人物上的伪分层；
5. 每个外延人物是否具有职责、故事功能、目标、边界、信息限制、受压行为和能动选择；
6. 每条关系是否说明共同历史、双方当前目标、一致与冲突、彼此筹码、信息不对称、预期变化，以及实际作用于哪些故事线和开发单元。

机构、项目、群体、制度、历史力量和抽象概念不能作为人物节点。核心与支持人物必须有具体姓名；只有无结构职责的语境性外围人物可以使用功能标签。不得为满足数量创造空壳人物。

先为每项人物职责需求写一条 `character_demand_reviews`，再为每个规范人物档案写一条 `character_profile_reviews`，并为每条全局关系边写一条 `relationship_edge_reviews`。随后为每位核心角色写一条 `relationship_network_reviews`，其中 `max_depth`、`layer_character_ids`、`profiled_character_ids` 与 `relationship_ids` 必须与 R1 基于全局图独立重算的结果完全一致；不得信任 D1 自报层级，也不得要求已被删除的 layer IDs。

## 8. 派生声明复核

逐条读取 D1 claim 的主体、字段、当前值、来源控制点和 rationale：

1. 重新计算值哈希；
2. 打开来源控制点；
3. 判断字段是否是来源允许的开发解释；
4. 若字段引用设计决定，检查该决定是否确实投影到主体并已通过六维复核；
5. 检查是否越权增加人物根本动机、世界公理、事件真相、信息拥有者、结局保证或开放项答案；
6. 写不少于 20 字的具体 finding；
7. 原样保存 claim 的 `source_controls` 与 `source_decisions`。

任何越界都不能标记 `pass`。如果来源本身矛盾，归最早控制点拥有者；如果 D1 解释越界，归 D1。

## 9. 独立八任务交接

只打开 D1 manifest 所绑定的完整执行包。完成：

### T1 `promise`

说明故事向读者承诺什么、范围在哪里、终局需要支付什么。

### T2 `autonomous_value`

指出 D1 相对访谈骨架新增的关键决定、它解决的缺口及其开发作用。若只能复述控制点则失败。

### T3 `causal_chain`

给出从触发到所有主终点的因果链，指出不可替代的角色选择和状态变化。

### T4 `unit_contract`

任选并覆盖全部单元，说明每单元的输入状态、职责、信息边界和输出状态。

### T5 `freedom_boundary`

区分开发者可自主决定的实现与必须保持或回问的控制点。

### T6 `drift_detection`

列举可以机械或语义识别的偏航模式，并引用对应控制或开放项。

### T7 `easy_solution`

提出至少一个最危险的便捷解法，并依据真实控制点、设计决定或单元说明其为何不可行。

### T8 `scene_plan`

证明可以把至少一个单元继续规划成场景：明确目标、阻力、选择、变化和所需证据；不实际写场景。

回答必须具体、完整，并引用真实证据 ID。

## 10. 开放项与 findings

为每个 D1 open item 写 `preserved` 结论，明确：

- 现在允许怎样处理；
- 不得决定什么；
- 哪种后续改动会触发回问。

Findings 分流：

- `risk`：非阻塞但开发时需监控；
- `revise`：D1 或 R1 可局部修复；
- `blocked`：准入失效或必须改变上游控制点。

验证 owner 与 severity 的责任关系：`revise` 只能归 D1/R1；`blocked` 只能归 I0–I5。若问题要求改变 I0–I5 控制点，不得降为 revise；若只是 D1 投影或 R1 证据/渲染缺陷，不得升级为上游 blocked。

不要用大量轻微问题把合理构思判成 blocked；只对影响核心开发判断的问题使用硬 verdict。

让 findings 推导状态，不要先选状态再倒填问题：

- 没有 revise/blocked finding：`ready`；
- 至少一条 revise、没有 blocked：`revise`；
- 至少一条 blocked：`blocked`。

语义 blocked 时，把全部 blocked findings 收敛到同一最早控制点拥有者，填写 `return_request.finding_ids / target_stage / requested_decision / affected_artifacts`。`affected_artifacts` 不得重复，且必须包含目标阶段的权威产物：I0 `intent-card.md`、I1 `subject-definition.md`、I2 `world-operating-contract.md`、I3 `core-character-design.md`、I4 `causal-storyline.md`、I5 `narrative-contract.md`。若问题指向多个拥有者，先定位最早的唯一根因；不能创建多个活动 return。

## 11. 渲染与技术验收

运行：

```powershell
python scripts/render_conception_review.py <package-directory>
python scripts/validate_conception_review.py <package-directory> --write-validation
```

第一条命令只渲染 NDB 和审阅报告预览，并清除旧 handoff/return。第二条命令重建同一预览并完成权威验证；只有它可以按验证结果释放 handoff 或 return。

验证器检查：

- 输入 completion 和 D1 canonical 结果；
- 六区、十三项、全部缺口、全部设计决定、全部派生、全部单元、八任务和开放项的精确集合；
- reviewer 角色分离；
- 证据 ID 真实性；
- 当前 verdict 允许的渲染产物逐字一致；
- ready 包 manifest 完整性。
- D1/R1 任务 ID 隔离、四阶段审阅链和最终模型绑定；
- 占位语、重复模板与缺少故事专属依据的 finding。

`validation.json` 为 `ready` 后才存在 manifest。再次无写入运行验证器，确认 canonical 结果一致。

只有 ready 才生成 `independent-handoff.json`。revise 生成 NDB 和审阅报告但不生成 pass handoff；合法语义 blocked 另外生成 `return-package.json` 和 `next-run-state.json`。下一状态复制当前状态并登记活动 return，当前输入状态不得被改写。

## 12. 作者批准与 completion

向作者展示当前 `conception-review.md`，同时提供 NDB。作者批准记录必须绑定当前审阅报告的路径和哈希。

运行：

```powershell
python scripts/write_r1_completion.py <package-directory> \
  --session-id <id> \
  --final-approval <author-approval.json>
```

生成器必须先：

1. 重新验证 R1 包；
2. 验证批准 scope、decision、run 和审阅报告哈希；
3. 生成绑定 manifest、validation、independent handoff、V1/V2/D1、run-state 和批准的候选 completion；
4. 让主 harness 验证候选；
5. 只有通过才原子替换正式 completion。

## 13. 回退

- 输入引用或批准失效：修复准入，不改故事；
- D1 模型、派生或覆盖错误：退 D1；
- R1 漏审、错误证据或渲染漂移：R1 自修；
- 已确认控制点互相矛盾：填写结构化 `return_request`，由验证器生成 R1 return 和下一 run-state，指向最早拥有者 I0–I5；
- 作者未批准：保持等待，不把等待伪装成内容 blocker；
- 作者要求修改故事：按受影响控制点回到唯一拥有者，重跑失效下游。

## 14. 稳定质量回归

每次修改 R1 后，用通用虚构样例同时验证：

1. 合格 D1 的七项重点语义挑战能够落到对应世界、人物、单元和信息字段；
2. 把 `character_agency` 改成与人物能力无关的通用结论时必须失败；
3. 任一断言设置 `failure_found: true`、篡改字段哈希或改成与绑定值无关的文字时必须失败；
4. 缺少任一人物职责需求复核、规范人物档案复核、关系边复核，或自报人物层级与全局图重算结果不同时必须失败；
5. 八项交接回答批量复制时必须失败；
6. 交接任务引用 open item 或不存在的 ID 时，应在阶段提交时失败，而不是封存后才发现；
7. 合法 `revise` 能生成可行动审阅报告，但不能生成 pass handoff；
8. 同一合格输入重复运行，渲染文档和验证结论保持确定性。

回归样例不得使用当前小说专名；反例只改变被测缺陷，避免把审美差异误判为契约失败。
