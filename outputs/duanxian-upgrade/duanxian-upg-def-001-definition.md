### 2.1 目标

### 2.2 工作方法

采用“冻结证据—原子控制—版本处置—因果／权限／知识联合设计—场景消费—反例回归”的次序。先把每项必须保持与禁止暗示绑定到 E02 的确切 Pointer 和稳定来源 ID，再写新的展开；不从旧文本抽一段“看起来合适”的内容就升为当前事实。

## 第三节：根本原因分析与总体方案

### 3.1 系统性根因及证据边界

**根因 A：权威有说明，但跨版本消费没有逐项适配证明。** 项目 README 已写批准优先，故不能说仓库没有权威规则；真正的内容风险是六、七月角色和能力前提与八月基准不同，旧链内部的 pass、canonical 名称和丰富素材会给直接沿用造成错觉。周岚参与链跨 E04/E05，感官跨 E06，终止跨 E08/E09/E10/E11，说明问题不是单一文档错字。需要建立逐项保留／改写／退出／待批的消费入口，而非再补一句“以批准为准”。

**根因 B：缺少共同的知识与权限状态模型。** #9 直接赋予能力，#11 漏输入过程，#12 混身份识别和名称披露，#13 混记忆和证据，#10 混选择和执行。这是从反例归纳的共性机制，不是已经取证的开发历史。统一“信息来源—接收—推断—核验—披露”和“意愿—授权—执行—保管”两条链可以同时约束各层产物，避免修复一处又从另一处带回冲突。

**根因 C：历史派生文档与来源绑定粒度不足。** #3 的章节指称、#5 的逐字段 trace、#6 的评审版本文本分别暴露路径、内容、状态三个粒度的问题。只补路径或把摘要加长不能证明字段一致。新包必须把 BASE、源 Pointer、设计字段、消费节点和结果证据一起登记。

**根因 D：内容有效与工程可复验被混为一种“就绪”。** #1/#4 是可证布局机制，#2 是库存数据，#7 是本树证据不可得；其责任和关闭手段不同。不能把工程运行修好等同小说设计修好，也不能用内容报告代替机器准入。旧流程失败的历史因果没有在本作业调查，不编造“某次迁移导致全部问题”的单一解释。

### 3.3 四类联合设计的具体约束

**人物与公共责任。** 周岚条目必须同时出现无辜亲属、独立生活、知情范围、协查与拒绝边界；公开关联可能伤害她，不代表她实施袭击。行动层向现实团队提供必要信息，原因层保持必要访问边界；任何阻断方案都不能要求先公开她的私人身份。程予安的在世妻子、同意与非所有权边界同步保留。新体系不得把整个世界缩成两个主角加一个出卖者；角色责任依 E02 保持秦峥的授权、梁策的核验入口、贺闻钧的现实行动、唐黎的技术核验与苏望舒的静态保管分工。

**记忆到证据。** 一个可用信息对象至少经历 `subjective_fragment → hypothesis → external_check_requested → externally_supported / refuted / unresolved`。这是设计状态名，不是新增技术能力。每次状态变化有具体责任人、材料与时间；R-07 只能提供线索和自身主观解释，不能读外部档案后自封“独立验证”。现实材料确切内容若批准来源不足，标成待设计／待批，不直接把 E12 的门禁例子搬进新版事实。反证或未取得材料时，后续只能保持不确定或采用经批准的替代因果，不能继续按 confirmed 推进。

**通道与时间。** 07 的 `sent_at/received_at/earliest_use` 可以采用序关系事件 ID，无需编造精确日期；要求发送≤接收≤使用，内容精度及接收者权限不越界。未发送、已删除、等待和收到分开。击键压力、删除次数、房间声音不因出现在沈逾视角就自动可被 R-07 获取；相关旧正文 E11 `:245–271` 在适配时列为接口审查候选，不据此新增第十四条 ISSUE 或擅称本次全部已证。

**终局与公平隐瞒。** 采用以下事件相对顺序作为设计义务：合法线索交付→现实核验／授权／阻断→危机后存在困境与自主选择→告别交互及必要操作条件满足→沈逾实际执行→唐黎核验当前实例结束、无活动备份→静态资料按责任链保管→后续余波。选择形成的内部时点、沈逾相信的重载可能性、读者能看到的迹象、实际关停动作分列。批准人物条目已写沈逾相信可能重载的承诺，不能擅改成早已全知；也不能因此由叙述者保证复活。

内部 POV 的具体截断点须映射新版事件，不直接写“C5=K9=PRD-S15”。在决定性终止意图形成后禁止内部直示和伪造无知；读者仍能看到真实文字、动作和状态。技术记录拆成行动证据、主观认知、未决问题等内容对象，各自规定形成、接收、访问与披露；不会因统一叫“记录”就无限开放原因层（E11 `:417` 的无条件开放应列为关联适配点）。

### 4.3 LOOP 预算与升级／回退

建议冻结预算为首次实施＋最多两次定向修订（共三个候选），每个候选至少一次独立验收；这是本定义的流程设计，不是历史既定政策。每次 FAIL 由第三步输出第六节格式的修正指令，第二步按最早责任层修订，递增包版本，再重跑受影响链及全局硬约束。

同一 high 经过两次修订仍失败，或第三个候选仍有 blocker，停止扩大生成，提交 Owner 裁决：调整定义、补齐批准／证据或追加明确预算。不得把预算耗尽写成 PASS，不无限重跑。修正需改变本定义、范围或核心事实时必须版本化变更并重新批准相关部分；一般设计遗漏由第二步修正，无须把所有局部措辞问题升级给 Owner。

回退采用新候选／新提交或受控 revert，仅在实施分支撤回本轮新产物；保留失败版本与证据。不 reset/force push 历史、不动批准目录、不将旧 HLD 再标为现行。待证据／待批不是 FAIL 次数消耗，但必须明示未完成与下一责任人；无法在限定资源内取得依赖则交付阻塞说明，阶段仍未结束。

## 第五节：实施作业工作指令（实施指令）

实施作业必须严格遵守本节指令与第一至四节口径，不得遗漏和随意调整；偏离须在交付物中单独说明理由。

说明偏离不等于授权偏离。改变范围、核心事实、冻结输入或验收门必须取得相应批准；一般实现细节可在本节允许范围内决定。以下每步均须登记输入版本、实际动作、产出、结果及未决依赖。

### 步骤 0：确认作业契约与候选版本

**输入：** 已通过定义验收的本文件提交、实施作业自己的 spec/PROMPT、BASE 与 ISSUE hash。

**动作：** 全文读定义及契约，核对工作分支、允许新增 U/ 的清单、网络和凭据范围。记录 `definition_commit`、`implementation_base`、原件 hash；若冻结定义缺少验收证据，保持候选研究状态，不冒称正式实施获准。不得继承定义作业的旧 ACK nonce 或复用它作为新作业确认。

**预期产出：** 00 中可追溯的输入登记；13 中前置核验结果。

**自检点：** 每一规定输入可读，未混用最新 main；既有文件未改。初始 dirty 文件逐一记录并隔离，不擅自清理用户修改。

### 步骤 1：建立当前权威与证据缺口登记

**输入：** E01–E03、E17、#7 与授权取得的同 run 材料。

**动作：** 核对 approved/conception、ready、run、manifest 与 handoff 引用。若机器本体可经受控渠道取得，在明确授权环境按当前正式契约复验版本、hash、来源、状态与 validator；保存脱敏证据引用。若未取得，只读当前批准人审材料形成控制投影，标明它不是 P1；继续后续不依赖机器消费的设计。不得伪造缺失文件或放行正式基线。

**预期产出：** 00、01 初版；#7 的实际依赖状态，formal_hld_admission 明确。

**自检点：** 每条批准控制有真实 Pointer；批准源 ID 没取得就标缺口，不填猜值。未决来源不得被 summary 字段掩盖。

### 步骤 2：完整读取原 ISSUE 与建立历史处置

**输入：** 全部 13 条原文，第一节索引及原件。

**动作：** 每条写现场、需求、证据、原关闭条件、裁决、责任、对应产物；逐文件核对适配点。制作 #3 的 17 路径＋5 内容映射；制作 #5 的替代声明；保留 #6 版本歧义。不把 #1/#2/#4/#6/#7 改成修复完成。

**预期产出：** 02、03、10 初版及 13 的全 13 行框架。

**自检点：** 17 个源和目标均可解析；五个内容项有实际比较结论。每个旧片段处置均给去向；历史文件字节不变。

### 步骤 3：提出决策并封住未批事实

**输入：** D01–D03、批准人物与事件控制、步骤 2 差异。

**动作：** 将需要的具体选择写成可审定备选、推荐、影响与受影响节点，不提出空泛“是否同意升级”。登记已有 Owner 决定或继续待批。建立可继续的独立节点和受阻分支，不因待批停下所有工作。

**预期产出：** 11 和 00/12 中的 decision dependency。

**自检点：** 无签认不填 approved；未批身份、责任人、终局关键机制没有混入确定性设计。独立事实的设计仍可推进。

### 步骤 4：重建人物、能力与证据责任

**输入：** 01、02、11，E02 当前人物／世界。

**动作：** 以当前角色控制为锚点建立 04；周岚保护理由与参与袭击脱钩，程予安同意保留，现有授权、核验、执行和保管角色各有职责。建立 05 的接口、记忆、推断与核验规则，实际列出失败条件和反证。

**预期产出：** 04、05；每一派生字段绑定控制及理由。

**自检点：** 不把职务相似当角色同一；R-07 无视觉／听觉／身体／自关停／外部操作；主观片段不生成客观确认。

### 步骤 5：建立因果与知识联合模型

**输入：** 04/05、当前批准故事主轴、可取得的正式事件／故事线来源。

**动作：** 写 06，逐事件给前置、行动、结果、代价和权限；写 07，逐知识变化给来源、发送／接收／使用次序及披露。把公共安全闭环与原因层保护并行设计，任何信息获取和权限提升都有合法责任人。旧编号建立带版本的多对多对应，不按数字硬配。

**预期产出：** 06、07，当前控制／人物／事件覆盖矩阵。

**自检点：** 不把原报告摘要中八次推进等同八事件；当前正式来源不可得的覆盖不谎称完整。先用后到、无来源结论、未批核心事实、主体混同均为阻塞。

### 步骤 6：设计终局与披露

**输入：** 06/07、E02 `/decision_controls/4`、当前两核心人物与运行／保管控制，D03 状态。

**动作：** 写 08 状态机及逐内容披露表；分开决定形成、R-07 输出、沈逾理解、读者获知、授权、实际关停、核验和保管。建立新版 POV 截断点并映射旧 C5/PRD-S15/K9 的功能差异。用两种旧终局分别作为负例，不误写七月版为自行关停。

**预期产出：** 08，更新 07 的终局信息对象。

**自检点：** 告别前无决定性内心直示；沈逾真实执行；她的相信不被叙述者变成复活保证；行动证据没有随关停失去必要核验依据；无活动备份、无非法开放原因层。

### 步骤 7：形成场景规格与逐段适配指令

**输入：** 04–08、11、完整旧正文和所有关联素材。

**动作：** 写 09，每个功能单元都有输入状态、具体选择、输出状态和可观察检验。展开 3.4 六个重点单元并覆盖其前后依赖及当前主轴；完成 10 的每个旧段对应与替代指令。#11 明确采用删除精确十秒依赖或合法转述的哪条设计路径；#12 若待批保留分支，不把二选一模糊地留给写作 Agent。相容的过去片段与克制表达可以保留，但绑定当前边界。

**预期产出：** 09、10，完整设计交接内容。

**自检点：** 下游能按表细化而无需发明新事实；设计中没有可发表成套正文；旧稿正文没有修改；`writing_status` 如实为待实施或授权外。

### 步骤 8：组装追踪与消费包

**输入：** 00–11 全部稳定版本。

**动作：** 写 12，将每条控制与 ISSUE 映射到具体设计字段、场景和回归 ID；逐字段检查值与来源的语义关系。为每个历史资产写消费禁用／替代边界，为 Owner 待批和工程门列暂停条件。README 指向唯一入口，形成 manifest；hash 对实际 UTF-8 文件字节计算，不对打印后的等价 JSON 计算。

**预期产出：** README、12、manifest 候选；#5 可审计替代记录。

**自检点：** 无悬空引用、无循环自哈希、无以源 ID 存在替代语义证明；正式 completion 与本适配包状态不混用。

### 步骤 9：实施自检与消费演练

**输入：** 冻结候选、原 ISSUE、第五节执行记录、第六节用例。

**动作：** 执行路径／hash／字段／引用／顺序核对；逐条做正例和负例语义检查。消费演练仅从 12 指定的交接内容重建重点场景的步骤与边界，封存结果后再比对完整设计。若同一实施者无法获得独立上下文，标明这是自检演练，将正式独立消费留给第三步，不伪称独立验证。

**自检点：** 不能以 grep 零命中代替全文语义审查；不能在被检查的正式候选中插入负例。负例用隔离副本，运行目录必须在实施作业授权工作区内。每条用例保留版本、输入、方法、实际结果、证据。

**输入：** 自检通过的候选或明确标记阻塞的阶段性交付，实施作业的分支与凭据授权。

## 第六节：独立验收作业检查单（验收检查单）

### 6.1 验收输入与职责

验收者取得固定 definition_commit、implementation_commit、manifest、原始 ISSUE、批准来源和决定证据。先核对提交、路径、hash，再读具体内容；不从实施摘要推断通过。A/ 至少交付 `acceptance.md`、`issue-regression.csv`、`findings.md`、`correction-instructions.md` 和 `evidence-index.json`。这些是拟建验收文件，当前作业不创建它们、不代签第三步结论。

检查单按下列顺序执行，并保留证据：

1. 六要素：目标与实际交付一致、方法可追溯、写入未越界、硬约束全覆盖、交付完整、标准未降级。
2. 总体方案：版本入口唯一；角色责任、能力、因果、信息、终局、场景使用同一控制；不能只有六个 ISSUE 的局部替换清单。
3. 路线图：输入/输出/模型配置记录和候选轮次可追踪；FAIL 有修正闭环；未把定义、实施自检或 Owner 待批伪装成独立通过。
4. 工程证据边界：#1/#2/#4/#6/#7 留存真实；若另行完成，检查单独授权与完整关闭证据，不接受口头“顺手修了”。
5. 作者边界：E03 原批准不被改写；D01–D03 有确定状态，任何改变核心事实的设计只有获得明确批准才可无条件消费。
6. 来源／字节／引用：全交付清单 hash 一致，旧文件不变，17+5 映射完整，逐字段追踪可回读，不以 Markdown 阅读投影代替正式 canonical。
7. 消费能力：在独立上下文先仅读 handoff 及其允许的交付材料，重建重点场景输入、动作、边界与验收，密封后对照正式候选；凡需自行找旧正文补事实即消费失败（E01 `:146–149`）。
8. 内容质量：人物有具体选择及代价，关系改变信息／责任／权限；公共危机由现实团队完成，亲属不成为筹码，告别不取消伦理余波。不用机械完整替代文学因果判断。

REG-03 还须附一张完整 22 行结果表，不允许“17项均通过”但无逐条证据。REG-08 至 REG-13 每条至少一个正例和一个负例，high 四项必须做跨人物／事件／信息／场景的完整链路走读。每个实际结果绑定候选提交与 manifest，修订后旧结果失效。

### 6.4 FAIL 修正指令与复验输入格式

第三步发现问题时，必须输出可供第二步直接执行的修正单，格式如下；字段中的故事陈述仍须引用来源，不能把验收者新设定当修复要求：

```yaml
finding_id: ACC-001
definition_commit: <固定提交>
implementation_commit: <被验候选>
manifest_sha256: <实际清单哈希>
severity: high
issue_refs: [10]
failed_checks: [REG-10, NEG-ENDING]
expected: <批准控制及定义书条款>
observed: <实际设计字段或文本与证据定位>
root_owner: <最早负责的产物/阶段>
correction:
  inputs: [<批准来源>, <受影响设计>]
  actions: [<需修正的具体关系或遗漏>]
  expected_outputs: [<路径/节点/状态变化>]
  forbidden_shortcuts: [<不能仅改标签/不能增加感官等>]
affected_consumers: [<必须同步重验的场景及交接项>]
retest: [<原失败用例>, <关联正负例>, <全局硬约束>]
owner_decision_required: false
loop_index: 1
remaining_revision_budget: 1
```

修正应指明错误关系和期望，不代作者创作新凶手或新机制。若需要新决定，`owner_decision_required=true` 并引用决策提案；第二步可以继续其他独立项。每次复验核查原失败点、受影响依赖和全部硬约束，不能只回跑一个已经被改过的关键词。

### 6.5 最终判定与证据交付

验收报告至少含定义版本、候选版本、检查覆盖、逐 ISSUE 双状态、Owner 决策、正式机器准入状态、正文／工程留存、发现及 LOOP 建议。`design_verdict=PASS` 必须有内容、来源、独立消费和必要批准的共同证据；若只有结构／hash 通过，结论只能说明这些机械项通过。

全 13 条原始关闭条件仍未满足时，报告不得写“所有 ISSUE 已解决”；设计范围内已通过也不得代 Owner 关闭 ISSUE。独立验收存在 FAIL、必要决定待批或必要证据未取得，阶段不得结束，按三步协议回到实施或依赖责任人。既有批准、历史失败、新版候选、最终正式准入各自保持自己的真实状态。
